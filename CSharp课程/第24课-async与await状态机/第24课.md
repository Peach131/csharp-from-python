## 一、一句话回答：await 到底做了什么

先记住这一句，本课剩下所有内容都是它的展开：

> **`await` 不是「暂停线程」，而是「把方法拆成多段并返回」。**

如果你是从 Python asyncio 过来的，这句话会立刻触发一个疑问：

```python
async def fetch():
    print("A")
    await asyncio.sleep(1)     # 这里让出了控制权……
    print("B")                 # ……但醒来时还是在【同一个线程】上
```

因为 asyncio 只有一个线程，Python 程序员的直觉是
"`await` = 让出控制权，等会儿回来接着跑，**我还是我，线程没变**"。
C# 不是这样。把 `await` 的真实过程拆成四步：

```
1. 遇到未完成的 Task  →  方法【直接 return】（返回一个未完成的 Task 给调用方）
2. 调用方线程被释放   →  它去干别的事了（不是"卡住"，是"走了"）
3. Task 完成后        →  由线程池线程（或 SynchronizationContext）
                         再次调用状态机的 MoveNext() 继续执行
4. 所以               →  【await 之后可能在不同的线程上】！
```

第 1 步最反直觉：**`await` 会让你的方法"返回"** ——
不是暂停、不是挂起、不是把栈留着等，是真的 `return` 了，栈帧被弹掉。
第 3 步则解释了"局部变量为什么还能用"：它们早就被搬进了一个**堆上的对象**（状态机）。
而**第 3 步也是 C# 与 Python 唯一分道扬镳的地方**：Python 的协程同样是"挂起并返回"
（`await` 把控制权还给事件循环），但醒来时还在同一个线程；
C# 醒来时可能是另一个线程 —— 「await 之后线程可能变」是 C# 独有的心智模型，
是本课最需要你"重建直觉"的一处。

## 二、亲眼看到线程 ID 变化（必跑）

理论说完了，现在看证据。核心就一个 API：`Environment.CurrentManagedThreadId`。

**示例里最核心的那段**（`Lesson24Demo\Program.cs`）：

```csharp
static async Task ThreadHopAsync()
{
    Log("进入方法（await 之前）");    // ① 这段仍然跑在【调用者线程】上
    await Task.Delay(80);
    Log("第 1 个 await 之后");
    await Task.Delay(80);
    Log("第 2 个 await 之后");
    await Task.Yield();               // ② Task.Yield()：几乎一定换线程
    Log("Task.Yield 之后");
}
```

**实测输出**（线程号每次运行都不同，看"变没变"）：
```
[14:22:01.100] Main 开始               线程  1 （非线程池）
[14:22:01.101] 进入方法（await 之前）   线程  1 （非线程池）
[14:22:01.183] 第 1 个 await 之后      线程  1 （非线程池）   ← 没变！
[14:22:01.265] 第 2 个 await 之后      线程  4 （线程池）     ← 变了
[14:22:01.268] Task.Yield 之后         线程  7 （线程池）     ← 又变了
[14:22:01.269] 回到 Main               线程  7 （线程池）
```

### 三个必须看出来的点

**① `await` 之前那行，和 Main 是同一个线程。**
`async` 方法在遇到第一个**未完成**的 `await` 之前，是**完全同步执行**的。
`async` 关键字不会让方法"自动异步"，它只是**允许**你在里面写 `await`。

**② `Task.Delay` 之后线程可能"没变" —— 这是允许的。**
.NET 的计时器会优先把续体塞回"刚刚空出来的那个线程"，这是性能优化。
所以正确的说法是【**可能**变】，不是"一定变"也不是"一定不变"。
**真正不能做的是：假设自己在哪条线程上。**

**③ `Task.Yield()` 之后几乎一定变**（`await Task.Yield()` ≈ Python 的 `await asyncio.sleep(0)`）。
它做的事就是"把自己重新排回线程池的队列"，所以是强制让出的标准手段。

> **`Task.Delay` vs `Thread.Sleep`**（本课最重要的一个对比）：
> `await Task.Delay(1000)` 只是定个闹钟就把线程还回去，1 秒后由线程池唤醒；
> `Thread.Sleep(1000)` 则把线程按住一秒，什么都干不了。
> **在 `async` 方法里用 `Thread.Sleep`，你就把整个异步链毁掉了**：线程不会被释放，
> 也就没有"并发"可言。而编译器**不会报错**（方法里还有别的 `await` 就不触发 CS1998），
> 所以这个错误经常一路溜到生产环境。

## 三、async 方法被编译成了什么

第 17 课说"顶层语句被包装成 `<Main>$`"，第 23 课说"闭包变成 `<>c__DisplayClass`"。
本课是同一套思路：**`async` 方法变成一个实现了 `IAsyncStateMachine` 的类型**。
下面左边是你在 `ThreadHopAsync` 里写的，右边是编译器生成的（去 ILSpy 里能看到真货）：

```csharp
// 你写的                              // 编译器生成的（节选）
static async Task ThreadHopAsync()     [CompilerGenerated]
{                                      private struct <ThreadHopAsync>d__8 : IAsyncStateMachine
    Log("进入方法");                   {
    await Task.Delay(80);                  public int <>1__state;                      // ★ 第几段
    Log("第 1 个 await 之后");             public AsyncTaskMethodBuilder <>t__builder; // ★ 返回的 Task
}                                          public TaskAwaiter <>u__1;                  // 这次 await 的 awaiter
                                           void IAsyncStateMachine.MoveNext()
                                           {
                                               int num = <>1__state;      // 先看"我停在哪一段"
                                               try {
                                                   TaskAwaiter awaiter;
                                                   if (num != 0)          // ── 第 0 段：await 之前 ──
                                                   {
                                                       Log("进入方法");
                                                       awaiter = Task.Delay(80).GetAwaiter();
                                                       if (!awaiter.IsCompleted)     // ★ 还没完成
                                                       {
                                                           <>1__state = num = 0;     // 记住停在第 0 段
                                                           <>u__1 = awaiter;         // awaiter 搬进字段
                                                           <>t__builder.AwaitUnsafeOnCompleted(ref awaiter, ref this);
                                                           return;                   // ★★ "直接 return"
                                                       }
                                                   }
                                                   else { awaiter = <>u__1; <>1__state = num = -1; }
                                                   awaiter.GetResult();   // 异常在这里抛出（关键！）
                                                   Log("第 1 个 await 之后");   // ── 第 1 段：await 之后 ──
                                               }
                                               catch (Exception e) { <>1__state = -2; <>t__builder.SetException(e); return; }
                                               <>1__state = -2;
                                               <>t__builder.SetResult();                  // ★ 完成 Task
                                           }
                                       }
```

**注意 `MoveNext()` 里那个 `return`** —— 那不是"暂停"，那是真的从方法里出去了。
调用方拿到的 `Task` 就是 `<>t__builder` 里那个"还没完成的凭证"。
而 `await` 恢复时，是**外部**（定时器线程、线程池）再次调 `MoveNext()`，
`switch(state)` 直接跳到第 1 段 —— **前半段不会重跑**。

### 三个必须记住的点

| 现象 | 底层原因 |
|---|---|
| `await` 之后局部变量还在 | 它们被**提升成状态机的字段**（在堆上），不是留在栈上 |
| `await` 恢复时"从中间继续" | `<>1__state` 记住段号，`MoveNext()` 一进来先 `switch` 跳过去，**不重跑前半段** |
| async 方法有时"零分配" | 状态机是 `struct`。只有真的遇到未完成的 `await` 才被装箱到堆上 |

### 自己验证：让反射把真货摊开

`Lesson24Demo` 第二节就是干这个的：遍历 `GetNestedTypes()`，找名字以
`<ThreadHopAsync>` 开头的那个类型，然后打印它的字段。**实测输出**（节选）：
```
  完整名字：LessonPractice.Lesson24Demo+<ThreadHopAsync>d__8
  是值类型（struct）：True        接口：IAsyncStateMachine
  【字段】—— 这就是 await 期间「活下来」的全部家当：
    Int32                        <>1__state
    AsyncTaskMethodBuilder       <>t__builder
    TaskAwaiter                  <>u__1
```

> ⚠️ 类型名里那个数字（`d__8`）**会变**：你加一个 async 方法它就可能重排。
> 所以反射时按"名字规律"筛，别写死编号 —— 这也是练习 TODO 3 的隐藏考点。
> **另外两个你迟早会遇到的怪东西**：堆栈里出现 `<FooAsync>d__12.MoveNext()`
> 不是 bug，就是状态机在跑；而 `static async Task Main()` 也是同一套机制
> （编译器生成 `<Main>$` 状态机，外面套一个同步 `Main` 去调 `GetAwaiter().GetResult()`）
> —— **`Main` 里的 `await` 和你自己方法里的 `await` 完全一样**。

## 四、顺序 await vs Task.WhenAll（实测耗时）

这是 `async` 最实用的收益，也是最容易写错的地方。

```csharp
// ① 顺序：一个等完再起下一个
int a1 = await FakeIoAsync(1, 150);
int a2 = await FakeIoAsync(2, 150);
int a3 = await FakeIoAsync(3, 150);

// ② 并发：先把三个任务全"启动"，再一起等
Task<int> t1 = FakeIoAsync(1, 150);   // ★ 这一行调用下去，方法就已经在跑了
Task<int> t2 = FakeIoAsync(2, 150);
Task<int> t3 = FakeIoAsync(3, 150);
int[] results = await Task.WhenAll(t1, t2, t3);
```

**示例实测输出**：
```
  理论值：顺序 = 3 × 150 = 450 ms；并发 ≈ 150 ms
  ① 顺序 await 三次： 452 ms   结果 10, 20, 30
  ② Task.WhenAll 三个： 153 ms   结果 10, 20, 30      实测倍数：2.95 倍
```

### 为什么"先创建 Task"才能并发？

这是全课最容易被 Python 经验带偏的一处：

| | C# | Python asyncio |
|---|---|---|
| `t = FetchAsync(1)` | **立刻开始执行**，跑到第一个 await 才返回 | 只是**造了个协程对象**，一行都没跑 |
| 什么时候开始跑 | 方法被**调用**时 | 被 `await` / `gather` 时 |
| 并发写法 | `Task.WhenAll(FetchAsync(1), FetchAsync(2))` 或先建 Task 再等 | **必须** `asyncio.gather(fetch(1), fetch(2))` |

```python
coro1 = fetch(1)          # Python：什么都没发生
await coro1               # 到这一行才开始跑
```

```csharp
Task<int> t1 = FetchAsync(1);   // C#：调用即启动，所以"先建后等"就是并发
Task<int> t2 = FetchAsync(2);   // 也已经在跑了
await Task.WhenAll(t1, t2);     // 只是"等它们都结束"

var t3 = FetchAsync(3); var r3 = await t3;   // ❌ 退化成串行：等完了才起下一个
```

**所以：`await` 是「等」，不是「启动」。** 想让 N 件事同时进行，
就必须在 `await` 之前把 N 个 Task 全创建出来。

### 附赠：Task.WhenAny（谁先完谁先处理）

```csharp
var tasks = new List<Task<int>> { JobAsync(1, 120), JobAsync(2, 40), JobAsync(3, 80) };
while (tasks.Count > 0)
{
    Task<int> finished = await Task.WhenAny(tasks);   // 只等"最快那个"
    tasks.Remove(finished);
    Console.WriteLine($"完成：{finished.Result}");      // 这里 .Result 安全：已经完成了
}
```

≈ Python 的 `asyncio.wait(..., return_when=FIRST_COMPLETED)`。

## 五、与 Python asyncio 的本质差异（背下来）

| | C# async/await | Python asyncio |
|---|---|---|
| 模型 | 状态机 + 线程池（**真并行**） | 事件循环（**单线程并发**） |
| await 后线程 | **可能变化** | **永远是同一个** |
| 阻塞调用的后果 | 只阻塞当前线程池线程 | **卡死整个事件循环** |
| 协程何时开始执行 | 调用即开始（返回运行中的 Task） | 被 await/gather 时才跑 |
| CPU 密集任务 | `Task.Run` 扔线程池，**真并行** | 需要 `ProcessPoolExecutor`（有 GIL） |

**把"阻塞的后果"这一格讲透**：`Thread.Sleep(3000)` 在 C# 里只是睡死一个线程池线程
（池子里还有几十上百个，别人继续跑）—— 这是**性能问题**；
而 `time.sleep(3)` 在 Python 里是把唯一那条跑事件循环的线程按住 3 秒 ——
**所有并发任务一起卡住，这是事故**。

所以 Python 程序员对"别在协程里写阻塞代码"的敏感度往往比 C# 程序员还高。
反过来，C# 程序员容易犯的错是"反正线程池顶得住，随手 `Thread.Sleep`" ——
在 ASP.NET Core 高并发下这就是线程池饥饿的经典成因。

**判断标准（背下来）**：

> 这个操作在等的时候，**需不需要一个线程站着**？
> **不需要** → 用异步 API（`Task.Delay` / `ReadAsync` / `WriteAsync` / `HttpClient`）
> **需要** → 它是 CPU 计算，用 `Task.Run` 交给线程池，或者干脆同步跑

## 六、四条铁律

### 铁律 1：**绝不**用 `.Result` / `.Wait()`（UI 程序会死锁）

成因见下一节（专章）。替代方案永远有：

```csharp
✅ static async Task Main()                 // 一路 async 到底（本课所有示例都是）
✅ task.GetAwaiter().GetResult()            // 真的在同步方法里时用；不包装异常
✅ Task.Run(() => task).GetAwaiter().GetResult()  // 换个线程等，不会和 UI 线程撞上
❌ var data = FetchAsync().Result;          // 永远不要
❌ FetchAsync().Wait();                     // 同上，且异常被包成 AggregateException
```

顺带记一个细节：`task.Result` 抛的是 `AggregateException`，
`task.GetAwaiter().GetResult()` 抛的是**原始异常**（和 `await` 行为一致）。

### 铁律 2：**绝不**写 `async void`（除事件处理器）

```csharp
static async void BadAsync()          // ❌
{
    await Task.Delay(20);
    throw new InvalidOperationException("没人接得住我");
}

try   { BadAsync(); }                 // ★ try 块会"正常结束"，异常还没发生
catch (Exception ex) { Console.WriteLine("抓到了"); }   // ★★ 永远不会执行
```

**为什么抓不到？** 因为 `async void` 没有 `Task` 可以装异常。
异常会被 **post 到当前 `SynchronizationContext`**：
WPF/WinForms 扔到 `Dispatcher` 上 → **进程崩溃**；控制台扔到线程池上 → **进程崩溃**。
唯一的补救是全局兜底（`AppDomain.UnhandledException`），但那时进程已经在死了。

对照 `async Task`：`await GoodAsync()` 的异常会**规规矩矩地抛在 `await` 那一行**，
一个 `try/catch` 就够 —— 同一个异常，只因签名不同，就从"崩溃"变成"一行 catch"。
**唯一允许 `async void` 的场合**：事件处理器的签名被框架钉死成 `void`，
而且内部必须自己兜住（`try { await DoWorkAsync(); } catch (Exception ex) { ShowError(ex); }`）。

### 铁律 3：库代码用 `.ConfigureAwait(false)`；UI 代码**不加**

```csharp
// 库代码（不知道谁来调）
var text = await File.ReadAllTextAsync(path).ConfigureAwait(false);   // ✅
```

- **加**的好处：续体不必回调用方的上下文 → 少一次调度、更快、
  **而且不会把调用方拖进死锁**（第七节会实测这个差别）
- **UI 代码不能加**：加了就回不到 UI 线程，下一行碰控件直接抛
  `InvalidOperationException`（"调用线程无法访问此对象"）

### 铁律 4：`await` 之后要更新 UI，靠的是 `SynchronizationContext`

它不是语言特性，只是"**谁来跑我的续体**"的一条协议。
示例实测输出：`当前 SynchronizationContext：null`（控制台就是这样）。

| 环境 | `SynchronizationContext.Current` | 续体在哪里恢复 |
|---|---|---|
| 控制台 / 服务端 | `null` | 线程池的任意线程 |
| WPF / WinForms | `DispatcherSynchronizationContext` 等 | **被投递回 UI 线程** |
| ASP.NET Core | `null` | 线程池（每个请求没有专属线程） |

所以你在控制台里学到的"线程 ID 天天变"，到了 WPF 里会变成"回到 UI 线程"。
**同一个 `await`，两种落点 —— 区别只在有没有上下文。**

## 七、专章：`.Result` 死锁的成因（图解）

这是本课唯一一个"会在真实项目里让你加班到半夜"的知识点。

### 慢动作回放

```
    UI 线程                          异步方法（FetchAsync）
    ────────                         ──────────────────────
    ① 调 FetchAsync() ─────────────→ 开始跑，遇到 await，
                                      把续体登记到 UI 线程的
                                      SynchronizationContext 上
    ② 拿到未完成的 Task             ←── return（人走了）
    ③ 调 .Result → 阻塞 UI 线程 ⛔
                                      Task 完成，上下文说：
                                      把续体投递回 UI 线程
    ④ 等续体执行                      ⑤ 续体排在 UI 线程的队列里
       ↑___________死锁___________↓     等 UI 线程空出来
```

### 一句话成因

> **`.Result` 阻塞的那个线程，正是续体唯一被允许运行的线程。**
> 我等你，你等我 → 谁都不动。

### 关键认知：不是"UI 线程特殊"，是"有上下文才这样"

- **控制台程序**：没有 `SynchronizationContext` → 续体去线程池 → `.Result` 其实能跑完
  （但依然是坏习惯，且在某些库里一样会死）
- **UI 程序 / 老 ASP.NET（有 `AspNetSynchronizationContext`）**：续体必须回那条线程 → **死锁**

### 亲手复现（但不会把程序挂住）

`Lesson24Demo` 第七节用一个"沙盒"：自己造一个**单线程 `SynchronizationContext`**
（模拟 UI 线程），然后用**带超时的 `Wait`**（`.Result` 的安全替代品）去等：

```csharp
Task<int> call = MakeCallAsync(context, continueOnCaptured: true, uiThreadId);
bool completed = call.Wait(TimeSpan.FromSeconds(1));    // 1 秒拿不到就判定死锁
```

**实测输出**：
```
  ── 复现 ①：有 SynchronizationContext，库代码没加 ConfigureAwait(false) ──
     模拟 UI 线程 = 7（它接下来会被 .Result 阻塞住）／调用方线程 = 1：开始 .Result
     ⛔ 1 秒内没等到 —— 死锁确认。call.Status = WaitingForActivation
  ── 复现 ②：同样的 .Result，但库代码加了 ConfigureAwait(false) ──
     续体恢复于线程 9（是不是那个 UI 线程：False）
     ✅ 跑完了！（续体不要求回 UI 线程，直接在线程池上跑）
```

**同一个调用方、同一个 `.Result`，只改了库代码的一行 —— 一个死锁、一个正常。**

```csharp
await Task.Yield();                        // 会回上下文 → 死锁
await Task.Yield().ConfigureAwait(false);  // 不回上下文 → 活
```

### 所以这条铁律有两面

- **写给别人的库**：加 `ConfigureAwait(false)`，别把调用方拖下水
- **调用别人的库**：永远不要写 `.Result`
  > 库作者做对了是运气，调用方写对了才是本分。

## 八、上下文不等于线程：AsyncLocal

一个常被混淆的点：`await` 换的是**线程**，不是**逻辑上下文**。

```csharp
var requestId = new AsyncLocal<string> { Value = "REQ-42" };
Console.WriteLine($"await 之前：线程 {Environment.CurrentManagedThreadId}");
await Task.Yield();
Console.WriteLine($"await 之后：requestId = {requestId.Value}，线程 {Environment.CurrentManagedThreadId}");
```

**实测**：线程号变了，`REQ-42` 没丢。

| | 跟着什么走 | 跨 `await` 之后 |
|---|---|---|
| `Environment.CurrentManagedThreadId` | 线程 | **可能变** |
| `[ThreadStatic]` 变量 | 线程 | **会丢（变成 null）** |
| `AsyncLocal<T>` / `ExecutionContext` / `SynchronizationContext` | 异步控制流 | **不丢** |

`AsyncLocal<T>` ≈ Python 的 `contextvars.ContextVar`。
`SynchronizationContext` 就存在 `ExecutionContext` 里，跟着 `await` 一路传播 ——
这也是为什么"线程 ID 变了但代码还能正常工作"：
线程是**物理资源**（会被复用、会变），执行上下文是**逻辑资源**（跟着流程走）。

## 九、常见坑速查

| 坑 | 症状 | 正解 |
|---|---|---|
| `async` 方法里用 `Thread.Sleep` | 线程不释放，并发收益归零 | 改 `await Task.Delay` |
| `await` 写成了"顺序两次" | 耗时叠加 | 先建 Task，再 `WhenAll` |
| `async void` | 异常无法捕获，进程崩溃 | 改 `async Task`（事件处理器除外） |
| `.Result` / `.Wait()` | UI 死锁 | 一路 `await`；实在不行带超时的 `Wait` |
| 库代码忘记 `ConfigureAwait(false)` | 把调用方拖进死锁 | 库代码每个 `await` 都加 |
| UI 代码里加了 `ConfigureAwait(false)` | 改控件抛异常 | UI 代码不加 |
| `async` 方法里没有 `await` | warning **CS1998** | 去掉 `async`，`return Task.CompletedTask` |
| 在 `lock` 里 `await` / 用 `ref`、`out` 参数 | **编译错误**（CS1996 等） | 换 `SemaphoreSlim.WaitAsync()` / 改成返回值 |
| 忘了 `await`（Fire-and-forget） | 异常静默丢失、顺序错乱 | 让 `await` 一路传上去 |
| 在 `async` 方法里捕获 `this` 后跨 `await` 用 | 对象生命周期被拉长 | 注意状态机会持有引用 |
**两个"看名字就该警惕"的信号**：编译器给 **CS1998**（此异步方法缺少 await）→
你写了"假异步"；堆栈里出现 `<XxxAsync>d__N.MoveNext()` → 正常现象，别慌。
