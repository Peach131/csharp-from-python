## 一、开胃菜：先看数字，再讲道理

本课最重要的不是定义，是**这个 API**：

```csharp
long before = GC.GetAllocatedBytesForCurrentThread();   // 读一次
// ... 你要测的代码 ...
long after = GC.GetAllocatedBytesForCurrentThread();    // 再读一次
long bytes = after - before;                            // 这段代码分配了多少字节
```

它返回**当前线程累计分配了多少字节**，只增不减。两次相减 = 这段代码制造了多少垃圾。

**现在看两条几乎一样的语句**（第 21 课示例项目里就是这么测的）：

```csharp
int    v = 42;          // 0 B/次
object o = 42;          // 24 B/次   ← 凭空多出来的 24 字节
```

**唯一的差别是左边的类型。** 一个 `int` 变量不分配任何东西；
一个 `object` 变量每次赋值都在堆上**新建一个对象**。

**这凭空多出来的 24 字节，就是"盒子"（box）。这个动作就叫装箱（boxing）。**

> **Python 对照 —— 这是本课最需要先讲清的一件事**
>
> ```python
> x = 42          # 42 是一个 PyLongObject，本身就在堆上
> y = x           # 只是多了一个引用，没有复制、没有新对象
> ```
>
> **Python 里根本没有"装箱"这个概念，因为 Python 里一切都是对象，而且一切都在堆上。**
> `42` 一开始就是一个完整的对象：有引用计数、有类型指针、有值。
>
> C# 不一样：`int` 是一个**纯粹的值**，4 个字节，可以住在栈上、可以内联在数组里、
> 可以塞进 CPU 寄存器 —— 正因为如此它才快。
>
> **但代价是：`int` 不是对象，它没有对象头，不能被 `object` 变量直接指向。**
>
> 所以当 C# 需要"把一个 int 当对象用"的时候，它只能：
> **在堆上临时造一个对象，把值复制进去，然后让引用指向它。**
>
> | | Python | C# |
> |---|---|---|
> | `42` 是什么 | 堆上的一个对象 | 一个 4 字节的值，可能住在栈上 |
> | `x = 42` 分配吗 | 分配（第一次） | **不分配** |
> | `object o = 42` 分配吗 | 不适用（本来就是对象） | **分配 24 字节** |
> | 有没有"装箱"这个词 | **没有** | **有，而且是性能分析的核心话题** |
> | 优化的方向 | 少建对象、用生成器 | 少装箱、用泛型 |
>
> **一句话**：Python 用"一切皆对象"换来简单、付出性能；C# 用"值类型 / 引用类型二分"换来性能、付出"装箱"这个坑。
> **你从 Python 过来，这个坑一定会踩 —— 本课就是提前把它拆掉。**

## 二、装箱到底发生了什么（看图）

假设有 `int x = 42;`，现在执行 `object o = x;`

**装箱前**：

```
      栈                        托管堆
   ┌──────────┐
   │  x = 42  │              （没有东西）
   └──────────┘
```

**装箱后**：

```
      栈                        托管堆
   ┌──────────┐            ┌──────────────────────┐
   │  x = 42  │            │ Object Header     8B │ ← 同步块索引（lock、哈希缓存）
   ├──────────┤            ├──────────────────────┤
   │  o ──────┼──────────► │ MethodTable 指针  8B │ ← GetType() 读的就是它
   └──────────┘            ├──────────────────────┤
                           │ 数据：42          4B │ ← 值被【复制】进来
                           ├──────────────────────┤
                           │ 填充              4B │ ← 对齐到 8 字节
                           └──────────────────────┘
                                  合计 = 24 字节
```

**三点必须看懂**：

1. **栈上那个 `o` 只有 8 字节** —— 它是一个**引用（地址）**，不是值本身。
2. **堆上那个盒子是一个完整的对象** —— 有对象头，能被 GC 管，会被 GC 回收。
3. **42 被复制了一份** —— 盒子里的是副本。以后改 `x`，盒子里的 42 不会变。

> **和第 18 课对上**：第 18 课算过 `16 + 字段`，再向上对齐到 8 字节。
> `int` 一个字段：`16 + 4 = 20 → 24`。**盒子用的就是这套规则**，
> 因为盒子就是一个最普通的对象。**"24 字节"不是魔法数字，是算出来的。**

**所以装箱 = 一次堆分配 + 一次内存复制 + 一个指向盒子的引用。**

**反过来说，拆箱（unboxing）** = 从盒子里把值**复制**出来（也有一次复制，只是不分配）。

## 三、三项代价

| 代价 | 说明 | 严重程度 |
|---|---|---|
| **① 堆分配** | 至少 24 字节。分配本身快，但它制造垃圾 → 喂给 GC | ★★★ |
| **② 内存复制** | 值被复制进盒子，拆箱时再复制出来。两份内存 | ★ |
| **③ 拆箱类型检查** | 必须**精确匹配**，否则抛 `InvalidCastException` | ★★★（正确性） |

### 代价 ③ 展开讲：拆箱不是类型转换

这是本课**最容易误解**的一点。

```csharp
object boxed = 42;

int  a = (int)boxed;      // ✅ 盒子上写着 Int32，你要 Int32 —— 匹配
long b = (long)boxed;     // ❌ 盒子上写着 Int32，你要 Int64 —— 抛异常！
```

**为什么？** 拆箱**不做任何数值转换**。它只做两件事：

```
① 检查盒子上的类型标记 == 你要的类型吗？
      否 → 立刻抛 InvalidCastException
      是 → ② 把盒子里的内容原样复制出来
```

**没有第三步。** 想真的做数值转换，得用 `Convert.ToInt64(boxed)` ——
那是**另一件事**（它内部会先拆箱、再转换）。

**枚举也有同一个坑**：

```csharp
object o = DayOfWeek.Monday;
int bad = (int)o;                    // ❌ InvalidCastException
int ok  = (int)(DayOfWeek)o;         // ✅ 先拆成 DayOfWeek，再转 int
```

**因为盒子上的标记是 `DayOfWeek`，不是它的底层类型 `int`。**

## 四、会装箱的地方（★ 背下来）

**这六条是"看到就要警觉"的清单**，来自大纲，并且在 `InternalsLab` 菜单 6 里逐条实测过：

```csharp
object o = 42;                        // ① 把值类型赋给 object
IComparable c = 42;                   // ② 把值类型赋给【接口】
new ArrayList().Add(42);              // ③ 非泛型集合（ArrayList / Hashtable）
string.Format("{0}", 42);             // ④ 传给 params object[] 的方法
someStruct.ToString();                // ⑤ struct 未重写 ToString() 时调用它
object[] arr = { 1, 2, 3 };           // ⑥ 值类型放进 object[]
```

**为什么是这六条？** 它们其实是**同一个原因**的六种伪装：

> **只要某个位置的类型是 `object` 或接口，而你把值类型放到那里 —— 就必须装箱。**

- ① 位置的类型是 `object` → 装
- ② 位置的类型是接口 → 装（接口是引用类型，值类型要"变成对象"才能实现它）
- ③ `ArrayList.Add` 的参数签名是 `Add(object value)` → 装
- ④ `string.Format` 的参数签名是 `params object[] args` → 装
- ⑤ `ValueType.ToString()` 是 `object` 上的方法，要在"对象"上调用 → **先把自己装成对象** → 装
- ⑥ `object[]` 的每个元素位置都是 `object` → 装

**⚠️ 第 ⑤ 条特别阴险**，因为它看起来什么特殊写法都没有：

```csharp
struct Player { public string Name; public int Health; }

var p = new Player();
Console.WriteLine(p);            // ❌ 悄悄装箱了！
Console.WriteLine(p.ToString()); // ❌ 也一样装箱

// ✅ 修法：给 struct 重写 ToString / GetHashCode / Equals
struct Player
{
    public string Name;
    public int Health;
    public override string ToString() => $"{Name}({Health})";   // ✅ 重写后不再装箱
}
```

> **`InternalsLab` 菜单 6 的实测对照**（两个 struct 只差"有没有重写"）：
>
> ```
> BadStruct.ToString()    24.0 B/次   ← 就是盒子
> GoodStruct.ToString()    0.0 B/次   ← 重写后零分配
> BadHash.GetHashCode()   48.0 B/次   ← 装箱 24 + ValueType 反射实现 24
> GoodHash.GetHashCode()  24.0 B/次   ← 只剩装箱那一份
> ```
>
> ⚠️ 第 4 行为什么是 24 不是 0？因为那组测量是从 `object` 变量调用的
> （为了跟 `BadHash` 严格对照）。**"重写能免掉装箱"的前提是"直接调用"** ——
> 一旦值类型先被塞进 `object` / 接口，盒子就已经造出来了，重写也救不回来。
>
> **结论：对 struct 来说，重写 `ToString` / `GetHashCode` / `Equals`
> 不是"可选优化"，是"必须做的事"。**

> **测量陷阱（老师踩过的坑，你要避开）**：
> 上面对比 `ToString` 时，**两个 struct 的 `ToString` 都只返回一个字符**。
> 为什么？因为 `ToString` 会**创建字符串**，字符串本身也在分配内存。
> 如果两个版本返回的字符串长度不同，**字符串的差异会盖住装箱的差异**，
> 你就得不出结论了。这叫**严格对照组**：除了你要证明的那一项，其它必须一模一样。
>
> **想直接看到最干净的 24 字节，去测 `GetHashCode`** —— 它返回 `int`，不产生字符串。

## 五、不会装箱的地方（同样要背）

```csharp
var list = new List<int>();
list.Add(42);                  // ✅ 泛型特化，零装箱

string s = $"{42}";            // ✅ 插值已优化，零装箱
```

### 为什么 `List<int>` 不装箱？

因为 C# 的泛型是**具现化（reified）**的（第 15 课）：

- `List<int>` 内部是 `int[]`（不是 `object[]`），**`int` 直接内联在数组里**
- 运行时为 `List<int>` 生成**专门的原生代码**，`Add` 的参数类型就是 `int`
- 所以 `list.Add(42)` 一个盒子都不用

**而 `ArrayList` 内部是 `object[]`**，`Add(object value)` —— 每个 `int` 都要装盒。

**这就是泛型最大的价值：不是"代码复用"，是"性能"。**

### 为什么 `$"{42}"` 不装箱？

`.NET 6` 以后，编译器会把插值字符串改写成**字符串处理器**调用：

```csharp
// 你写的：
string s = $"{42}";

// 编译器实际生成的（简化版）：
var handler = new DefaultInterpolatedStringHandler(0, 1);
handler.AppendFormatted(42);        // ★ 参数类型是 int，不是 object！
string s = handler.ToString();
```

**关键就在参数类型**：`AppendFormatted(int)` 有一个 `int` 重载，
编译器会挑最匹配的那个 —— **根本不需要装箱**。

**对照 `string.Format("{0}", 42)`**：它的签名是 `string.Format(string, params object[])`，
**只有 `object` 一条路可走** → 必然装箱。

> **⚠️ 所以"插值一定比 `string.Format` 快"这个说法要精确表述**：
> 不是因为插值"更聪明"，而是因为**编译器能给插值生成强类型重载的调用**，
> 而 `string.Format` 的 API 形状决定了它只能收 `object`。
> （插值本身仍然会分配结果字符串 —— 那部分跑不掉。）

### ⚠️ 一个反直觉的点：`object[] arr = { 1, 2, 3 };` 装了几个盒？

**三个。** 不是三个元素共用一个盒子，也不是"数组里存 3 个 int"。

`object[]` 是一个**引用数组**，每个格子 8 字节，只能放引用。
所以 `1`、`2`、`3` 各自要装一个盒子 → **72 字节**。

**同理**，同一个值装两次盒，是**两个不同的盒子**：

```csharp
object a = 42;
object b = 42;

Console.WriteLine(a == b);                      // True  ← 比的是【值】
Console.WriteLine(ReferenceEquals(a, b));       // False ← ★ 两个不同的盒子！
```

**为什么 `==` 是 `True`？** 因为 `object` 的 `==` 走的是虚方法 `Equals`，
而 `Int32` 重写了它，比的是值。

**教训**：想判断两个装箱对象是不是同一个盒子，**只能用 `ReferenceEquals`**。

## 六、⭐ 本课最有力的演示：给每一次装箱开一张账单

现在把第二节到第五节的每一句话都变成数字。下面是**示例项目逐条实测**的结果
（Debug，`net9.0`，你的数字会有小幅波动，**看量级和结构**）：

```
---------- 会装箱的写法 ----------
object o = 42;                              24.0 B/次
IComparable c = 42;                         24.0 B/次
ArrayList.Add(42);                          24.0 B/次
string.Format("{0}", 42);                   24.0 B/次
new Tiny().GetHashCode();   ← 未重写        24.0 B/次
objectArray[0] = someStruct;                24.0 B/次

---------- 不装箱的写法（对照）----------
List<int>.Add(42);                           0.0 B/次
new TinyHash().GetHashCode(); ← 已重写       0.0 B/次
TinyComparable.CompareTo（泛型约束）          0.0 B/次
Comparer<TinyComparable>.Default.Compare     0.0 B/次
```

**★ 这张表就是本课的全部内容。** 六条路径全部指向**同一个 24 字节的盒子** ——
不是因为它们"碰巧都分配 24 字节"，而是因为**它们做的是同一件事**。

**注意最后两行的意义**：`TinyComparable` 那个 struct 只做了一件事 ——
实现 `IComparable<TinyComparable>`（泛型接口）而不是 `IComparable`（非泛型接口）。
结果：**0 字节**。

```csharp
// ❌ 非泛型接口：必须装箱
IComparable c = myStruct;
c.CompareTo(other);

// ✅ 泛型约束：编译器知道类型，直接调用，零装箱
static T Max<T>(T a, T b) where T : IComparable<T>
    => a.CompareTo(b) >= 0 ? a : b;
```

> **`InternalsLab` 菜单 13 的实测**（`Max1<T>` 无约束 vs `Max2<T>` 有约束，各 100 万次）：
> `Max1` 分配量远高于 `Max2` —— 因为无约束时 `T` 被当成 `object` 处理。
> **`Comparer<T>.Default` 会优先用 `IComparable<T>`，值类型不必装箱。**
>
> **结论：「加泛型约束」不只是为了类型安全，也是为了性能。**

### 再来一张更大的账单：`List<int>` vs `ArrayList`

`InternalsLab` 菜单 13，各写 500 万个 `int`：

| 集合 | 耗时 | 分配 | Gen0 GC |
|---|---|---|---|
| `ArrayList`（非泛型，装箱） | 慢 | **几百 MB** | **多次** |
| `List<int>`（泛型，零装箱） | 快得多 | 只有那块 `int` 数组 | 少 |

**⚠️ 做这个对照实验有两个必须遵守的条件**，否则你测到的是别的东西：

1. **两边都要预分配容量**：
   ```csharp
   var oldList = new ArrayList(1_000_000);
   var newList = new List<int>(1_000_000);
   ```
   不预分配的话，你测到的主要是**数组翻倍扩容 + 搬运**，不是装箱。
2. **两边都要用泛型/非泛型的唯一差别**做对照 —— 循环次数、循环体、容量必须一模一样。

**满足这两条之后，两者的差就纯粹是盒子。** 这就是**严格对照组**。

## 七、⚠️ 为什么这是 Unity 的生死问题

**先看反面代码。这是 Unity 新手最常见的一段代码：**

```csharp
public class ScoreUI : MonoBehaviour
{
    private int score;

    void Update()                                  // ★ 每帧执行，60 fps
    {
        object boxedScore = score;                 // ❌ 每帧装箱 24 B
        string label = "Score: " + boxedScore;     // ❌ 每帧新建字符串
        myText.text = label;                       // ❌ 每次赋值又可能分配
    }
}
```

**算一下这笔账**（分数每 20 帧才变一次，所以 3600 帧里有 3420 帧是"白算"的）：

```
每帧：24 B（盒子）+ 24 B（字符串）= 48 B
每秒：48 B × 60 帧 = 2,880 B
每分钟：48 B × 3600 帧 = 172,800 B ≈ 169 KB
```

**示例项目实测**（模拟 3600 帧 = 60 秒，分数每 20 帧变一次 → 180 次变化）：

```
❌ 坏写法（每帧装箱 + 每帧拼字符串）
     分配      :   172,800 字节  （168.8 KB）
     每帧平均  :      48.0 字节        ← 盒子 24 + 字符串 24
     Gen0 GC   : 1 次

🔸 半好写法（去掉装箱，但仍然每帧拼字符串）
     分配      :    86,400 字节  （ 84.4 KB）
     每帧平均  :      24.0 字节        ← 只剩字符串那份
     Gen0 GC   : 0 次

✅ 最好写法（值没变就 return + 拼接不经过 object）
     分配      :     4,320 字节  （  4.2 KB）
     每帧平均  :       1.2 字节        ← 只有那 180 次变化在花钱
     Gen0 GC   : 0 次
```

> **⚠️ 注意中间那一档 —— 这是本课最容易被忽略的一课。**
> 很多人以为"不装箱就完事了"，结果**字符串照样每帧分配**，
> 垃圾只少了一半。
> **两条优化是独立的，必须都做**：
> ① 减少**次数**（值没变就别算）② 去掉**装箱**（别经过 `object`）。

**169 KB 听起来不多。但真实项目里有几十个这样的调用** ——
血条、分数、计时器、坐标、状态文字…… **很快就变成每秒几 MB 的垃圾。**

### 为什么在 Unity 里这比在 .NET 里严重 10 倍

| | .NET 9 | Unity |
|---|---|---|
| GC 类型 | 分代 + **压缩** | Boehm：**不分代、不压缩** |
| Gen0 回收成本 | 极低（新生代垃圾几乎不要钱） | **没有分代，全堆一起扫** |
| 堆碎片 | 压缩解决 | **不压缩 → 碎片累积** |
| 表现 | 偶尔一次短暂停顿 | **明显的、周期性的掉帧** |

> **结论（第 26 课会再讲）：在 Unity 里"少分配"比在 .NET 里重要得多。**
> 而且 Unity 的 Profiler 有一个专门的指标叫 **`GC Alloc`**，
> 你的目标是让它显示 **`0 B`**。

### 正确写法

```csharp
public class ScoreUI : MonoBehaviour
{
    private int score;
    private int lastShownScore = int.MinValue;      // ★ 记住上次显示的是什么
    private string labelCache = "";

    void Update()
    {
        if (score == lastShownScore) return;        // ★ 没变就一行都不干
        lastShownScore = score;

        labelCache = "Score: " + score;             // ✅ 不经过 object
        myText.text = labelCache;
    }
}
```

**两条独立的优化，缺一不可**：

| 优化 | 效果 | 为什么 |
|---|---|---|
| ① **只在变化时才重建** | 分配次数从 3600 次降到 180 次 | 大多数帧的值根本没变，白算 |
| ② **拼接时不经过 `object`** | 每次省下 24 B 的盒子 | `"Score: " + score` 走的是 `string.Concat(string, string)` 的 `int` 重载 |

**只做 ② 不做 ①**（每帧都拼，只是不装箱）= 上面表中的"半好写法"：
垃圾从 169 KB 降到 84 KB，**只少了一半**。

**两条都做**，3600 帧才只剩 180 次分配 → **4.2 KB，Gen0 GC 0 次**。

> **这就是"优化报告"该有的写法**：不是"我优化了"，而是
> **"我把每帧 48 B 降到了总计 4.2 KB，GC 次数从 1 降到 0"** ——
> 有对照组、有数字、能复现。

### Unity 里其它几个同源的坑

```csharp
// ① foreach 遍历非泛型集合 → 每次迭代可能装箱（老版本 Mono 的 IEnumerator）
foreach (object item in arrayList) { }        // ❌ 用泛型或 for 循环

// ② 把 struct 传给 Debug.Log
Debug.Log(myStruct);                          // ❌ object 参数 → 装箱
Debug.Log(myStruct.ToString());               // ⚠️ 若未重写 ToString，一样装

// ③ 用 struct 存进 object 字段/字典
Dictionary<string, object> bag;               // ❌ 每个 int/float 都要装盒
Dictionary<string, int> goodBag;              // ✅ 泛型，零装箱
```

## 八、动手：自己把它改坏

**"改坏它"比"看它跑"学得快。** 下面五个实验都在示例项目里，做完你才真懂。

| 实验 | 怎么做 | 你会看到 |
|---|---|---|
| **1. 把"半好写法"改回装箱** | 把 `UpdateGood` 里的 `"Score: " + score` 改成先 `object boxed = score;` 再拼 | 那一段从 24 B/帧 跳到 48 B/帧 —— 盒子的 24 B 回来了 |
| **2. 拆掉"最好写法"的护栏** | 注释掉 `UpdateBest` 里的 `if (score == _lastScore) return;` 和 `_lastScore = score;` | "最好"那段立刻退化成"半好"的 24 B/帧 —— 证明"变化才重建"是独立生效的 |
| **3. 给 struct 加一个没重写的 `ToString`** | 把 `TinyHash.GetHashCode` 注释掉，换成 `ToString` | 数字变得"不好读" —— 因为**字符串的分配混进来了**（测量陷阱） |
| **4. 用 ILSpy 找 `box` 指令** | 打开 `bin\Debug\net9.0\Lesson21Demo.dll`，看 `UpdateBad` | 你会找到 `box [System.Runtime]System.Int32`；`UpdateGood` / `UpdateBest` 里没有 |
| **5. 去掉预热** | 注释掉 `Measure()` 里那段预热循环 | 第一次测量的数字虚高 —— 那是 **JIT 编译**的分配，不是装箱 |

**实验 4 最重要**：

> **分配量是「结果」，`box` 指令是「原因」。**
> 能看到原因，才算真懂 —— 否则你只是记住了几个数字。

**实验 5 是本课的通用教训**：

> **任何性能测量，不预热都是错的。** 第 17 课讲过"JIT 只编译一次"，
> 这里就是它的直接后果：第一次调用包含编译开销，会把你的基准线抬高一截。
> **本课所有数字都建立在"先预热 100 次"这个前提上。**

## 十一、【下一课预告】

**第 22 课 ｜ 字符串的底层真相**

- 字符串**不可变** → 任何"修改"都在创建新对象
- **字符串驻留**：为什么 `ReferenceEquals("abc", "abc")` 是 `True`
- **UTF-16**：为什么 `"𝄞".Length` 是 **2**，而 Python 里是 **1**
- **拼接灾难**：循环 `+=` 是 O(n²)
- 第 13 课实测数据：拼接 20,000 次 `77.5 ms / 1581 MB` vs `StringBuilder` `0.8 ms / 0.35 MB`

> **为什么紧接着讲字符串？**
> 因为字符串是**唯一一个"每次用都在分配"的常用类型** ——
> 它和本课的装箱是同一类问题：**你在不知不觉中制造垃圾。**
> 上一节 `Update()` 那个例子里，`"Score: " + boxed` 一次就踩了两个坑
> （装箱 + 字符串），第 22 课把后半个坑填平。
