## 一、先看全貌：一条四段的流水线

```
   你写的 Program.cs
          │
          │  ① 编译（Roslyn）—— 发生在【你按 Ctrl+F5 的那一刻】
          ▼
   IL 中间语言 + 元数据  ──打包成──►  Lesson17Demo.dll
          │
          │  ② 加载（CLR）—— 发生在【程序启动时】
          ▼
   运行时载入 dll，读元数据，建好类型信息
          │
          │  ③ JIT 编译 —— 发生在【某个方法第一次被调用时】
          ▼
   该方法的原生机器码（存在内存里，不落盘）
          │
          │  ④ 执行
          ▼
        CPU
```

**这张图是本课的全部内容。** 下面逐段拆开。

### Python 对照（第一处关键差异）

| | Python | C# |
|---|---|---|
| 你运行的东西 | `.py` **源码本身** | **编译好的 `.dll`**（源码不参与运行） |
| 中间产物 | `.pyc` 字节码（**只是缓存**，删了照样跑） | IL **是必需的**，没有 dll 就没有程序 |
| 谁翻译成机器码 | **CPython 不翻译** —— 直接解释字节码 | **JIT 翻译成机器码** |
| 类型检查时机 | 运行时（跑到那一行才知道） | **编译时**（大部分错误打字的瞬间就报） |

> **"CPython 不生成机器码"是本课程反复出现的一句话** —— 它是 C# 通常比 Python 快 10-50 倍的第一个原因。

## 二、第①段：编译 —— 源码变成 IL

### 编译发生在什么时候

**不发生在你运行程序的时候，而发生在你"构建"的时候。**

```bash
dotnet build          # 只编译，不运行 → 产出 dll
dotnet run            # 编译 + 运行（所以第一次会慢一点）
```

在 Rider 里按 `Ctrl + F5`，它**先自动 build，再运行**。所以那 0.5 秒里有一大半是在编译。

### IL 是什么

**IL（Intermediate Language，中间语言）**，也叫 **CIL** 或 **MSIL** —— 三个名字指的是同一个东西。

它长这样（`Console.WriteLine("Hello")` 的 IL）：

```il
ldstr      "Hello"                                          // 加载字符串常量
call       void [System.Console]System.Console::WriteLine(string)   // 调用方法
```

**和 Python 字节码的关键差异**：

| | Python 字节码 | C# IL |
|---|---|---|
| 类型 | **动态** —— `LOAD_FAST` 不关心装的是什么 | **静态** —— `call` 指令里写明了参数类型 `string` |
| 能反推出什么 | 只能看出"调了个方法" | 能看出**调用的是哪个类的哪个重载** |

> **`call void [System.Console]System.Console::WriteLine(string)` 这一行里，
> 把类名、方法名、参数类型全写清楚了** —— 这就是"静态类型"在 IL 层面的体现。
> Python 的字节码做不到这一点，因为它在编译时根本不知道 `print` 会收到什么。

### 元数据：Python 完全没有的东西

**元数据（Metadata）** 是跟着 IL 一起打进 dll 的**类型信息表**：

- 这个程序集里有哪些类
- 每个类有哪些字段、属性、方法
- 每个方法的参数是什么类型、返回什么
- 每个类型继承自谁

**谁在读元数据？**

| 场景 | 读元数据做什么 |
|---|---|
| 程序启动 | 建好类型系统，知道 `Console` 是什么 |
| JIT 编译 | 知道 `WriteLine` 要接收 `string`，才能生成正确的机器码 |
| `obj.GetType()` | 读对象头里的 MethodTable 指针（第 18 课细讲） |
| 反射 / 序列化 | 运行时动态发现类型结构（第 16 周的内容） |
| IDE 智能提示 | 读引用的 dll 元数据，才知道有什么方法可以补全 |

> **Python 里没有元数据这个概念** —— 类型信息活在运行时对象里，不落盘。
>
> 这带来一个直接后果：**Python 无法在不导入模块的情况下知道它有什么函数**（所以要 `inspect`、要 import），
> 而 C# 的 IDE 只读 dll 的元数据就能给你完整补全 —— **不执行任何代码**。

## 三、第②段：加载 —— CLR 登场

**CLR（Common Language Runtime）** 是 .NET 的虚拟机，负责：

| 职责 | 说明 |
|---|---|
| 内存管理 | GC（第 19 课） |
| 线程管理 | 线程池、同步原语 |
| 类型加载 | 把 dll 的元数据读进内存 |
| **JIT 编译** | 把 IL 翻译成机器码 |
| 异常处理 | 跨方法的异常传播 |
| 安全检查 | 边界检查等 |

> **Python 对照**：CLR ≈ CPython 解释器。
> 但有个本质区别：**CPython 是解释执行字节码，CLR 是把 IL 编译成机器码再执行。**

### 启动时发生了什么

```
① 操作系统启动 Lesson17Demo.exe
        ↓
② .exe 是个很薄的启动器 —— 它读 Lesson17Demo.runtimeconfig.json，
   知道"这个程序要 .NET 9"，然后找到并加载 dotnet 运行时
        ↓
③ CLR 初始化：建 GC 堆、建线程池、加载核心库（System.Private.CoreLib）
        ↓
④ 找到入口方法（Main），对它做 JIT 编译，然后执行
```

> **⚠️ 一个反直觉的事实**：`Lesson17Demo.exe` 里**没有你的代码**。
> 你的代码全在 `Lesson17Demo.dll` 里。exe 只是个"启动器"。
>
> 证据：**Linux 和 macOS 上根本没有 `.exe` 文件** —— 那边只有 `.dll`，
> 用 `dotnet Lesson17Demo.dll` 启动。同一份 dll 跨平台通用。

## 四、第③段：JIT —— 只编译"要用到的方法"

**JIT（Just-In-Time，即时编译）** 是 CLR 最核心的机制。

### 它的工作方式

```
程序启动
   │
   ├─ 只 JIT 编译 Main，然后开始执行 Main
   │
   ├─ Main 里调用 SlowMethod()
   │     → 发现 SlowMethod 还没编译
   │     → 【此刻】把它的 IL 编译成机器码
   │     → 机器码存在内存里，并把方法的入口地址"打补丁"指向机器码
   │     → 执行
   │
   └─ 第二次调用 SlowMethod()
         → 直接跳到已编译好的机器码，【不再编译】
```

### 为什么是"按需"而不是"一次全编译"

| 方案 | 启动速度 | 运行速度 |
|---|---|---|
| 启动时编译全部 | ❌ **极慢** —— 一个有 5 万个方法的程序要全编译一遍 | 快 |
| **JIT 按需编译（现在）** | ✅ 快 —— 只编译真正用到的 | 首次调用慢，之后快 |
| AOT / ReadyToRun | ✅ 快（编译时已生成机器码） | 快，但失去一些动态能力 |

**这就是你按 `Ctrl + F5` 后程序几乎立刻出来，而不是等半分钟的原因。**

### ⚠️ 这条知识的实用价值：性能测试必须先预热

**本课练习 TODO 2 会让你亲手测量这个现象**：第一次调用比后面平均每次慢**成百上千倍**。

这意味着：

```csharp
// ❌ 错误的测法
var sw = Stopwatch.StartNew();
DoWork();                       // 这次包含了 JIT 编译！
sw.Stop();

// ✅ 正确的测法
DoWork();                       // 预热：让它先被 JIT 编译
DoWork();                       // 再预热一次（有些优化要多次调用才触发）
var sw = Stopwatch.StartNew();
for (int i = 0; i < 1000; i++) { DoWork(); }
sw.Stop();
```

> **"预热"不是玄学，它就是在等 JIT 编译完成。**
>
> 这就是为什么第 09、13、15 课的那些性能对比数字，都必须先预热才有意义。
> 课程里反复出现的"预热"，根子就在这一课。

### 还有更深的层次：分层编译

现代 .NET 的 JIT 其实有**两档**：

| 档位 | 特点 | 什么时候用 |
|---|---|---|
| **Tier 0** | 编译快、优化少 | 方法刚被调用时 |
| **Tier 1** | 编译慢、优化多（内联、寄存器分配等） | 方法被调用很多次后（"热"了）自动升级 |

所以一个方法**可能被 JIT 编译两次**。这也是"预热"要预热够多次数的原因 ——
不只是等第一次编译，还要等它升级到 Tier 1。

## 五、`bin\` 和 `obj\` 里到底有什么

这是本课最实用的一节。**编译一次，然后去看文件夹**。

### `bin\Debug\net9.0\`（最终产物）

| 文件 | 是什么 | 删了会怎样 |
|---|---|---|
| **`Lesson17Demo.dll`** | ★ **主角**。IL + 元数据，你的代码全在这 | 程序跑不起来 |
| `Lesson17Demo.exe` | Windows 启动器，很薄 | 双击启动不了（命令行 `dotnet xxx.dll` 还能跑） |
| `Lesson17Demo.pdb` | 调试符号：IL 行号 ↔ 源码行号的对照表 | 程序照跑，但**断点失准、异常没有行号** |
| `Lesson17Demo.deps.json` | 依赖清单：需要哪些包、什么版本 | 运行时不知道加载什么依赖 |
| `Lesson17Demo.runtimeconfig.json` | 运行时配置：需要哪个版本的 .NET | 找不到运行时 |

### `obj\Debug\net9.0\`（中间产物）

| 文件 | 是什么 |
|---|---|
| `Lesson17Demo.AssemblyInfo.cs` | **你没写过，编译器生成的** —— 里面是版本号、程序集名等 |
| `Lesson17Demo.GlobalUsings.g.cs` | **`<ImplicitUsings>enable</ImplicitUsings>` 的产物** —— 那些自动的 `using` 就是它 |
| `project.assets.json` | NuGet 还原的结果（记录了包的实际路径） |
| `.cache` 类文件 | 增量编译用的缓存 |

> **看到 `GlobalUsings.g.cs` 你就明白了**：课程里你从没写过 `using System;`，
> 但 `Console` 能用 —— 因为编译器**自动生成了一个文件**替你写了那些 using。
>
> **想验证**：把 `.csproj` 里的 `<ImplicitUsings>enable</ImplicitUsings>` 改成 `disable`，
> 重新编译，看 `Console` 是不是立刻报"找不到"。

### `obj\` 能删吗？

**能删。** 下次编译会重新生成，只是会慢一点（要重新 restore）。
所以 `.gitignore` 里同时排除了 `bin/` 和 `obj/`。

> ⚠️ **但报 `MSB3027`（文件被锁）时，删 `obj\` 是错的解法** ——
> 真正原因是程序还在运行。按 `Ctrl + F2` 停掉就好。这一条在第 00 课就讲过。

## 六、解决方案（.sln）在编译流水线里的角色

**`.sln` 本身不产出任何东西**，它只是"项目清单 + 编译顺序"。

```bash
# 这三种编译方式等价：
dotnet build 第17课.sln              # 编译整个解决方案（两个项目）
dotnet build Lesson17Demo\Lesson17Demo.csproj   # 只编译一个项目
cd Lesson17Demo && dotnet build      # 在项目目录里直接编译
```

**为什么本课程坚持"一课一个 .sln"**（第 00 课讲过，这里从编译角度看）：

| 如果所有课堆在一个 `.sln` | 后果 |
|---|---|
| 改第 17 课一行 | 17 课全部重新编译 |
| 第 12 课的 `CS8618` 警告 | 出现在你修第 17 课的警告列表里 |
| 一处语法错 | 整个解决方案编译不过 |

> **"独立解决方案"不是偷懒，是在控制编译单元的大小** —— 这也是真实工程里的做法：
> 大项目会拆成多个 `.csproj`，改一个模块不重编全部。

## 八、常见误解纠正

| 误解 | 真相 |
|---|---|
| "C# 编译成 exe" | ❌ 编译成 **dll**（IL + 元数据）；exe 只是个启动器 |
| "运行的是我的源码" | ❌ 运行的是 **dll**；改源码不重新编译，运行结果不会变 |
| "`obj` 是垃圾，随时该删" | ⚠️ 平时可以删，但**它里面有你没写过的生成文件**，理解它比删它重要 |
| "JIT 编译整个程序" | ❌ **按方法**编译，第一次调用时才编译那个方法 |
| "编译一次就永远是机器码" | ⚠️ 现代 .NET 有**分层编译**，热方法会被重新编译成更优化的版本 |
| "Python 也有字节码，所以一样" | ❌ Python 的 `.pyc` 是**缓存**（删了照跑）；C# 的 IL 是**必需品** |

不看资料回答，答不上就回去重读对应章节：

5. 做性能测试前为什么必须"预热"？从 JIT 的角度解释。
6. JIT 为什么按方法编译，而不是启动时全编译？这样设计的代价是什么？
7. `dotnet build` 和 `dotnet run` 有什么区别？
8. 为什么说「删掉 `bin\` 能解决问题」几乎总是错的建议？（提示：想想 `MSB3027`）

<details>
<summary>参考答案要点</summary>

1. `.dll` = IL + 元数据（**你的代码在这**）；`.exe` = Windows 启动器（很薄）；`.pdb` = 调试符号（行号对照）
2. 编译器自动生成；它把 `ImplicitUsings` 该引入的 using 写成了代码文件
3. ① JIT 生成机器码，CPython 只解释字节码 ② 编译期静态类型检查，省掉大量运行时类型判断 ③ 值类型不装箱、无对象头开销（第 11、21 课）
4. 元数据 = 打进 dll 的类型信息表；JIT/反射/IDE 都靠它。Python 类型信息活在运行时对象里，不落盘
5. 第一次调用含 JIT 编译开销，可能比稳态慢成百上千倍；不预热测到的主要是 JIT 时间
6. 启动快（几万方法全编译会让启动极慢）；代价是首次调用慢
7. `build` 只编译产出 dll；`run` = 编译 + 运行
8. `MSB3027` 的真正原因是**程序还在运行**、文件被锁；删 `bin\` 既没用也可能因句柄占用而失败。正确做法是 `Ctrl + F2` 停掉程序

</details>
