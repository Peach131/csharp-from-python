## 第 17 课 ｜ 编译流水线：从源码到 CPU

**对应实验**：`InternalsLab` 菜单 **1（编译流水线）** 和 **2（JIT 只编译一次）**

### 核心要点

```
Program.cs
    │  ① C# 编译器（Roslyn）
    ▼
IL 中间语言 + 元数据  ──►  打包成 Program.dll（程序集）
    │  ② 运行时加载（CLR）
    ▼
JIT 编译器（只编译被调用的方法）
    ▼
原生机器码  ──►  CPU 执行
```

| 概念 | 说明 | Python 对照 |
|---|---|---|
| **IL**（中间语言） | 类似字节码，但**是静态类型**的 | Python 字节码 |
| **元数据** | 类型信息以二进制表格存在 dll 里 | **Python 没有对应物** |
| **JIT** | 运行时把 IL 编译成机器码 | **CPython 不生成机器码** ← 这是 C# 快的首要原因 |
| **程序集** | `.dll` = IL + 元数据 | `.pyc` 只是缓存 |
| **CLR** | 管内存、线程、类型加载、JIT | CPython 解释器 |

| 菜单 2 | 首次调用 vs 稳态调用的耗时差（JIT 的开销） |

## 第 18 课 ｜ 栈与堆、对象的内存布局

**对应实验**：`InternalsLab` 菜单 **4（对象占多少字节）** 和 **5（栈帧与递归）**

### 核心要点（**第 11 课已经讲过主体，这课做实验验证**）

| | 栈 | 托管堆 |
|---|---|---|
| 存什么 | 局部变量、参数、返回地址 | 对象本体 |
| 谁管理 | 编译器 + CPU 栈指针 | GC |
| 速度 | 极快（移动栈指针） | 快（移动分配指针） |
| 容量 | 小（默认 1MB/线程） | 大 |
| 碎片 | 不会 | **会** |

**对象布局（x64）**：

```
┌────────────────────────────┐
│ Object Header (8 字节)      │ ← 同步块索引（lock、GetHashCode 缓存）
├────────────────────────────┤
│ MethodTable 指针 (8 字节)   │ ← GetType() 读的就是它
├────────────────────────────┤
│ 字段（按 8 字节对齐）        │
└────────────────────────────┘
```

**大小规律**：`16 + 字段`，再向上对齐到 8 字节。

```
Empty    : 16 + 0  = 16 → 24（最小值）
OneInt   : 16 + 4  = 20 → 24   ← int 是"免费"的
TwoInt   : 16 + 8  = 24 → 24
ThreeInt : 16 + 12 = 28 → 32
```

## 第 19 课 ｜ 垃圾回收（GC）

**对应实验**：`InternalsLab` 菜单 **8（WeakReference）** 和 **9（对象晋升与 GC 计数）**

### 核心要点

**GC 用"可达性分析"**：从**根**（栈变量、静态字段、CPU 寄存器、GC Handle）出发遍历，
找不到的对象就是垃圾。

```
标记（Mark）→ 清除（Sweep）→ 压缩（Compact）
```

| 概念 | 说明 |
|---|---|
| **分代** | Gen0（新对象，频繁查）→ Gen1 → Gen2（长期存活，少查） |
| **分代假设** | "绝大多数对象活不过第一次 GC" |
| **LOH** | > 85000 字节的对象直接进大对象堆（属 Gen2，**默认不压缩**） |
| **托管堆分配快** | 只是移动分配指针（≈1 条 CPU 指令） |

**对比 Python**：Python 用**引用计数 + 循环检测**（对象不可达时通常立即释放）；
C# 用**追踪式分代 GC**（释放时机不确定，但天然处理循环引用）。

### 必做实验

| 实验 | 看什么 |
|---|---|
| 菜单 8 | 用 `WeakReference` **证明对象真的被回收了**；循环引用也能被回收 |
| 菜单 9 | 对象晋升（Gen0→1→2）；LOH 阈值；`ArrayPool` 复用大数组 |

### 关键 API

```csharp
GC.GetAllocatedBytesForCurrentThread()   // 当前线程累计分配（测"产生多少垃圾"）
GC.GetTotalMemory(true)                  // 强制 GC 后的存活堆大小
GC.CollectionCount(0)                    // Gen0 回收次数
GC.GetGCMemoryInfo()                     // 堆大小、碎片、提交内存
GC.KeepAlive(obj)                        // 防止对象被提前回收
```

### ⚠️ 唯一允许 `GC.Collect()` 的场合：测试和诊断

**生产代码永远不要调用它。**

### 自测

2. 为什么托管堆分配很快？
3. 分代假设是什么？它带来什么优化？
4. 什么是 LOH？它有什么问题？

## 第 20 课 ｜ 终结器与 IDisposable

**对应实验**：`InternalsLab` 菜单 **8** 的延展（建议自己写新实验）

### 核心要点

**GC 只管"托管内存"，不管"非托管资源"**（文件句柄、网络连接、数据库连接、原生内存）。

| | 终结器 `~ClassName()` | `IDisposable.Dispose()` |
|---|---|---|
| 谁调用 | **GC**（时机不确定） | **你**（确定时机） |
| 触发 | 对象被回收时 | 显式调用 / `using` 结束 |
| 开销 | **会让对象多活一轮 GC** | 无 |
| 用途 | 最后防线 | **主要手段** |

### 标准 Dispose 模式

```csharp
public class ResourceHolder : IDisposable
{
    private bool _disposed;
    private readonly IntPtr _native = Marshal.AllocHGlobal(1024);
    private readonly Stream _file = File.OpenRead("data.txt");

    ~ResourceHolder() => Dispose(false);          // 只有直接持有非托管资源才需要

    public void Dispose()
    {
        Dispose(true);
        GC.SuppressFinalize(this);                 // ★ 主动释放过了，不用再走终结器
    }

    protected virtual void Dispose(bool disposing)
    {
        if (_disposed) return;
        if (disposing) _file?.Dispose();           // 终结器线程上不能碰托管对象
        Marshal.FreeHGlobal(_native);
        _disposed = true;
    }
}
```

**`using` 的两种写法**：

```csharp
using (var f = File.OpenRead("a.txt")) { }     // 作用域
using var f2 = File.OpenRead("a.txt");          // 声明式（C# 8+，推荐）
```

> **`using` ≈ Python 的 `with`。**

### 自测

1. 为什么光有 GC 不够，还需要 `IDisposable`？
2. 有终结器的对象为什么需要**两轮 GC** 才能被回收？
3. `GC.SuppressFinalize(this)` 是干什么的？
4. `Dispose(bool disposing)` 里的 `disposing` 参数有什么用？
5. `using` 和 Python 的 `with` 有什么对应关系？

## 第 21 课 ｜ 装箱与拆箱

**对应实验**：`InternalsLab` 菜单 **6（装箱与拆箱）** 和 **13（泛型 vs ArrayList）**

### 核心要点

**装箱 = 把值类型复制到堆上的一个盒子里。**

```
装箱前：栈 [42]          装箱后：栈 [地址] ──┐
                                        ▼
                                堆 [Header][MT:Int32][42]
```

### 代价

| 成本 | 说明 |
|---|---|
| **堆分配** | 至少 24 字节 |
| 内存复制 | 值被复制进盒子 |
| 拆箱类型检查 | 必须**精确匹配**，否则抛 `InvalidCastException` |

### 会装箱的地方（背下来）

```csharp
object o = 42;                      // 赋给 object
IComparable c = 42;                 // 赋给接口
var al = new ArrayList(); al.Add(42);   // 非泛型集合
string.Format("{0}", 42);           // string.Format 传值类型
struct 未重写 ToString() 时调用它
object[] arr = { 1, 2, 3 };         // 值类型放进 object[]
```

### 不会装箱

```csharp
var list = new List<int>(); list.Add(42);   // ✅ 泛型特化
string s = $"{42}";                          // ✅ 插值已优化
```

### ⚠️ 为什么这对 Unity 是生死问题

```csharp
void Update()                       // 每帧执行，60fps
{
    object o = score;               // ❌ 每帧装箱
    Debug.Log("Score: " + score);   // ❌ 每帧字符串拼接
}
// 每秒 60 次分配 → 几分钟后 GC 卡顿
```

### 自测

1. 什么是装箱？代价是什么？
2. 列出 5 个会触发装箱的写法。
3. 为什么 `List<int>` 不装箱？
4. `(long)(object)42` 会怎样？为什么？
5. 为什么说装箱是 Unity 的性能杀手？

## 第 24 课 ｜ async / await 状态机

**对应实验**：`InternalsLab` 菜单 **14（await 之后线程会变吗）**

### 核心要点

> **`await` 不是"暂停线程"，而是"把方法拆成多段并返回"。**

```
1. 遇到未完成的任务 → 方法【直接 return】（返回未完成的 Task）
2. 调用方线程被释放
3. 任务完成后，由线程池线程（或 SynchronizationContext）
   再次调用状态机的 MoveNext() 继续执行
4. 所以 → 【await 之后可能在不同的线程上】！
```

### 与 Python asyncio 的本质差异

| | C# async/await | Python asyncio |
|---|---|---|
| 模型 | 状态机 + 线程池（**真并行**） | 事件循环（**单线程并发**） |
| await 后线程 | **可能变化** | **永远是同一个** |
| 阻塞调用的后果 | 只阻塞当前线程池线程 | **卡死整个事件循环** |

### 铁律

1. **绝不**用 `.Result` / `.Wait()`（UI 程序会死锁）
2. **绝不**写 `async void`（除事件处理器）—— 异常无法捕获
3. 库代码用 `.ConfigureAwait(false)`；UI 代码**不加**
4. `await` 之后要更新 UI，靠的是 `SynchronizationContext`

### 必做实验

菜单 14：观察 `await` 前后的线程 ID 变化；`Task.WhenAll` 并发 vs 顺序 await 的耗时差。

### 自测

1. `await` 时线程发生了什么？
2. 为什么 UI 程序里用 `.Result` 会死锁？
3. 为什么 `async void` 危险？
4. C# 的 async 和 Python 的 asyncio 有什么本质区别？

## 第 25 课 ｜ 集合的内部实现

**对应实验**：`InternalsLab` 菜单 **13**，以及第 09 课的性能实测

### 核心要点

| 集合 | 底层结构 | 查找 | 插入 | 删除 |
|---|---|---|---|---|
| `T[]` | 连续内存 | O(n) | ❌ | ❌ |
| `List<T>` | 动态数组（翻倍扩容） | O(n) | O(n) | O(n) |
| `Dictionary<K,V>` | 哈希表 | **O(1)** | O(1) | O(1) |
| `HashSet<T>` | 哈希表 | **O(1)** | O(1) | O(1) |
| `SortedDictionary` | 红黑树 | O(log n) | O(log n) | O(log n) |
| `LinkedList<T>` | 双向链表 | O(n) | O(1) | O(1) |

**第 09 课实测**：10 万元素里查找，`List` 比 `Dictionary` 慢 **711 倍**。

### 手写练习（建议做）

1. **手写一个 `MyList<T>`**：带 `Add` / 索引器 / 自动扩容。理解 `Capacity` vs `Count`。
2. **手写一个简易哈希表**：理解"哈希 → 桶 → 冲突链"。
3. **复杂度实测**：对比 List 查找 vs Dictionary 查找（10 万元素）。

### ⚠️ 哈希的契约

**如果 `a.Equals(b)` 为 true，那么 `a.GetHashCode()` 必须相等。**
违反它 → `Dictionary` 找不到已存在的键（第 05 课实验 7 验证过）。

## 第 26 课 ｜ 落地 Unity：从底层知识到流畅游戏

**对应实验**：需新建（Unity 项目）

### Unity 的运行时和 .NET 不一样

| 后端 | 说明 | 什么时候用 |
|---|---|---|
| **Mono** | 运行 JIT，支持大部分 C# 特性 | 开发期（Editor 里） |
| **IL2CPP** | IL → C++ → 原生代码 | 发布版，性能更好，但反射受限 |

**Unity 的 GC 是 Boehm GC**（非分代、非压缩），比 .NET Core 的 GC **弱得多**：
- 堆碎片化严重
- **不能移动对象**（无压缩）
- GC 停顿更明显

> **结论：在 Unity 里"少分配"比在 .NET 里重要 10 倍。**

### Unity 性能优化清单（全部来自前面课程）

| 问题 | 底层原因 | 解法 | 对应课 |
|---|---|---|---|
| 每帧卡顿 | `Update` 里 new 对象 → GC | 缓存对象、对象池 | 19 |
| `foreach` 有分配 | 老版本 Mono 的 `IEnumerator` 装箱 | 用 `for` 遍历数组 | 21 |
| 字符串拼接卡顿 | 不可变 + 每次分配 | 缓存 `ToString()`、`StringBuilder` | 22 |
| `GetComponent<T>()` 慢 | 内部查找 | `Awake()` 里取一次存字段 | — |
| `Camera.main` 慢 | 每次查找场景对象 | 缓存到字段 | — |
| Lambda 分配 | 闭包生成类 | 提取成静态方法/字段 | 23 |
| struct 反而变慢 | 装箱 | 用泛型容器 | 21 |

### 最终项目：第一个 Unity 小游戏

**要求**：
- 完整游戏循环（开始 → 游玩 → 死亡 → 重开）
- **用 Profiler 优化到每帧 `GC Alloc = 0 B`**
- 写一份优化报告：优化前后对比 + 每个优化点对应的底层原因

**这份报告就是你学习成果的最好证明。**

### 自测

1. Unity 用的 GC 和 .NET 有什么不同？为什么"少分配"更重要？
2. `Mono` 和 `IL2CPP` 有什么区别？
