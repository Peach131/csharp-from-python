> **本课目标**：搞清楚 GC 的边界在哪，学会用 `IDisposable` + `using` 确定性地归还资源，
> 并且知道终结器（finalizer）为什么只是"最后防线"而不是主力。

> `using` 两种写法、`GC.SuppressFinalize`、`Marshal.AllocHGlobal` / `FreeHGlobal`、`WeakReference`

## 一、先记住一句话

> **GC 负责【内存】，不负责【资源】。**

上一课你看到 GC 怎么把托管堆打理得井井有条。但托管堆里躺着的只是**对象**；
对象**手里可能攥着一些堆外的东西**：

| 非托管资源 | 谁持有它 | 不还的后果 |
|---|---|---|
| 文件句柄 | `FileStream` / `File` | 别人打不开文件；句柄耗尽后程序崩溃 |
| 网络连接 | `Socket` / `TcpClient` / `HttpClient` | 连接数涨到上限，新请求全失败 |
| 数据库连接 | `SqlConnection`（连接池） | **池子枯竭**，整个服务卡死 |
| 原生内存 | `Marshal.AllocHGlobal`、C 库 `malloc` | 进程内存一直涨，托管堆却显示很小 |
| GDI / 窗口句柄 | 画刷、字体、位图 | 界面资源泄漏，最终无法绘图 |

**GC 只看得到"托管堆里那个包装对象"，看不到它手里握着的那份外部资源。**

所以：

```
包装对象被回收  ≠  外部资源被归还
```

**你在 Python 里其实早就习惯了这件事**：

```python
f = open("a.txt", "w")
f.write("hi")
# 忘记 f.close()：文件句柄就一直开着
```

Python 也有 `with` 来解决它。C# 的答案就是本课的主角：`IDisposable` + `using`。

## 二、两个角色登场：终结器 vs Dispose

C# 提供了**两套**机制来归还资源，但它们的分工完全不同。

### 终结器（finalizer）

```csharp
class Foo
{
    ~Foo()          // ★ 类名前面加 ~，无参数、无返回值、不能手动调用
    {
        // 释放非托管资源
    }
}
```

**它由 GC 调用。** 对象被判定为垃圾时，运行时先执行终结器，然后才回收内存。

### IDisposable.Dispose()

```csharp
class Foo : IDisposable
{
    public void Dispose()
    {
        // 释放资源
    }
}
```

**它由你调用。** 或者由 `using` 替你调用。

### 对比表（背下来）

| | 终结器 `~ClassName()` | `IDisposable.Dispose()` |
|---|---|---|
| **谁调用** | **GC**（运行时） | **你**（或 `using` 自动调） |
| **触发时机** | 对象被回收时，**不确定** | 你写的那一行，**确定** |
| **执行线程** | 专用终结器线程 | 调用它的那个线程 |
| **能否碰托管对象** | **★ 不能** | 可以 |
| **开销** | **会让对象多活一轮 GC** | 基本没有 |
| **能否保证执行** | **不保证**（进程被杀就没了） | 只要 `using` 就一定执行 |
| **定位** | 最后防线（保险） | **★ 主要手段** |

> **一句话记忆**：`Dispose` 是正门，终结器是"从窗户爬进来救火"。

## 三、终结器的时机到底有多不确定？

不亲眼看见是不会信的。**实验 1**（`Lesson20Demo` 实验 2）：

```csharp
var d = new DemoOrder("d");   // 创建，故意不 Dispose
d = null;                     // 去掉最后一个引用

// 此时 d 已经没有任何人引用了，但终结器【不会】现在就跑
Console.WriteLine("我还活着，d 的终结器还没跑");

GC.Collect();                 // 强制回收（★ 测试专用，生产代码不许写）
GC.WaitForPendingFinalizers(); // 等终结器队列排空
GC.Collect();
```

你会看到：**"★终结器 : d" 出现在你强制回收的那一刻，而不是 `d = null` 的那一刻。**

而在真实程序里，**没有 `GC.Collect()` 这一行**。那么终结器什么时候跑？

- 内存压力大的时候，可能几毫秒后
- 内存宽裕的时候，可能几秒后
- **也可能一直不跑，直到进程结束**（此时"释放"已经毫无意义）

> ⚠️ **Python 对照**：CPython 的引用计数让"对象死亡"和"资源释放"几乎同时发生，
> 所以 Python 程序员很容易养成"反正会自动关"的坏习惯。
> **C# / .NET 里没有这个保证**：`GC.Collect` 不在你的控制范围内，分代 GC 更是把时机拉得很长。

### 还有两个"不确定"

1. **顺序不确定**：两个对象谁先终结，规范没有保证。**不要写依赖终结顺序的代码。**
2. **线程不确定**：终结器在专用线程上跑。**不要用普通字段的"可见性"思路去和它打交道。**

### 终结器里绝对不能做的事

| 禁止 | 原因 |
|---|---|
| 访问别的托管对象 | 那个对象可能已经被回收了 |
| 抛异常 | **终结器线程上的异常无法 catch，直接杀进程** |
| 长时间阻塞 | 所有终结器排在一个队列里，你卡住，别人的资源也还不掉 |
| 做业务逻辑（发通知、写日志、调 API） | 时机不可控，行为不可预测 |

**规矩**：终结器里只做一件事 —— **释放你自己直接持有的非托管资源**，然后立刻返回。

## 四、终结器的代价：对象要多活一轮 GC

这是本课最重要的结论。原因在上一课讲过：**如果对象有终结器，运行时就不能在它终结之前回收它的内存。**

于是流程变成：

```
第 1 轮 GC：对象变成垃圾 → 被放进"待终结"队列 → ★内存【不回收】，对象被挪到更老的一代
            （终结器线程执行 ~Foo()）
第 2 轮 GC：终结器已经跑完 → 这一次才真正回收内存
```

**实验 2**（`Lesson20Demo` 实验 3）。用 `WeakReference`（弱引用）把它钉死：

```csharp
var probe = new NativeBuffer(32);
var weak = new WeakReference(probe);
probe = null;                      // 去掉最后一个强引用

GC.Collect(); GC.WaitForPendingFinalizers();
Console.WriteLine(weak.IsAlive);   // ★ True —— 终结器跑完了，内存还在！

GC.Collect(); GC.WaitForPendingFinalizers();
Console.WriteLine(weak.IsAlive);   // ★ False —— 现在才真的回收
```

`WeakReference` 的关键性质：**它不阻止对象被回收**；对象被回收后 `IsAlive` 变成 `false`。
所以 `IsAlive` 从 `true` 变 `false` 的那一步，就是"内存真的被收走"的那一刻。

**自己动手复现**（示例代码里就有）：把 `GC.GetGeneration(buffer)` 在 GC 前后各打一次，
你会看到带终结器的对象被"提拔"到了第 1 代。

### 这意味着什么

| 影响 | 说明 |
|---|---|
| **回收延迟** | 你的对象占用内存的时间至少翻倍 |
| **代际晋升** | 它被推进老一代，而老一代 GC 更贵、更少做 |
| **终结器线程排队** | 终结器一多，队列变长，资源归还进一步延后 |
| **压测数据更难看** | 大量临时对象 + 终结器 = GC 时间明显上升（示例里能跑出倍数） |

> **所以**：能 `Dispose` 就不要指望终结器。终结器只在"用户忘了 Dispose"时兜底。

## 五、标准 Dispose 模式（逐行讲透）

这是本课要背下来的代码。**大纲给的就是它**，下面每一行都有存在理由：

```csharp
public class NativeBuffer : IDisposable
{
    private bool _disposed;                                        // ①
    private IntPtr _native = Marshal.AllocHGlobal(1024);           // ②
    private readonly MemoryStream _stream = new();                 // ③

    ~NativeBuffer() => Dispose(false);                             // ④

    public void Dispose()                                          // ⑤
    {
        Dispose(true);
        GC.SuppressFinalize(this);                                 // ⑥
    }

    protected virtual void Dispose(bool disposing)                 // ⑦
    {
        if (_disposed) return;                                     // ⑧
        if (disposing)
        {
            _stream.Dispose();                                     // ⑨
        }
        if (_native != IntPtr.Zero)
        {
            Marshal.FreeHGlobal(_native);                          // ⑩
            _native = IntPtr.Zero;
        }
        _disposed = true;                                          // ⑪
    }
}
```

| # | 这一行 | 作用 |
|---|---|---|
| ① | `bool _disposed` | **幂等**：`Dispose` 可能被调用多次（你一次 + `using` 一次），重复释放非托管资源是**未定义行为**，可能直接崩溃 |
| ② | `IntPtr _native` | 一块**非托管**内存的地址。它就是个整数，GC 看不见、也不会替你释放 |
| ③ | `MemoryStream _stream` | 一个**托管**对象。它的存在是为了演示 ⑨ 的分支 |
| ④ | `~NativeBuffer() => Dispose(false)` | 终结器：最后防线。注意传的是 **`false`** |
| ⑤ | `public void Dispose()` | 用户主动释放的入口。**两行的顺序不能反** |
| ⑥ | `GC.SuppressFinalize(this)` | ★ **我处理过了，别再把对象放进终结队列**。省掉"多活一轮 GC"的代价 |
| ⑦ | `protected virtual void Dispose(bool)` | 一个实现，**两个入口**（用户 / 终结器）。`virtual` 是给派生类扩展用的 |
| ⑧ | `if (_disposed) return;` | 重复调用直接返回 —— 幂等性的落点 |
| ⑨ | `_stream.Dispose()` | **只有 `disposing == true` 才碰托管对象** |
| ⑩ | `Marshal.FreeHGlobal(_native)` | 非托管资源，**两个入口都必须放** |
| ⑪ | `_disposed = true;` | 打标记 |

### `disposing` 参数到底在防什么？

| 参数值 | 谁在调用 | 能做什么 |
|---|---|---|
| `true` | 用户：`Dispose()` / `using` | 托管对象 + 非托管资源**都能放** |
| `false` | **终结器线程** | **只能放非托管资源** |

为什么 `false` 时不能碰托管对象？两个理由，都很硬：

1. **那个托管对象可能已经被回收了。** 终结器运行时，它引用的对象没有任何"存活保证" ——
   你访问到的可能是一块已经被别人复用的内存。
2. **终结器线程上碰托管对象可能触发新的终结/异常**，而这里的异常**无法 catch，直接杀进程**。

> **记忆**：`disposing == false` 时，你只当"这个类里除了 `IntPtr` 之外什么都不存在"。

### 派生类怎么办？

```csharp
class NativeBufferChild : NativeBuffer
{
    private readonly MemoryStream _extra = new();

    protected override void Dispose(bool disposing)
    {
        if (disposing) _extra.Dispose();   // 先放自己新增的
        base.Dispose(disposing);           // ★ 再放基类的（顺序和构造相反）
    }
}
```

- 派生类**不要**再写终结器（基类那个已经够了，它会一路调到你的重写版本）
- **不要**在派生类里重新实现 `IDisposable`（会形成两个 `Dispose`，调用方混乱）

### 到底什么时候才需要终结器？

> **只有【直接】持有非托管资源的类型才需要终结器。**

| 情况 | 需要终结器吗 |
|---|---|
| 字段是 `IntPtr`（`AllocHGlobal` 来的） | ✅ 需要 |
| 字段是 `SafeHandle` 派生类 | ❌ 不需要（`SafeHandle` 自己处理了） |
| 字段是 `FileStream` / `Socket` / `SqlConnection` | ❌ 不需要（它们自己有终结器） |
| 只是持有别的 `IDisposable` 的包装类 | ❌ 不需要，但**必须在 `Dispose` 里把它们放掉** |

**第四条最容易忘**：包装类可以没有终结器，但**不能没有 `Dispose`**，否则你包装的那个资源永远不会被及时释放。

## 六、`using`：一行代码不写，也能保证释放

### 两种写法

```csharp
// 写法一：作用域形式（老写法，仍然常见）
using (var f = new StreamWriter("a.txt"))
{
    f.WriteLine("hi");
}   // ← 右花括号 = 释放点

// 写法二：声明式（C# 8+，★ 推荐）
using var f2 = new StreamWriter("b.txt");
f2.WriteLine("hi");
// ← 释放点 = 这个变量所在的【作用域】结束
```

两种写法**语义完全一样**，都等价于：

```csharp
var f = new StreamWriter("a.txt");
try
{
    f.WriteLine("hi");
}
finally
{
    f?.Dispose();     // ★ 编译器帮你写的就是这一行
}
```

**所以：**

- 不管 `try` 里怎么退出（正常、`return`、`throw`），`Dispose` **一定**会被执行
- 多个资源时，释放顺序是**后进先出**（像叠盘子）
- 变量类型必须实现 `IDisposable`（否则编译错误）

### `using` ≈ Python 的 `with`

| Python | C# |
|---|---|
| `with open("a.txt") as f:` | `using var f = File.OpenRead("a.txt");` |
| `__enter__` | （没有对应物） |
| `__exit__` | `Dispose()` |
| `__del__` | `~ClassName()` 终结器 |
| `try/finally` 手动清理 | 一样，但 C# 有 `using` 更省事 |
| `contextlib.contextmanager` | 自己写个 `IDisposable` 类 |
| `async with` / `__aexit__` | `await using` / `IAsyncDisposable` |
| 引用计数（CPython 立即释放） | GC（分代、非确定） |
| `gc` 模块的两阶段回收 | 无（不需要：C# GC 本来就处理循环引用） |

> **语法形态上最像的**：
> ```python
> with open("a.txt") as f:      # Python
> ```
> ```csharp
> using var f = File.OpenRead("a.txt");   // C#
> ```
> 都是"进入作用域 → 拿资源 → 离开作用域 → 自动还"。

**`using` 比 `with` 少的那部分**：Python 的 `__exit__` 可以吞掉异常（返回 `True`）；
C# 的 `Dispose` 不参与异常处理 —— 它只是 `finally`。**这是好事**：职责更单一。

## 七、忘记 Dispose 会发生什么（实验 6）

`Lesson20Demo` 的第 6 个实验跑出来的三件事：

### 1. 别人拿不到（句柄没还）

```csharp
var kept = new DemoFileWriter(leakPath);   // FileShare.None 独占打开
kept.WriteLine("这行数据在缓冲区里");
// 不 Dispose

new FileStream(leakPath, FileMode.Open, ...);   // ★ IOException：文件被占用
```

### 2. 数据丢了（托管缓冲区救不回来）

`FileStream` / `StreamWriter` 默认带 **1KB~4KB 缓冲区**。你不 `Dispose`：

- 数据一直躺在**内存**里，没写到文件
- `FileStream` 的终结器**只关句柄，不会替你 `Flush`**
- 结果：文件长度 **0 字节**，而且**没有任何异常** —— 最安静的 bug

**示例输出对照**（`Lesson20Demo` 实验 6；具体字节数随平台换行符不同，Windows 上每行多一个 `\r`）：

```
用 using 的  : 文件长度 = 12 字节     ← 正常落盘
不 Dispose 的: 文件长度 = 0 字节      ← 数据没了
```

### 3. 池子枯竭（最致命的一种）

数据库连接池 / 线程池 / 对象池的逻辑都一样：

```
借出 → 归还 → 借出 → 归还
```

只要有一处忘记归还，池子里的可用资源就**永久少一个**。请求一多，池子见底，
整个服务卡死 —— **而且 GC 不会及时救你**（终结器可能几秒甚至几分钟后才跑，甚至不跑）。

> **经验**：**"内存泄漏"通常只是慢，"资源泄漏"会直接让服务挂掉。**
> 因为内存有 GC 兜底，资源没有。

## 八、本课新 API 速查表

| API | 作用 | 备注 |
|---|---|---|
| `IDisposable` | 只有 `void Dispose()` 一个方法 | 想被 `using` 就必须实现它 |
| `~ClassName()` | 终结器 | 只有直接持有非托管资源才写 |
| `GC.SuppressFinalize(obj)` | 把对象从终结队列摘掉 | 主动 Dispose 后必写 |
| `GC.Collect()` | 强制回收 | **只在测试/诊断里用** |
| `GC.WaitForPendingFinalizers()` | 等终结器队列排空 | 配合 `GC.Collect()` 做实验 |
| `GC.GetGeneration(obj)` | 对象在第几代 | 观察"多活一轮"的工具 |
| `WeakReference` | 弱引用，不阻止回收 | `IsAlive` 判断对象是否还在 |
| `Marshal.AllocHGlobal(n)` | 分配非托管内存 | **不需要 unsafe** |
| `Marshal.FreeHGlobal(p)` | 释放非托管内存 | 忘了就永久泄漏 |
| `ObjectDisposedException.ThrowIf(cond, obj)` | 已释放后使用就抛异常 | .NET 7+，一行搞定 |
| `IAsyncDisposable` / `await using` | 异步清理 | C# 8+，本课只看一眼 |
