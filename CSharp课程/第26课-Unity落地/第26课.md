## 一、Unity 的运行时和 .NET 不一样（这是最重要的一节）

你在第 17 课学的"源码 → IL → JIT → 机器码"，在 Unity 里**只对了一半**。

### 两种后端

| 后端 | 怎么执行 | 什么时候用 | 代价 |
|---|---|---|---|
| **Mono** | 运行 JIT，和 .NET 类似 | **开发期**（Editor 里、调试构建） | 性能一般 |
| **IL2CPP** | IL → **C++ 源码** → 编译成原生代码 | **发布版**（尤其 iOS 强制） | 编译慢、**反射受限** |

**IL2CPP 的工作方式**（和你学的 IL 知识直接相关）：

```
你的 C# 源码
    │ ① Roslyn 编译
    ▼
IL + 元数据（就是第 17 课那个 .dll）
    │ ② IL2CPP 把 IL 翻译成 C++ 源码     ← ★ 多了这一步！
    ▼
C++ 源码（.cpp 文件）
    │ ③ 用 C++ 编译器编译
    ▼
原生机器码（每个平台各编译一次）
```

**关键差异**：

| | .NET（第 17 课学的） | Unity IL2CPP |
|---|---|---|
| 什么时候翻译成机器码 | **运行时**（JIT，按方法） | **打包时**（提前全部翻译） |
| 能不能用反射 | ✅ 完全支持 | ⚠️ **受限**（代码可能被裁掉，要用 `link.xml` 保护） |
| 启动速度 | 慢（要 JIT） | 快（已经是原生码） |
| 调试 | 容易 | 难（是 C++ 了） |

> **第 17 课的 JIT 知识在这里的用处**：理解"为什么开发期和发布版性能不同"。
> Editor 里跑 Mono + JIT，打包后跑 IL2CPP，**同一份代码性能可能差不少**。
> 所以：**别用 Editor 里的性能当最终结论。**

### Unity 的 GC 比 .NET 弱得多

| | .NET Core（你一直在用的） | **Unity（Boehm GC）** |
|---|---|---|
| 分代 | ✅ Gen0/Gen1/Gen2 | ❌ **不分代**（每次都是全堆扫描） |
| 压缩 | ✅ 会移动对象、消除碎片 | ❌ **不移动对象**（不能压缩） |
| 碎片 | 会被压缩掉 | ⚠️ **只增不减** |
| 停顿 | 可预测、可配置 | **随堆增长越来越长** |
| 增量回收 | ✅ 支持 | 老版本不支持 |

**"不压缩"意味着什么**（用第 19 课的知识推导）：

```
第 19 课：.NET 的 GC = 标记 → 清除 → 【压缩】
         压缩会把存活对象挪到一起，碎片就没了

Unity：  标记 → 清除 → 【不压缩】
         对象留在原地 → 内存出现"空洞" → 堆越来越大
         → 下次扫描更慢 → 停顿更长 → 卡顿更明显
```

> **结论（本课最重要的一句话）**：
> **在 Unity 里"少分配"比在 .NET 里重要 10 倍。**
>
> - .NET 里：多分配一点，GC 帮你收拾干净，代价是偶尔一次停顿
> - Unity 里：多分配一点，**碎片永久留下**，堆越来越大，停顿越来越长
>
> **所以 Unity 优化的第一原则不是"让代码更快"，而是"让代码不分配"。**

## 二、总清单：7 个常见问题 → 底层原因 → 解法 → 对应课

**这张表是本课的核心。** 每一条你都要能在自己的项目里找到实例。

| # | 现象 | 底层原因 | 解法 | 哪一课讲的 |
|---|---|---|---|---|
| 1 | 每帧卡顿 | `Update` 里 `new` 对象 → 累积垃圾 → GC 停顿 | 缓存对象、**对象池** | **19**（GC）、**20**（Dispose） |
| 2 | `foreach` 有分配 | 老版本 Mono 的 `IEnumerator` 是**装箱的接口** | 遍历数组用 `for`；集合用 `List<T>` | **21**（装箱） |
| 3 | 字符串拼接卡顿 | 不可变 → 每次拼接都分配新字符串 | 缓存 `ToString()`、用 `StringBuilder` | **22**（字符串） |
| 4 | `GetComponent<T>()` 慢 | 内部要做类型查找 | **`Awake()` 里取一次存字段** | — |
| 5 | `Camera.main` 慢 | 每次调用都去场景里**找**带标签的对象 | 缓存到字段 | — |
| 6 | Lambda 分配 | 闭包 → 编译器生成 `<>c__DisplayClass` | 提取成**静态方法**或字段缓存 | **23**（闭包） |
| 7 | `struct` 反而变慢 | **装箱**（塞进 `object`/非泛型容器） | 用泛型容器、避免赋给 `object` | **21**（装箱） |

**再加三条来自第 19、25 课的**：

| # | 现象 | 底层原因 | 解法 | 哪一课 |
|---|---|---|---|---|
| 8 | 加载时卡一下 | 大数组（> 85000 字节）进 **LOH**，且不压缩 | 分块、用 `ArrayPool` 复用 | **19**（LOH） |
| 9 | 遍历慢 | 链表/装箱容器**缓存不友好** | 用数组 / `List<T>`（连续内存） | **25**（集合内部） |
| 10 | 每帧字符串比较 | 字符串比较是 O(n) | 用 `int` 常量、`enum`、`StringComparison.Ordinal` | **22** |

## 三、逐条给出"错误写法 → 正确写法"

### ① `Update` 里的分配（最常见）

```csharp
// ❌ 每帧都在分配
void Update()
{
    object boxed = score;                                  // 装箱：24 字节
    Debug.Log("Score: " + score);                          // 字符串拼接：若干字节
    var list = new List<Enemy>();                          // 新集合
    enemies.ForEach(e => e.Tick(Time.deltaTime));          // 闭包 + 委托
}
// 60fps → 每秒 60 次以上分配 → 几分钟后 GC 卡顿
```

```csharp
// ✅ 零分配版本
private string _scoreText = "";          // 缓存字符串
private int _lastScore = -1;
private float _dt;                       // 缓存 deltaTime，避免每帧读属性

void Update()
{
    _dt = Time.deltaTime;

    // 只在分数变了才重建字符串（而不是每帧）
    if (score != _lastScore)
    {
        _scoreText = score.ToString();   // 只在这一刻分配一次
        _lastScore = score;
    }

    // 遍历用 for + 缓存 Count，不用 ForEach + Lambda
    int count = _enemies.Count;
    for (int i = 0; i < count; i++)
    {
        _enemies[i].Tick(_dt);
    }
}
```

> **`score.ToString()` 那一行的细节**：`int.ToString()` **不装箱**（它是 `int` 自己的方法），
> 但**会分配一个字符串**。所以关键是"别每帧都调用"，而不是"别调用"。

### ② `GetComponent` / `Camera.main` 缓存

```csharp
// ❌ 每次调用都查找
void Update()
{
    GetComponent<Rigidbody>().AddForce(Vector3.up);
    Camera.main.transform.position = transform.position;
}
```

```csharp
// ✅ Awake 里查一次，之后用字段
private Rigidbody _rb;
private Transform _cam;

void Awake()
{
    _rb = GetComponent<Rigidbody>();
    _cam = Camera.main.transform;        // ★ Camera.main 只在 Awake 里调这一次
}

void Update()
{
    _rb.AddForce(Vector3.up);
    _cam.position = transform.position;
}
```

> **`Camera.main` 为什么慢**：它内部等价于 `FindGameObjectWithTag("MainCamera")` ——
> **每次调用都要遍历场景里的对象**。这是"看起来像个简单属性、实际是个查找"的典型陷阱。

### ③ Lambda 提取成静态方法

```csharp
// ❌ 每帧创建闭包
void Update()
{
    _items.Sort((a, b) => a.Priority.CompareTo(b.Priority));
    //                ↑ 这个 Lambda 如果捕获了外部变量，每帧都会 new 一个 DisplayClass
}
```

```csharp
// ✅ 不捕获任何外部变量的 Lambda 会被编译器缓存（只分配一次）
private static readonly Comparison<Item> ByPriority =
    (a, b) => a.Priority.CompareTo(b.Priority);

void Update()
{
    _items.Sort(ByPriority);        // 复用同一个委托对象 → 零分配
}
```

**为什么有效**（第 23 课的原理）：

| Lambda 情况 | 编译器怎么做 | 分配次数 |
|---|---|---|
| **不捕获**外部变量 | 缓存成**静态字段**（`<>c.<>9__...`） | **只 1 次** |
| **捕获**了局部变量 | 每次执行都要 `new <>c__DisplayClass` | **每次执行都分配** |

> **判断口诀**：**Lambda 里用到了外面的局部变量吗？用到了 → 每次调用都在分配。**

### ④ 对象池（针对频繁创建/销毁）

```csharp
// ❌ 每次开火都 new 一颗子弹，1 秒后 Destroy
void Fire()
{
    var bullet = Instantiate(_bulletPrefab);        // 分配 + 实例化开销
    Destroy(bullet.gameObject, 1f);                 // 变成垃圾
}
// 密集射击时：每秒几十次分配 → GC 压力
```

```csharp
// ✅ 对象池：预先创建，反复复用
private readonly Queue<Bullet> _pool = new();

Bullet GetBullet()
{
    if (_pool.Count > 0)
    {
        var b = _pool.Dequeue();
        b.gameObject.SetActive(true);       // 复用，零分配
        return b;
    }
    return Instantiate(_bulletPrefab);      // 池空了才新建
}

void Recycle(Bullet b)
{
    b.gameObject.SetActive(false);          // 不 Destroy，放回池
    _pool.Enqueue(b);
}
```

> **对象池的本质**：**用"空间换时间"，把"分配/回收"变成"启用/禁用"。**
> 这也是第 19 课"少分配"原则的最直接落地。

## 四、怎么用 Profiler 找到"分配在哪"

**不要靠猜。** Unity Profiler 会直接告诉你哪一行在分配。

### 操作步骤

```
① Window → Analysis → Profiler（打开 Profiler 窗口）
② 上方把目标切到 Play Mode（游戏运行时才有数据）
③ 左侧选 【GC Alloc】 列 —— 这就是每个函数分配的字节数
④ 撑爆列表里数字大的那几行 → 双击 → 看调用栈，定位到你的哪一行代码
⑤ 用 Deep Profile（更深但更慢）看小函数的分配
```

### 要看懂的关键指标

| 指标 | 含义 | 目标 |
|---|---|---|
| **GC Alloc** | 这一帧分配了多少字节 | ★ **稳态时 `0 B`** |
| **GC Collect** | 这一帧触发了几次 GC | 越少越好，最好没有 |
| **Time ms** | 这一帧耗时 | 稳定在 16.6ms 以内（60fps） |
| **Total Allocated** | 累计分配 | 只增不减是正常的，看**每帧增量** |

> **⚠️ "`GC Alloc = 0 B`"是理想目标，不是所有项目都能完全做到。**
> 但**稳态游戏循环（没有新对象出生/死亡的那些帧）应该是 0** ——
> 如果稳态每帧都在分配，那就是 bug。

### 一个诊断技巧：分段注释法

找不到分配源时，**把 `Update` 里的代码一段段注释掉**，看 `GC Alloc` 什么时候归零：

```csharp
void Update()
{
    // UpdateA();        // ← 先注释这段，跑一次看 GC Alloc
    // UpdateB();        // ← 再注释这段
    UpdateC();            // ← 剩下的就是凶手
}
```

**二分法找分配源** —— 代码多的时候比逐行看 Profiler 快得多。

## 五、最终项目要求

### 项目：你的第一个 Unity 小游戏

**规模**：不用做大。**一个能完整跑通的循环 + 0 分配稳态**，比一个功能很多但每帧分配 5KB 的 demo 有价值得多。

**必须有完整游戏循环**：

```
开始（菜单/初始状态）
  → 游玩（核心玩法）
  → 死亡/失败（终止条件）
  → 重开（回到开始，且不泄漏对象）
```

**推荐选题**（挑一个，都够简单够完整）：

| 选题 | 涉及哪些本课优化点 |
|---|---|
| 弹幕射击（打飞机） | 对象池（子弹）、`Update` 分配、字符串缓存（分数） |
| 跑酷/跳一跳 | 对象池（地形块）、`GetComponent` 缓存 |
| 打砖块 | 对象池（球）、碰撞回调分配 |
| 点击放置类 | 字符串缓存（大数字格式化）、UI 刷新频率 |

### 验收标准

| # | 要求 | 怎么验证 |
|---|---|---|
| 1 | 游戏循环完整：开始 → 游玩 → 死亡 → 重开 | 自己玩三遍 |
| 2 | **稳态 `GC Alloc = 0 B`** | Profiler 看稳态帧（不是加载帧） |
| 3 | 重开 10 次不泄漏、不越来越卡 | 重开 10 次，看 Profiler 的堆大小是否稳定 |
| 4 | 每一步优化都有"优化前 / 优化后"的 Profiler 截图或数字 | 报告里 |
| 5 | **每个优化点都写清对应的底层原因** | 报告里 |

> **第 5 条是关键**：只写"我改用了对象池"不算；
> 要写"**因为 Unity 的 GC 不压缩，每帧 new 子弹会造成碎片，堆越来越大导致 GC 停顿变长，
> 所以我用对象池把分配变成复用**"。
>
> **这就是第 17-25 课的全部意义** —— 让你能说出这种句子。

## 七、本课验收自测

1. Unity 用的 GC 和 .NET 有什么不同？**为什么"少分配"在 Unity 里重要 10 倍？**
2. `Mono` 和 `IL2CPP` 有什么区别？为什么 Editor 里的性能数字不能当最终结论？

4. 为什么 Unity 里"遍历数组用 `for` 而不是 `foreach`"？这根源于哪个机制？
5. 什么样的 Lambda 会每次调用都分配？怎么改能变成只分配一次？
6. `.NET` 的 GC 有"压缩"，Unity 的没有 —— **这个差别会导致什么后果？**
7. 对象池为什么能减少 GC 压力？它"省"掉的到底是什么？
8. 你的项目里，稳态 `GC Alloc` 是多少？最大的那个分配源是什么？**它的底层原因是什么？**

<details>
<summary>参考答案要点</summary>

1. Unity 的 Boehm GC **不分代、不压缩**；碎片只增不减 → 堆越来越大 → 停顿越来越长。.NET 的 GC 会压缩、会分代，能收拾干净
2. Mono 运行 JIT（开发期）；IL2CPP 把 IL 翻译成 C++ 再编译成原生码（发布版）。两者执行方式不同，性能不同，所以 Editor 数据不能当最终结论
3. 见本课第二节那张表（`Update` 分配 / `foreach` 装箱 / 字符串拼接 / `GetComponent` / `Camera.main` / Lambda / `struct` 装箱）
4. 老版本 Mono 里 `foreach` 走 `IEnumerable`/`IEnumerator` 接口，值类型枚举器**装箱**；`for` 是纯下标访问，不装箱
5. **捕获了外部局部变量**的 Lambda → 每次执行都 `new <>c__DisplayClass`。改成不捕获（用静态字段/静态方法），编译器会缓存成静态字段，只分配一次
6. 不压缩 → 对象留在原地 → 内存出现永久空洞 → 堆持续增长 → GC 扫描和停顿越来越长
7. 省的是一次次"堆分配"（以及随之而来的碎片和 GC 压力）；把"创建/销毁"换成"启用/禁用"
8. 开放题。要点是**能说出底层原因**，而不是"我用了对象池"
