## 一、委托是对象，不是函数指针

C 的"函数指针"里**只有一个地址**。C# 的委托装不下这么少，因为下面这种写法合法：

```csharp
var a = new Widget { Name = "按钮A" };
var b = new Widget { Name = "按钮B" };
Action x = a.Show;
Action y = b.Show;
x();        // → 按钮A
y();        // → 按钮B
```

**`a.Show` 和 `b.Show` 是同一个方法**（同一段代码、同一个地址），
但执行效果不同 —— 因为作用在**不同的对象**上。**一个地址装不下"方法 + 对象"两件事。**

```
┌──────────────────────────────────────────────┐
│  委托对象（在托管堆上）                        │
├──────────────────────────────────────────────┤
│  Target : 目标对象      ← 在【哪个对象】上调用   │
│  Method : 方法指针      ← 调用【哪个方法】       │
└──────────────────────────────────────────────┘
```

### 1.1 用 `Target` 亲眼证明

`System.Delegate` 把这两格直接暴露成两个属性：**`Target`（类型 `object?`，静态方法时是 `null`）**
和 **`Method`（类型 `MethodInfo`，第 17 课说的"元数据"在这里现形了）**。

**示例代码（`Lesson23Demo\Program.cs` 第一段）**：

```csharp
Action staticDel = StaticHello;                                     // 静态方法
Console.WriteLine($"  a.Target : {DescribeTarget(staticDel)}");     // → (null)

var counter = new Counter { Label = "counter-1" };                  // 实例方法
Action instanceDel = counter.Hello;
Console.WriteLine($"  b.Target : {DescribeTarget(instanceDel)}");   // → counter-1（Counter 的实例）

// 辅助方法：Target 是 object?，所以要先判空再取 ToString()
static string DescribeTarget(Delegate d)
{
    object? target = d.Target;
    if (target is null) return "(null)";
    return $"{target}（{target.GetType().Name} 的实例）";
}
```

> ⚠️ **Nullable enable 下的坑**：`Target` 是 `object?`，直接 `.ToString()` 会得到 CS8602。
> 更隐蔽的是：**插值洞里不允许写 `{obj?.Prop}`**（`?.` 后不能紧跟 `.`）——
> 必须**先取到变量里再插值**。

### 1.2 关键证据：方法相同、对象不同

```csharp
var counter2 = new Counter { Label = "counter-2" };
Action instanceDel2 = counter2.Hello;

instanceDel.Method == instanceDel2.Method                  // True  ← 同一个方法
ReferenceEquals(instanceDel.Target, instanceDel2.Target)   // False ← 不同的对象
instanceDel == instanceDel2                                // False ← 所以委托也不相等

Action same = counter.Hello;
instanceDel == same                                        // True  ← Target + Method 都相同
```

**委托的 `==` 规则**：`Target` 和 `Method` **两个都相同**才算相等。

### 1.3 Lambda 也是一种方法

```csharp
Func<int, int> lambda = x => x + 1;
string? cls = lambda.Method.DeclaringType?.Name;    // 编译器编出来的类名（形如 <>c）
Console.WriteLine(lambda.Method.Name);              // 形如 <ShowDelegateIsObject>b__1_0
```

**这种 `<方法名>b__数字_数字` 的名字你永远写不出来** —— 它预告了后半段：
**Lambda 会变成某个编译器生成的类的一个方法。**

> **Python 对照**：Python 函数本来就是对象，`f.__self__` 是绑定的实例、`f.__func__` 是函数本体，
> 和 `Target` / `Method` 一一对应。区别：Python 里"方法 = 函数 + self"是**运行时**概念，
> C# 里"委托 = Target + Method"是**编译期**定下来的类型（`System.Delegate` 的派生类）。

## 二、闭包 = 编译器生成的 `<>c__DisplayClass`

### 2.1 问题：局部变量活不过方法调用

```csharp
static Func<int, int> MakeMultiplier()
{
    int multiplier = 3;
    return x => x * multiplier;      // ★ 方法返回后，multiplier 应该已经死了
}

var f = MakeMultiplier();
f(10);                               // → 30   但它还能读到 multiplier！
```

`multiplier` 在**栈上**，方法一返回栈帧就没了，可 Lambda 之后还要用它。
**唯一的办法：把它搬到堆上。**

### 2.2 编译器生成的类

编译器把上面那段变成**概念上**这样（类名是真实的写法，只是用了编译器专用字符）：

```csharp
// ★ 编译器生成（你在源码里写不出 <> 开头的标识符）
sealed class <>c__DisplayClass0_0
{
    public int multiplier;                                       // ← 被捕获的变量变成【字段】

    public int <MakeMultiplier>b__0(int x) => x * multiplier;    // ← Lambda 变成【实例方法】
}

static Func<int, int> MakeMultiplier()
{
    var displayClass = new <>c__DisplayClass0_0();               // ★ 每次调用都要 new！
    displayClass.multiplier = 3;
    return new Func<int, int>(displayClass.<MakeMultiplier>b__0); // Target = displayClass
}
```

**对着 1.1 节看**：`new Func<...>(displayClass.方法)` 的 `Target` 正是 `displayClass`。
那句话的三个部件是这样对应的：

| 你写的 | 编译器把它变成 |
|---|---|
| `int multiplier = 3;` | 堆上对象的**一个字段** |
| `x => x * multiplier` | 那个对象的**实例方法** |
| 返回的委托 | `Target` = 那个对象，`Method` = 那个方法 |

> **"闭包"指的就是这个结构** —— 一个函数 + 它捕获的环境（被打包成一个对象）。

### 2.3 实测：闭包每次都要分配

`Lesson23Demo` 第二段就干这件事（用的还是第 19 课那套测量法：**预热 → `GC.Collect()` → 记下 `Alloc()` → 循环 10000 次 → 取差值平均**）：

```csharp
// makeCapturing 里的 Lambda 捕获了 multiplier → 每次调用都 new DisplayClass + new 委托
double capturedBytes = MeasureAllocPerCall(() =>
{
    Func<int, int> f = makeCapturing();      // ★ 有分配
    GC.KeepAlive(f);
}, 10_000);

// 不捕获任何变量的 Lambda → 拿的是 <>c 里缓存的静态委托，一次都不分配
double plainBytes = MeasureAllocPerCall(() =>
{
    Func<int, int> f = x => x * 2;
    GC.KeepAlive(f);
}, 10_000);
```

**实跑结果（形态，数字随机器变化）**：

```
  捕获了局部变量的 Lambda 的类名 : <>c__DisplayClass3_0
  不捕获任何变量的 Lambda 的类名 : <>c

  循环 10,000 次创建 Lambda：
    捕获局部变量（闭包） :     64.0 字节/次      ← ❌ 每次都是新对象
    不捕获任何变量       :      0.0 字节/次      ← ✅ 一次都没分配
```

再用 `Method.IsStatic` 把区别钉死：捕获的那个是 `False`（DisplayClass 的**实例**方法，
要用那个字段），不捕获的那个是 `True`（`<>c` 的**静态**方法，无状态所以能缓存）。

### 2.4 三条规则（背下来）

| 写法 | 编译器生成什么 | 分配 |
|---|---|---|
| **捕获了**外部变量的 Lambda | `<>c__DisplayClass` 的**实例方法** | **每次创建都分配**（DisplayClass + 委托） |
| **不捕获**任何变量的 Lambda | `<>c` 的**静态方法** | **一次性**：委托缓存在 `<>c` 的静态字段，之后拿到的都是同一个 |
| 方法组（`obj.Method` / `Class.StaticMethod`） | 无新类 | 每次写一次就 new 一个委托（可存字段缓存） |

> ★ "不捕获零分配"是 **C# 9 之后**的行为；更早的版本每次都会 new 一个委托对象。
> 你的项目是 net9.0，所以享受这个优化。

### 2.5 捕获的是"变量"，不是"值的快照"

这是理解 `for` 陷阱的**唯一钥匙**：

```csharp
int counter = 10;
Func<int> read = () => counter;      // 捕获【变量 counter】

Console.WriteLine(read());           // 10
counter = 99;                        // ★ 改的是那个变量
Console.WriteLine(read());           // 99    ← 跟着变了！
```

如果编译器"把 10 复制一份存进 DisplayClass"，第二个输出就该是 `10`。
它给出 `99`，说明 **DisplayClass 里的字段和原来的局部变量是同一份存储**。

> **Python 对照：cell 对象**
> ```python
> def make():
>     counter = 10
>     def read():
>         return counter          # ★ Python 把 counter 装进一个 cell 对象
>     return read
> ```
> CPython 在符号表分析阶段发现 `counter` 被内层函数引用，就把它标记为 **cell 变量**
> （`read.__closure__[0].cell_contents` 可以取出来看）。
>
> | | C# | Python |
> |---|---|---|
> | 被捕获的变量存在哪 | 编译器生成的 **`<>c__DisplayClass` 实例的字段** | 运行时创建的 **cell 对象** |
> | 容器是谁造的 | **编译器**（编译期就有这个真实类型，ILSpy 里点得开） | **解释器**（运行时才有，源码里没有对应物） |
> | 捕获语义 | 按变量捕获（同一个存储） | 按变量捕获（同一个 cell） |
> | 想在闭包里**赋值** | 直接赋值即可 | 必须写 `nonlocal counter` |
>
> **结论：语义几乎一样，机制完全不同。**
> C# 的 DisplayClass 是有名字、有字段、能反射、能在 ILSpy 里展开的真实类型；
> Python 的 cell 是内置小容器 —— 你没法"看到编译器生成的类"，因为**根本没有**。

## 三、`for` 循环捕获陷阱（可复现）

### 3.1 三种写法，三种命运

```csharp
var actions = new List<Action>();

// ❌ 陷阱：for 的 i 从头到尾只有【一个变量】
for (int i = 0; i < 3; i++) actions.Add(() => Console.Write($"{i} "));
RunAll(actions);                              // → 3 3 3

// ✅ 修复：每轮在循环体里新建一个变量
actions.Clear();
for (int i = 0; i < 3; i++)
{
    int copy = i;                             // ★ 关键这一行
    actions.Add(() => Console.Write($"{copy} "));
}
RunAll(actions);                              // → 0 1 2

// ✅ foreach（Enumerable.Range(0, 3)）：C# 5 起每次迭代都是新变量，直接捕获就对 → 0 1 2
```

### 3.2 为什么会是 `3 3 3`

```
编译器生成（概念上）：
  <>c__DisplayClass0_0 { public int i; public void b__0() => Write(i); }

  var dc = new <>c__DisplayClass0_0();     ← ★ 整个循环【只有一个】 dc
  for (dc.i = 0; dc.i < 3; dc.i++)
  {
      actions.Add(new Action(dc.b__0));    ← 三个委托的 Target 都是【同一个 dc】
  }
  // 循环结束时 dc.i == 3 → 三个委托读到的都是 3
```

**三句话记牢**：① `for` 的 `i` 声明在循环**外面** → 只有**一份**存储；
② 三个 Lambda 的 DisplayClass 是**同一个对象** → 共享那个 `i` 字段；
③ 真正执行时循环早跑完了，`i` 已经是 `3`。

| 循环 | 循环变量声明在 | 每次迭代是新变量？ |
|---|---|---|
| `for (int i = 0; ...)` | 循环**外** | ❌ 只有一份 |
| `foreach (int i in ...)` | 循环**内**（C# 5 规范保证） | ✅ 每次新的 |
| `while` + 循环体内声明 | 循环**内** | ✅ 每次新的 |

### 3.3 Python 对照

```python
funcs = [lambda: i for i in range(3)]            # ❌ [2, 2, 2]  连 for 都是同一个变量
funcs = [lambda i=i: i for i in range(3)]        # ✅ [0, 1, 2]  默认参数在定义时求值

def make(i):                                     # ✅ 另一种修法：工厂函数造出独立作用域
    return lambda: i                             #    ≈ C# 里"每轮新建一个 copy"
```

| | C# | Python |
|---|---|---|
| `for` 循环变量 | 一个（陷阱） | 一个（陷阱） |
| `foreach` 循环变量 | **每次新的**（C# 5 起修复） | 没有 foreach，`for x in ...` 也是一个变量 |
| 修法 | `int copy = i;` | `lambda i=i: i` 或工厂函数 |
| 修法本质 | 造出**一个新的变量** | 造出**一个新的 cell** |

> 两种语言的闭包都**按变量捕获**，所以这个坑是**跨语言的通用坑**。

## 四、⚠️ Unity 实战：`Update()` 里的 Lambda

第 19 课讲过：**Unity 用的 Boehm GC 非分代、非压缩**，停顿更明显。
再加上 **`Update()` 每秒执行 60 次**：

```
一行 Lambda × 每秒 60 次 × 10 分钟 = 36000 个垃圾对象
            ↓
        GC 触发 → 停顿（Spike）→ 玩家感觉到"卡了一下"
```

**在 PC 上你几乎感觉不到；在手机上这是最常见的"莫名卡顿"来源。**

```csharp
// ❌ 反面写法（模拟 Update）
float target = cachedTarget.Position;      // ← 每帧才有的状态
AllEnemies(e => IsBehind(e, target));      // ❌ 每帧新建 DisplayClass + 委托
// 等价于：enemies.ForEach(e => e.Tick(dt));
// 等价于：enemies.Where(e => e.Hp > 0).ToList();

// ✅ 正确写法 A：动作不依赖当帧状态 → 缓存成字段
static readonly Action<EnemyActor> CachedTickSlow = DemoTickSlow;   // 建一次
void Update() => AllEnemies(CachedTickSlow);    // 0 分配

// ✅ 正确写法 B：动作依赖当帧状态 → 把状态放进字段
sealed class EnemyFrameMover
{
    public float TargetPosition { get; set; }        // ★ 每帧变的量变成【字段】
    public void Tick(EnemyActor e)                   // ★ 方法本身不捕获任何变量
    {
        if (e.Position < TargetPosition) e.Position += e.Speed * 0.1f;
    }
}
var mover = new EnemyFrameMover();                   // 建一次
void Update()
{
    mover.TargetPosition = cachedTarget.Position;    // 只改字段，不新建任何东西
    AllEnemies(mover.Tick);                          // 0 分配
}
```

**反面写法为什么分配**：Lambda 里用了 `target` 这个**方法参数** → 参数被捕获 →
每帧都要 new 一个 `<>c__DisplayClass` + 一个委托。**实跑结果（形态）**：

```
  模拟 300 帧，每帧遍历 10 个敌人：
    ❌ AllEnemies(e => IsBehind(e, target))  :    104.0 字节/帧  ← 闭包 + 委托
    ✅ AllEnemies(CachedTickSlow)            :      0.0 字节/帧  ← 缓存委托
    ✅ AllEnemies(mover.Tick)                :      0.0 字节/帧  ← 复用同一个委托
```

按 60 FPS 换算：第一行每秒约 **6.1 KB**，一小时约 **21.4 MB** 垃圾。

**两个补充**：

```csharp
// ① LINQ 更容易踩，而且有【两层】成本
var alive = enemies.Where(e => e.Hp > 0).ToList();
//           └─ 第 1 层：Lambda 委托可能分配    └─ 第 2 层：ToList() 必然 new 一个 List

// ② "调用"永远不分配 —— 只有"创建"才分配
//    （示例第四段里那个 multicast 是【启动时】 += 拼好的，不在每帧里）
double bytes = MeasureAllocPerCall(() => multicast(0), 300);      // → 0.0 字节/帧
```

> ### 一句话规则：热路径（`Update` / `FixedUpdate` / `LateUpdate`）里，
> ### **不要创建委托，只调用委托。**

要警惕的四种"创建"写法：

```csharp
Action a = () => DoSomething();          // Lambda → 可能分配
Action b = SomeMethod;                   // 方法组转换 → 每次转换 new 一个委托
Action c = obj.InstanceMethod;           // 实例方法组 → 同上
list.ForEach(x => ...);                  // 隐式创建 Action → 可能分配
```

ldftn      instance int32 ...<>c__DisplayClass3_0::'<ShowClosureAllocation>b__2'(int32)

> 一个 `object`（Target）+ 一个 `native int`（方法指针，就是 `ldftn` 压进来的那个）。
> **两个参数，不是"一个函数指针"。**

**第 24 课 ｜ async / await 状态机**

本课你已经看到了编译器"替你生成一个类"的手法。下一课是**同一套手法的放大版**：
