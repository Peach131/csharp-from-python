## 一、回到第 01 课那个实验

第 01 课我们做过这个实验：

```csharp
struct SPoint { public int X; public int Y; }
class  CPoint { public int X; public int Y; }

var s1 = new SPoint { X = 1, Y = 1 };
var s2 = s1;  s2.X = 99;
Console.WriteLine(s1.X);      // 1    ← 没变

var c1 = new CPoint { X = 1, Y = 1 };
var c2 = c1;  c2.X = 99;
Console.WriteLine(c1.X);      // 99   ← 变了
```

**当时你写的结论是对的**："`struct` 是值类型，`class` 是引用类型。"

**但这一课要回答更深的问题**：

> **为什么？变量里到底装了什么？数据住在哪里？**

## 二、核心答案：变量里装的东西不一样

### 值类型的变量：装着**数据本身**

```csharp
int a = 42;
```

```
变量 a 的内存：  [ 42 ]
                 ↑ 这里就是数据本身，4 个字节
```

### 引用类型的变量：装着**地址**

```csharp
var obj = new MyClass();
```

```
变量 obj 的内存：  [ 0x0000025F... ]  ──┐
                  ↑ 8 字节的【地址】     │ 指向
                                        ▼
                          堆上的对象：  [ 对象头 ][ 字段1 ][ 字段2 ]
```

**所以 `b = a` 的行为差异就解释清楚了**：

| | 复制的是什么 | 结果 |
|---|---|---|
| 值类型 `b = a` | **4/8 字节的数据** | 两份独立数据 |
| 引用类型 `b = a` | **8 字节的地址** | 两个变量指向同一个对象 |

> **一句话**：**值类型复制"东西"，引用类型复制"地址"。**

## 三、数据住在哪：栈 vs 堆

### 进程内存布局（简化）

```
高地址
  ┌─────────────────────────┐
  │      内核空间            │
  ├─────────────────────────┤
  │  栈 Stack               │ ← 线程私有，容量小（默认 1MB）
  │  局部变量、参数           │    分配极快（只是移动栈指针）
  │         ↓ 向下增长        │
  ├─────────────────────────┤
  │         ↑ 向上增长        │
  │  堆 Heap（托管堆）        │ ← 进程共享，容量大
  │  对象本体                │    由 GC 管理，分配也很快
  ├─────────────────────────┤
  │  静态字段区              │ ← 类的静态成员住这里
  ├─────────────────────────┤
  │  代码段                  │
  └─────────────────────────┘
低地址
```

### ⚠️ 纠正一个常见的错误说法

**"值类型在栈上，引用类型在堆上" —— 这句话是错的（至少不完整）。**

**正确说法**：

| 情况 | 数据住在哪 |
|---|---|
| **局部变量**是值类型（`int x`） | **栈** |
| **类的字段**是值类型 | **堆**（作为对象的一部分） |
| **数组的元素**是值类型 | **堆**（作为数组的一部分） |
| **装箱后**的值类型 | **堆** |
| 引用类型**对象本体** | **堆** |
| 引用类型的**地址**（变量本身） | 看变量在哪（局部变量在栈） |

### 判断方法（很实用）

> **问自己：「这个值是不是某个堆对象的一部分？」**
>
> - 是 → **在堆上**
> - 不是（它本身就是个独立的局部变量）→ **在栈上**

**例子**：

```csharp
class Holder
{
    public int Value;          // ← 这个 int 在【堆】上（Holder 对象的一部分）
}

struct Point
{
    public int X, Y;           // ← 取决于 Point 这个变量在哪
}

void Demo()
{
    int local = 5;                     // 栈
    var holder = new Holder();         // holder 的【地址】在栈，Holder 对象和它的 Value 在堆
    Point p = new Point();             // 栈
    Point[] arr = new Point[10];       // 数组在堆，10 个 Point 也在堆
    object boxed = p;                  // 装箱 → p 的副本在堆上
}
```

## 四、对象在堆上长什么样

### x64 上的对象布局

```
        托管堆上
  ┌──────────────────────────────┐
  │  Object Header  (8 字节)      │ ← 同步块索引：用于 lock、缓存 GetHashCode
  ├──────────────────────────────┤
  │  MethodTable 指针 (8 字节)     │ ← 指向类型描述表，GetType() 就是读它
  ├──────────────────────────────┤
  │  字段 1                       │
  │  字段 2                       │ ← 按 8 字节对齐排列
  └──────────────────────────────┘
         ↑
     变量里存的是这个地址
```

### 由此推出的两个重要事实

**事实 1：任何对象至少占 24 字节**

```
8（对象头）+ 8（MethodTable 指针）+ 至少 8（字段/填充）= 24 字节
```

**所以 `new object()` 占 24 字节，不是 0 字节。**

**事实 2：一个只有 1 个 `int` 字段的类，占 24 字节**

```csharp
class OneInt { public int A; }      // 数据只有 4 字节，实际占 24 字节
```

**16 字节的头部"开销"是数据本身的 4 倍。** 这在 Unity 里是致命的
（几千个对象 = 十几万字节的隐形开销）。

**事实 3：`struct` 没有这个头部开销**

```csharp
struct SOneInt { public int A; }    // 就是 4 字节
```

**这就是 `struct` 存在的第一个理由**：省掉对象头开销。**但前提是它别被装箱。**

## 五、`MethodTable`：运行时怎么知道"这是什么类型"

**每个类型在运行时只有一份 MethodTable（类型描述表）**，里面存着：

- 类型名、命名空间、所在程序集
- 基类指针、实现的接口列表
- **方法表**（虚方法地址数组）← **第 07 课的多态就是靠它实现的**
- 静态字段的存储区
- 实例字段大小、对齐要求

**`obj.GetType()` 干的事就是：读对象头的 MethodTable 指针 → 找到类型描述表。**

### 多态的执行过程（把第 07 课串起来）

```csharp
Animal a = new Dog();
a.Speak();
```

```
1. 找到 a 指向的对象
2. 读对象头 → 拿到 MethodTable 指针
3. 在 MethodTable 的方法表里，按【固定槽位】取 Speak 的地址
4. 调用取到的那个地址
```

**关键**：`Dog` 的 MethodTable 里，`Speak` 槽位填的是 **Dog 的版本**。
所以即使变量声明成 `Animal`，实际调用的还是 `Dog.Speak()`。

> **这就是多态的底层机制**：方法地址在运行时从 MethodTable 查，而不是编译期定死。
>
> **槽位在编译期就确定了**（`Speak` 是第几个虚方法），所以查找是 **O(1)** 的，
> 不是"按名字搜索"。虚方法调用只比普通调用多一次间接寻址。

## 六、用代码验证这些结论

### 验证 1：对象至少 24 字节

```csharp
static long MeasureClass<T>(int count = 100_000) where T : new()
{
    GC.Collect(); GC.WaitForPendingFinalizers(); GC.Collect();

    var before = GC.GetTotalMemory(true);
    var arr = new T[count];
    for (int i = 0; i < count; i++) arr[i] = new T();
    GC.KeepAlive(arr);
    var after = GC.GetTotalMemory(true);

    // 减去引用数组本身的 24 字节头 + 8 字节/元素
    return (after - before - (24 + count * 8L)) / count;
}

class Empty { }
class OneInt { public int A; }
```

**实测结果**：

| 类型 | 字段 | 实测大小 |
|---|---|---|
| `Empty` | 无 | **24 字节** |
| `OneInt` | 4 字节 | **24 字节** ← 和 Empty 一样大！ |
| `TwoInt` | 8 字节 | **24 字节** |
| `ThreeInt` | 12 字节 | **32 字节** |

**规律**：对象大小 = `16（对象头 + MethodTable 指针）+ 字段`，然后**向上对齐到 8 字节**。

```
Empty    : 16 + 0  = 16 → 对齐到 24（.NET 最小对象是 24 字节）
OneInt   : 16 + 4  = 20 → 对齐到 24   ← 那个 int 是"免费"的
TwoInt   : 16 + 8  = 24 → 24
ThreeInt : 16 + 12 = 28 → 对齐到 32   ← 跨过了 24 这条线，多花 8 字节
```

> **两个重要结论**：
> 1. **对象大小不是"字段之和"**，而是"16 字节头 + 字段，再按 8 字节对齐"
> 2. **`OneInt` 的那个 `int` 是免费的** —— 它塞进了对齐填充里，不增加总大小
>
> ⚠️ **测量时的坑**（我自己踩过）：如果算平均值时用了整数除法，
> `24` 会被截断成 `23`，让你以为对象只占 23 字节。
> **要求平均值时记得用 `double` 除再四舍五入。**

### 验证 2：`ReferenceEquals` 证明"地址"

```csharp
object a = new object();
object b = a;
object c = new object();

Console.WriteLine(ReferenceEquals(a, b));   // True  ← 同一个地址
Console.WriteLine(ReferenceEquals(a, c));   // False ← 不同地址
```

`ReferenceEquals` **比较的就是那 8 个字节的地址**。

### 验证 3：`struct` 装箱后每次都是新对象

```csharp
struct P { public int X; }
P p1 = new P { X = 1 };

object o1 = p1;      // 装箱一次
object o2 = p1;      // 又装箱一次
Console.WriteLine(ReferenceEquals(o1, o2));   // False！两个不同的盒子
```

## 七、为什么这些知识会影响性能

### 影响 1：`struct` 复制的代价

```csharp
struct BigStruct               // 100 个 int = 400 字节
{
    public int A1, A2, /* ... */ A100;
}

void Process(BigStruct s) { }  // ★ 每次调用都复制 400 字节！
```

**`struct` 赋值成本 = 字段总大小；`class` 赋值成本 = 8 字节（一个地址）。**

**所以微软给的标准是"实例大小 < 16 字节"** —— 超过这个尺寸，复制的开销就超过省下的对象头了。

### 影响 2：装箱（Unity 的死敌）

```csharp
object boxed = 42;                 // 堆上分配一个 24 字节的盒子
```

**装箱 = 把值类型复制到堆上**，产生垃圾，触发 GC。

**Unity 里 `Update()` 每帧执行**，任何一次装箱都会累积：

```
每帧 1 次装箱 × 60 fps × 300 秒 = 18000 个盒子对象
→ 触发 GC → 肉眼可见的卡顿
```

### 影响 3：缓存友好性

**数组在内存里是连续的，链表是散落的**：

```
数组：[1][2][3][4][5][6][7][8]    ← 读 1 个元素，顺带缓存了后面 7 个
链表：[1]→[4]→[2]→[7]→[3]...      ← 每次跳转都可能"缓存未命中"
```

**后果**：遍历 100 万元素的数组，可能比链表**快 5-10 倍**，即使复杂度都是 O(n)。

## 八、一张决策表（结合第 08 课）

| 你的类型是 | 复制成本 | 有对象头开销吗 | 适合场景 |
|---|---|---|---|
| 小型 `struct`（< 16 字节） | 小 | ❌ 没有 | 坐标、颜色、金额 |
| 大型 `struct`（> 16 字节） | **大** | ❌ 没有 | ⚠️ 避免，改用 class |
| `class` | 8 字节（地址） | ✅ 24 字节起 | 绝大多数业务对象 |

**选择原则**（第 08 课讲过，这里补上"为什么"）：

> **小的、不可变的、像"一个值"的 → `struct`**
> **其他 → `class`**
