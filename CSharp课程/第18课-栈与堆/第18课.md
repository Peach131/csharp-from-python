## 二、栈 vs 堆：一张表说清

```
高地址
  ┌─────────────────────────┐
  │      内核空间            │
  ├─────────────────────────┤
  │  栈 Stack               │ ← 线程私有，容量小（Windows 默认 1 MB/线程）
  │  局部变量、参数、返回地址  │    分配极快（只是移动栈指针）
  │         ↓ 向下增长        │
  ├─────────────────────────┤
  │         ↑ 向上增长        │
  │  堆 Heap（托管堆）        │ ← 进程共享，容量大（受物理内存限制）
  │  对象本体                │    由 GC 管理
  ├─────────────────────────┤
  │  静态字段区              │ ← 类的静态成员住这里（既不在栈也不在普通堆上）
  ├─────────────────────────┤
  │  代码段（IL / JIT 后的机器码）│
  └─────────────────────────┘
低地址
```

| | 栈 Stack | 托管堆 Managed Heap |
|---|---|---|
| **存什么** | 局部变量、参数、返回地址 | 对象本体 |
| **谁管理** | 编译器 + CPU 栈指针 | GC（垃圾回收器） |
| **速度** | 极快（移动栈指针，≈1 条 CPU 指令） | 快（移动分配指针），但要付 GC 的账 |
| **容量** | 小（Windows 默认 **1 MB / 线程**） | 大（受物理内存限制） |
| **碎片** | **不会**（连续、后进先出） | **会**（所以 GC 要做"压缩"） |
| **何时释放** | 方法返回时自动弹栈，**立刻** | 不确定，等 GC |
| **溢出/耗尽** | `StackOverflowException` → **进程直接死** | `OutOfMemoryException`（**可以** catch） |
| **谁私有** | **每个线程一份** | 全进程共享 |

**为什么栈"极快"？** 因为分配 = 把栈指针**减去**一个数，释放 = **加**回来。
没有"找空闲块"、没有链表、没有锁 —— 就是一条 `sub rsp, N`。

> **Python 对照**：CPython 的**调用栈也是 C 栈**，但**对象全在堆上**。
> 所以 Python 里 `a = 1` 的那个 `1` 也是堆上的一整个 `PyLongObject`（大约 28 字节），
> 而 C# 的 `int a = 1` 就是栈帧里 4 个字节。
> 这就是"数值计算为什么快很多"的第一个原因。
> 也正因为如此，Python **没有**"结构体省内存"这一说（除非用 `numpy` / `array` 模块）。

## 三、x64 上的对象布局

**每个堆对象的前 16 个字节是固定开销**：

```
        托管堆上
  ┌──────────────────────────────┐
  │  Object Header  (8 字节)     │ ← 同步块索引：lock、缓存 GetHashCode 用它
  ├──────────────────────────────┤
  │  MethodTable 指针 (8 字节)   │ ← 指向类型描述表，GetType() 读的就是它
  ├──────────────────────────────┤
  │  字段 1                      │
  │  字段 2                      │ ← 按 8 字节对齐排列
  └──────────────────────────────┘
         ↑
     变量里存的是这个地址（8 字节）
```

**这两块各自干什么**：

| 头部 | 内容 | 什么时候会用到 |
|---|---|---|
| **Object Header**（同步块索引） | 平时是 0；一旦 `lock` 它或第一次算 `GetHashCode`，运行时就往这里写一个索引 | `lock`、`GetHashCode`、`Object.GetType` 之外的运行时服务 |
| **MethodTable 指针** | 指向这个类型的**描述表** | `GetType()`、虚方法分派（**第 07 课的多态**就靠它）、类型转换检查 |

**运行时会把这个指针的**低位**当标志位用** —— 所以对象必须按 8 字节对齐。
对齐不是"为了好看"，而是"为了让标志位有地方放"。

> **Python 对照**：CPython 的每个对象也有固定头部 —— `PyObject_HEAD`：
> 引用计数（8 字节）+ 类型指针（8 字节），**一共也是 16 字节**。
> 这不是巧合，这是所有托管运行时的共同选择：**用一个指针告诉你"这是什么类型"**。

## 四、大小规律：`16 + 字段`，向上对齐到 8

**公式**：

```
对象大小 = 16（对象头 8 + MethodTable 指针 8）+ 字段总大小
          然后【向上对齐到 8 的倍数】
          并且最小 24 字节
```

**逐项推导（这一步必须自己算一遍）**：

| 类型 | 字段数据 | 算术 | 对齐到 | 实测 |
|---|---|---|---|---|
| `Empty` | 0 | 16 + 0 = 16 | 24（最小值） | **24** |
| `OneInt` | 4 | 16 + 4 = 20 | 24 | **24** ← int 是"免费"的 |
| `TwoInt` | 8 | 16 + 8 = **24** | 24（已经是 8 的倍数） | **24** ← ★ 不是 32！ |
| `ThreeInt` | 12 | 16 + 12 = 28 | **32** | **32** |
| `OneLong` | 8 | 16 + 8 = 24 | 24 | **24** |
| `TwoLong` | 16 | 16 + 16 = 32 | 32 | **32** |
| `ThreeLong` | 24 | 16 + 24 = 40 | 40 | **40** |

**三个必须记住的点**：

1. **`Empty` 是 24 字节，不是 0**。空对象也有对象头和 MethodTable 指针。
2. **`OneInt` 和 `Empty` 一样大**。那 4 字节的 `int` 塞进了对齐填充里，等于**免费**。
3. **★ `TwoInt` 是 24，不是 32**。`16 + 8 = 24` **本身就是 8 的倍数**，零头为 0，不需要再补。
   只有 `ThreeInt`（28）这种**有余数**的才要向上补到 32。

> ⚠️ **这个数字（`TwoInt` = 24）在课件里被写错过至少两次**。
> 遇到"实测和注释不一致"时，**先按规则自己算一遍，再去怀疑代码**。
> 记住一句话：**只有零头才需要向上补**。

### 顺带记住另外两个常用算式

| 东西 | 公式 | 例子 |
|---|---|---|
| **引用类型数组** | `24 + 元素大小 × 长度`，再对齐到 8 | `new object[10]` → 24 + 80 = 104 |
| **值类型数组** | `24 + 元素大小 × 长度`（元素**内嵌**，没有各自的头） | `new int[10]` → 24 + 40 = 64 |
| **字符串** | `16 + 4（长度）+ 字符数 × 2`，再对齐到 8 | 10 个字符 → 16+4+20 = 40 |
| **StringBuilder** | `24 + 4 + 字符容量 × 2`，再对齐到 8 | 容量 100 万 → 2000024 |

（数组头为什么是 24 而不是 16？因为多了"长度"这 4 个字节，再补 4 字节填充。）

## 五、★ 为什么"值类型在栈上"是错的

**先说结论**：

> **栈 / 堆的区别不属于【类型】，属于【位置】。**
> 同一个 `int`，写成局部变量就在栈上，写成类字段就在堆上。
> 同一个 `Point`，当局部变量在栈上，当类字段 / 数组元素就在堆上。

**唯一的判断标准**（问自己一句话）：

> **「这个值是不是某个堆对象的一部分？」**
> - **是** → 堆
> - **不是**（它自己就是一个独立的局部变量）→ 栈

### 逐场景对照表

| 场景 | 值类型还是引用类型 | 住在哪 | 理由 |
|---|---|---|---|
| 局部变量 `int a = 10;` | 值类型 | **栈** | 它自己就是变量 |
| 局部变量 `Point p = new Point();` | 值类型 | **栈** | ★ `new` 对 struct **不上堆**，只是把 8 字节清零 |
| 局部变量 `var o = new Foo();` 的**变量本身** | 引用类型 | **栈** | 变量里装的是 8 字节地址 |
| `new Foo()` 出来的**对象本体** | 引用类型 | **堆** | `new` 出来的本体 |
| **类的字段** `int Age` | 值类型 | **堆** | 它是对象的一部分 |
| **类的字段** `Point Position` | 值类型 | **堆** | 它**内嵌**在对象里，也是对象的一部分 |
| **数组元素** `int[] a` 里的每个 int | 值类型 | **堆** | 内嵌在数组对象里 |
| **装箱后** `object o = 42;` | 值类型→引用 | **堆** | 装箱 = 在堆上造一个盒子，把值复制进去 |
| **静态字段** `static int Count` | 值类型 | **静态字段区** | 地址写在 MethodTable 里，活得和类型一样久 |
| 字符串字面量 `"abc"` | 引用类型 | **堆** | ★ 连字面量也在堆上（驻留池），**不在栈上** |

### 一个不用测量也能看懂的佐证

```csharp
class Shape
{
    public int Id;
    public Point Center;    // ← 字段，不是属性
}

Shape s = new Shape();
s.Center.X = 3;             // ← 这行能编译通过！
```

**为什么这行能编译通过就说明 `Center` 是内嵌的？**
因为"改一个东西"的前提是**能拿到它的地址**。`s.Center` 能一路点进去改，
说明 `Center` 的 8 个字节就长在 `Shape` 对象**内部**。

**反例**：如果 `Center` 是**属性**而不是字段，这行会直接编译报错 **CS1612**
（"无法修改返回值，因为它不是变量"）—— 因为读属性拿到的只是**一份副本**，改副本没有意义。
（第 11 课讲过这个坑，当时叫"值类型 = 复制"。）

### 用测量再证一次

| 情况 | 实测 | 说明 |
|---|---|---|
| `struct Point` 数组里每个元素 | **8 字节** | 只有数据本身，没有对象头 |
| `class PointAsClass`（字段一样）每个对象 | **24 字节** | 16 头 + 8 数据，向上对齐 |
| `class Shape { int Id; Point Center; }` | **32 字节** | 16 + 4 + 8 = 28 → 对齐 32；**没有**为 `Center` 多付 16 字节头 |
| 如果 `Center` 是 `class`：`Shape` | **24 字节** | 里面只存一个 8 字节地址 |
| 如果 `Center` 是 `class`：每个 `Center` 对象 | **+24 字节** | ★ 省下的 8 字节，换来的是每个点多花 24 字节 |

**这就是 `struct` 省内存省在哪**：省掉了**每个对象一份的 16 字节头**，`struct` 变成了"内嵌的裸数据"。
**前提是它别被装箱、别长成独立对象** —— 一装箱，24 字节立刻回来。

> **Python 对照**：Python 里没有"内嵌"这回事。一个对象里有 3 个字段，
> 就是 3 个**指针**指向 3 个**另外的堆对象**；连 `1` 这种小整数都是单独的对象。
> 所以 Python 的"对象图"永远是**指针网**，永远不可能是"一块连续内存"。
> 这也是 `numpy` 存在的原因：它用一块连续内存 + 裸数据，绕开了整个对象模型。

## 六、实验 1：用 `GC.GetTotalMemory` 测对象大小

**做法**（这就是 `InternalsLab` 里 `E04_ObjectSize.cs` 的核心）：

```csharp
static long MeasureClass<T>(int count = 100_000) where T : new()
{
    // ① 先强制回收，把基线弄干净
    GC.Collect();
    GC.WaitForPendingFinalizers();
    GC.Collect();

    long before = GC.GetTotalMemory(true);      // true = 先做一次完整回收再读数

    T[] arr = new T[count];                     // 引用数组：每个元素 8 字节
    for (int i = 0; i < count; i++) arr[i] = new T();   // ← 真正被测量的分配

    long after = GC.GetTotalMemory(true);
    GC.KeepAlive(arr);                          // ★ 必须写在读数之后

    // 减掉数组自身的开销：24 字节头 + 8 字节/元素的引用槽
    // ★ 先转 double 再除！否则 24 会被截断成 23
    return (long)Math.Round((after - before - (24 + count * 8L)) / (double)count);
}
```

**四个"少一个就测不准"的细节**：

| 细节 | 少了它会怎样 |
|---|---|
| `GC.Collect()` × 2 轮 + `WaitForPendingFinalizers()` | 基线里混着前面的垃圾，数字乱跳 |
| `GC.GetTotalMemory(true)` 的 `true` | 不做完整回收，"当前堆大小"里全是未清理的垃圾 |
| `GC.KeepAlive(arr)` 放在**读数之后** | JIT 的存活分析从后往前看，arr 提前"死掉" → 对象被回收 → 数字偏小 |
| 样本量大（10 万） | 数组自身那 24 字节摊到 10 个元素上，误差放大 1 万倍 |

> ★ `GC.KeepAlive(arr)` **不能**写成 `GC.KeepAlive(arr[i])`：
> `arr[i]` 是个 `T`，`KeepAlive` 的参数是 `object` —— 传进去会**装箱**，
> 那就是 10 万次装箱，测出来的全是箱子的钱。
> 而且 `KeepAlive(arr)` 保住的是**整个数组**，自然连它挂着的 10 万个对象一起保住了。

**实测结果**（和第四节那张表一致）：

```
Empty（0 字节）      16+0=16  →24   实测 24 字节
OneInt（4 字节）     16+4=20  →24   实测 24 字节   ← int 是免费的
TwoInt（8 字节）     16+8=24  →24   实测 24 字节   ← ★ 不是 32
ThreeInt（12 字节）  16+12=28 →32   实测 32 字节
OneLong（8 字节）    16+8=24  →24   实测 24 字节
TwoLong（16 字节）   16+16=32 →32   实测 32 字节
ThreeLong（24 字节） 16+24=40 →40   实测 40 字节
```

### 顺手把"装箱的账"也算清楚

```
装箱一个 int    : 24 字节   （值本身只有 4 字节）
不装箱的 int    : 4 字节    （只有数据本身）
→ 放大 6 倍
```

**这就是 Unity 里"怕装箱怕得要命"的原因**：
每帧一次装箱 × 60 fps × 300 秒 = 18000 个盒子，每个盒子 24 字节，
全部都是需要 GC 来收的垃圾（第 19 课的主角）。

## 七、栈帧与递归

**每次方法调用都会在栈上压入一个【栈帧】，里面装着**：

| 内容 | 说明 |
|---|---|
| **参数** | 传进来的值（值类型是副本，引用类型是地址的副本） |
| **返回地址** | 回到调用方的哪一行继续执行 |
| **局部变量** | ★ 这就是"每帧多大"的主要变量 |
| **保存的寄存器** | 被调用方要用到的那些 |
| **栈探测余量** | JIT 会插入"栈探测"（probe），见第九节 |

**推论**：**栈帧越大 → 同样的 1 MB 栈能压的层数越少。**

**可以自己验的对照实验**：同一个递归函数，一份每帧只有 1 个 `int`，另一份每帧多一个
`stackalloc byte[64]` —— **后者的层数会明显变少**。

```
每帧多 64 字节 × 20000 层 = 多 1.25 MB
→ 已经超过默认的 1MB 栈了
```

> ⚠️ **测栈深度必须带安全阀**（比如 `if (depth >= stopAt) return depth;`）。
> 一次没上限的递归就会让进程当场死掉，白跑一次。

### 异常的 `StackTrace` 就是栈帧的快照

```csharp
try { Level1(); }                         // Level1 → Level2 → Level3 → ThrowHere
catch (Exception ex) { Console.WriteLine(ex.StackTrace); }
```

```
   在 Lesson18Demo.ThrowHere()
   在 Lesson18Demo.Level3()
   在 Lesson18Demo.Level2()
   在 Lesson18Demo.Level1()
```

**每行 = 一层栈帧**。所以"抛异常"很贵：它要把整条调用链抓下来。
**不要用异常做流程控制**（能用返回值判断的，就别抛）。

> **Python 对照**：Python 用 `traceback` 做同一件事，而且默认会去读源码显示出错行。
> 这是 Python traceback 比 C# `StackTrace` 更友好的地方（C# 要 `.pdb` 才能显示行号）。

### 尾调用：C# 到底做不做优化？

| | 结论 |
|---|---|
| **尾调用优化** | x64 上条件满足时 **会做**：`return M(...)` 被编译成 `jmp` 而不是 `call`，栈帧不增长 |
| **尾递归优化** | **不保证**。换个目标平台、换个 JIT、加一个局部变量，优化就可能消失 |
| 对比 | **F# 保证**尾递归优化，**C# 不保证**（原因之一：保留完整栈帧才能给你准确的异常调用栈） |

**实用结论**：处理"可能有几万层深"的数据结构（超深链表、超深目录树）：
**老老实实改成"迭代 + 自己的栈（`Stack<T>`）"**，把"隐式的栈"搬到"显式的堆"上，**不要赌 JIT**。

## 八、实验 2：为什么栈溢出 `catch` 不到

**很多人第一反应是这么写**：

```csharp
try { Boom(0); }
catch (Exception e) { Console.WriteLine("抓到了"); }   // ← 永远不会执行
```

**它抓不到，原因只有一句话**：

> `catch` 块**本身也需要栈**才能运行（要压栈帧、要调 `Console.WriteLine`），
> 而**栈已经满了** —— 没有空间给 `catch` 用。
> 运行时的选择是：**不冒险，直接终止进程。**

**`StackOverflowException` 的反常识特点**：

| 特点 | 说明 |
|---|---|
| `try` / `catch` **抓不到** | `catch (Exception)` 也抓不到 |
| `finally` **不执行** | 没有任何"优雅收尾"的机会 |
| 进程**立即死亡** | 退出码非 0，没有崩溃日志的默认输出 |
| .NET 5+ 里**无法**从托管代码捕获 | 彻底不给机会（.NET Framework 时代某些 CLR 宿主还能拦一下） |
| 它是 .NET 里少数**无法用异常机制处理**的错误之一 | 另一个是 `StackOverflow` 的亲戚：**AccessViolation** 之类 |

### 为什么会"发现得那么早"：`Probe` 与守卫页

```
每次方法进入，JIT 生成的代码会做一次【栈探测】：
    往栈顶下面的一页内存【写】一个字节
    这一页就是"守卫页"（guard page）
         ↓
指针一旦走进守卫页 → 操作系统抛一个结构化异常
         ↓
CLR 看到"这是栈溢出" → 直接杀进程（不会去抛一个托管异常）
```

探测的作用是**保证越界之前就被发现**，而不是等栈真的踩到别的内存。

### 会踩到这个坑的真实场景

| 场景 | 为什么危险 |
|---|---|
| 树 / 链表的递归遍历 | 数据深到几十万层 |
| 递归解析用户输入（嵌套 JSON / XML） | **没有长度上限** → 一个请求就能打崩进程（常见安全漏洞） |
| 属性 getter 里不小心调了自己 | 看起来像死循环，其实是栈溢出 |
| 终结器里抛异常、或终结器互相等待 | 无法 catch、无法诊断 |

### 怎么防

1. 深结构改成**迭代 + `Stack<T>`**（首选）
2. 一定要递归时，**加深度上限参数**，超了就抛普通异常或返回错误
3. 需要真的大栈 → **新建线程并指定栈大小**：

```csharp
// 默认 1MB 不够？给这个线程 16MB 栈
var t = new Thread(() => { /* 深递归放这里 */ }, 16 * 1024 * 1024);
t.Start();
t.Join();
// ★ 栈大小只能在【创建线程时】指定，创建完就改不了
// ★ 对【主线程】无效：主线程的栈在进程启动时就定好了
```

## 九、★ 实验 3：自己动手改坏它

**这一节是本课最重要的部分。** 下面每条都写清了"改哪里、预期看到什么、为什么"。
**改一处、重跑一次，比读十行强。**

| # | 改什么 | 预期看到 | 为什么 |
|---|---|---|---|
| 1 | 把 `OneInt` 的 `int` 换成 `long` | 数字**没变**（还是 24） | `16+8=24`，8 字节刚好填满填充位 |
| 1b | 再加一个 `int`（共 12 字节） | 变成 **32** | 零头 4 字节跨过 24 这条线 |
| 2 | 把 `MeasureClass` 里的 `GC.Collect()` 注释掉 | 数字乱跳（24 变成 23、56、200 多） | 基线里混着前面的垃圾，差值不再是"只多了新对象" |
| 3 | 把 `count` 从 `100_000` 改成 `10` | 数字难看（24 / 16 / 32 / 0 都有） | ① 样本太小 ② 数组那 24 字节摊到 10 个元素上，误差放大 1 万倍 |
| 4 | 把求平均那行的 `(double)` 去掉 | **全部少 1**（24→23，56→55） | 整数除法是**截断**，不是四舍五入（第 02 课的坑） |
| 5 | 把递归每帧的 `stackalloc` 从 4 个 long 改成 64 个 | 能压的**层数明显变少** | 每帧多 480 字节 —— 局部变量就长在栈帧里 |
| 6 | 把 `MeasureClass<ClassHolder>()` 换成 `MeasureStruct<Point>()` | **24 → 8** | 少的 16 字节就是"每个对象一份的对象头" |
| 7 | 把 `GC.KeepAlive(arr)` 挪到两次读数**之间** | 数字随机波动，偶尔偏小 | JIT 认为后面 arr 已死 → 那 10 万个对象可能被回收 |
| 8 | 去掉递归函数的 `[MethodImpl(NoInlining)]` | 层数突然变得很大 | 方法被内联了，"每层一个栈帧"不成立 |
| 9 | 把 `return F(d + 1);` 改成 `return F(d + 1) + 1;` | 层数突然**变得很小**（甚至崩） | 加了"活要干"，就不是尾调用了，栈帧必须真的压起来 |
