## 一、先说结论：GC 解决的是"谁来 free"

在 C 里你要自己 `free`，在 Python 里你几乎不用管，在 C# 里你**完全不用管**。

**但"不用管"不等于"不用懂"**——不懂 GC 的人会在 Unity 里写出每帧卡顿的代码，
在服务端写出内存只涨不降的服务，然后花三天时间去查一个"根本不是泄漏"的问题。

> **Python 对照**：如果你写过 Python，你的直觉是"没人引用了，内存就立刻还回来了"。
> **这个直觉在 C# 里是错的**，本课最重要的一件事就是把这个直觉改过来。

| 你可能以为 | 实际上 |
|---|---|
| `obj = null` 之后内存就释放了 | 只是"不可达"，内存还占着，直到 GC 跑 |
| 内存泄漏只发生在忘了 `free` 的语言里 | C# 一样会泄漏（静态字段、事件订阅、缓存），只是原因不同 |
| 用了 GC 就不用关心内存 | GC 让**分配**免费，但**回收**要花你的 CPU 时间 |

## 二、可达性分析：从"根"出发找活人

C# 的 GC 是**追踪式（tracing）** 的。它不数引用，而是：

> **从一组"根"出发，把所有能走到的对象标记为"活着"；走不到的，就是垃圾。**

**哪些是根？** 这是本课最该背下来的一张表：

| 根 | 说明 | 典型例子 |
|---|---|---|
| **栈上的局部变量 / 方法参数** | 当前正在执行的方法的栈帧 | `var e = new Enemy();` 里的 `e` |
| **CPU 寄存器** | JIT 把引用放进寄存器里暂存 | 你看不见，但它是真的 |
| **静态字段** | 只要类被加载，静态字段就是活的 | `static List<Enemy> _all;` |
| **GC Handle** | 与非托管代码交互时用的句柄 | `GCHandle.Alloc`、Unity 的引擎侧引用 |
| **终结队列里的对象** | 等待跑终结器的对象（第 20 课） | 有 `~ClassName()` 的对象 |

**一句话推论**：**静态字段是根 ⇒ 静态字段会造成内存泄漏。**
静态集合只 `Add` 不 `Remove`，里面的对象**永远**不会被回收。这就是 Unity"切场景后内存降不下来"的头号原因。

> **Python 对照**：Python 的引用计数里，"引用"包括局部变量、全局变量、容器元素；
> 概念上和"根"很像，但它**不从根出发做遍历**，而是每个对象自己维护一个计数器。
> 差别在后面第五、七节会体现出来。

## 三、标记 → 清除 → 压缩

一次回收分三步：

```
① 标记 Mark     从根出发遍历，给走得到的对象打标记
② 清除 Sweep    没被标记的对象，它们的内存被记为空闲
③ 压缩 Compact  把活着的对象往内存的一头挪，把空隙挤掉
```

**为什么要"压缩"？** 因为下一节你就知道：托管堆的分配只是"把指针往后挪一格"。
这个技巧成立的前提是**空闲空间必须连成一大片**。碎片会让分配变慢，也让大对象找不到位置。

**代价是什么？** 压缩要**移动对象** ⇒ 移动意味着**改地址** ⇒ 所有指向它的引用都要跟着改。
所以压缩期间必须**暂停你的所有线程**（stop-the-world）。

> **Python 对照**：CPython 的 `pymalloc` 也做内存池，但它**不移动对象**（因为 C 扩展会直接持有对象指针）。
> 所以 Python 的内存碎片只能靠"整块 arena 空了才还给系统"来缓解。

| | C# | Python |
|---|---|---|
| 释放决策依据 | 可达性遍历（从根出发） | 引用计数归零 + 循环检测 |
| 会移动对象吗 | **会**（压缩） | **不会** |
| 碎片问题 | 靠压缩解决 | 靠内存池缓解，碎片会长期存在 |
| 停顿 | 有（stop-the-world，可调） | 基本没有长时间停顿 |

## 四、分代：Gen0 / Gen1 / Gen2 与"分代假设"

**分代假设（generational hypothesis）**：

> **绝大多数对象活不过第一次 GC。**

这不是理论猜想，是实测出来的经验规律：临时字符串、装箱值、LINQ 中间结果、
每次循环 new 的小对象……它们出生即死亡。

**既然新对象大多是垃圾，那就只扫新对象。**

| 代 | 装什么 | 回收频率 | 回收代价 | 谁会被晋升进来 |
|---|---|---|---|---|
| **Gen0** | 刚 `new` 出来的小对象 | **最高**（最频繁） | 极小（通常几百 KB） | — |
| **Gen1** | 熬过 1 次 GC 的 | 中 | 小 | Gen0 存活者 |
| **Gen2** | 长期存活的 | **最低**（最稀疏） | 大（要扫全堆） | Gen1 存活者、**所有大对象** |

**关键规则：晋升是单向的。** Gen0 → Gen1 → Gen2，到 Gen2 就封顶，**永不回头**。

**为什么这样能快？** 因为一次 Gen0 回收只需要扫描"新分配的那一小块"。你的程序分配了几百万个对象，
Gen0 回收了几十次，每次只花零点几毫秒——你根本感觉不到。

**但代价是**：一个对象一旦进了 Gen2，它以后**每次 Gen2 回收都要被扫描一遍**。
所以内存分析的第一原则是：

> **别让短命对象晋升到 Gen2。** 长期存活的大集合（比如只增不减的缓存）是头号怀疑对象。

> **Python 对照**：CPython 也有"三代"（`gc.get_threshold()`），思想完全一样（也是基于分代假设），
> 但**它只管循环垃圾**——普通对象在引用计数归零时就已经死了，根本轮不到分代。

## 五、大对象堆（LOH）与 85,000 字节门槛

| 规则 | 说明 |
|---|---|
| 门槛 | **大于等于 85,000 字节**（≈83 KB）的对象**直接进大对象堆 LOH** |
| 归属 | LOH **属于 Gen2**（`GC.GetGeneration` 对它返回 2） |
| 压缩 | **默认不压缩**（这是它最大的问题） |
| 为什么单独放 | 大对象移动一次太贵（复制 85KB 的成本 >> 复制 24 字节），索性不移动 |

**⚠️ 门槛看的是"字节总数"，不是"元素个数"。**

```csharp
var a = new byte[85_000];      // 85,000 字节 → 进 LOH
var b = new int[21_251];       // 21,251 × 4 = 85,004 字节 → 也进 LOH
var c = new int[10_000];       // 40,000 字节 → 普通堆
```

**⚠️ 而且"对象大小"不等于"数组元素字节数"**——数组还有对象头、长度字段、对齐填充。
所以**门槛附近的边界要以实测为准**（这就是本课要求你亲手跑一遍的原因）：

```csharp
Console.WriteLine(GC.GetGeneration(new byte[80_000]));   // 普通堆
Console.WriteLine(GC.GetGeneration(new byte[90_000]));   // LOH
```

**LOH 的两个坑**：

1. **不压缩 ⇒ 碎片**。反复分配/释放**不同大小**的大数组，堆里会留下一个个空洞，
   最后明明总量够、却找不到一块连续的 2MB。
2. **回收贵**。它总跟着 Gen2 一起处理，而 Gen2 回收是最贵的。

**标准解法**：需要反复用的大数组，用 `ArrayPool<T>` 复用（见 `InternalsLab` 菜单 9 的实验 D）。

> **Python 对照**：Python 没有"大对象堆"这个概念，但 `pymalloc` 对大于 512 字节的分配
> 直接转交 `malloc`，本质上是同一个思路：**大块内存走另一条路**。

## 六、为什么托管堆的分配这么快？

托管堆的分配就是**移动一个指针**（叫 bump pointer allocation）：

```
next = next + size;    // 挪一格
return next;           // 这一格就是给你的新对象
```

这在机器码层面大约就是**一条加法指令**。

| | C/C++ `malloc` | C# 托管堆 |
|---|---|---|
| 怎么做 | 在空闲链表里找一块足够大的 | 指针往后挪一格 |
| 会失败吗 | 会（内存不足/碎片） | 不会（不够就触发 GC 腾地方） |
| 要锁吗 | 要（多线程安全） | 每个线程有自己的分配上下文，几乎不用 |
| 相对成本 | 慢（几十到几百个周期） | **极快（≈1 条指令）** |

**⚠️ 但请记住这个恒等式：分配快 ≠ 回收免费。**

> 你分配得越多，GC 来得越勤。真正的性能原则是 **少产生垃圾**，不是"不怕分配"。
> Unity 里"每帧 new 一个 List"之所以是经典错误，不是因为 new 慢，而是因为它把 GC 频率拉满了。

## 七、五个关键 API（全都要会）

```csharp
GC.GetAllocatedBytesForCurrentThread()  // 本线程【累计分配】多少字节（只增不减）
GC.GetTotalMemory(true)                 // 先强制一次完整 GC，再报【存活堆】大小
GC.CollectionCount(0)                   // Gen0 被回收了多少次
GC.GetGCMemoryInfo()                    // 堆的详细体检报告
GC.KeepAlive(obj)                       // 把对象的"死亡时间"推迟到这一行
```

| API | 它回答的问题 | 什么场合用 | ⚠️ 注意 |
|---|---|---|---|
| `GetAllocatedBytesForCurrentThread()` | "这段代码产生多少垃圾？" | 性能优化前后对比 | **只统计当前线程**，多线程要各线程分别测 |
| `GetTotalMemory(true)` | "现在真正占了多少内存？" | 测试、内存快照 | `true` 会**阻塞**当前线程跑一次完整 GC |
| `GetTotalMemory(false)` | "堆里现在有多少（含垃圾）？" | 看锯齿曲线 | 数字里包含尚未回收的垃圾 |
| `CollectionCount(n)` | "我的代码是不是在疯狂造垃圾？" | 压测、Unity Profiler 的替代品 | 计数**无法重置**，只能用前后差值 |
| `GetGCMemoryInfo()` | "堆的碎片/提交内存/停顿怎么样？" | 排查内存问题 | 字段含义见下表 |
| `GetGeneration(obj)` | "这个对象在第几代？" | 验证晋升 | 对 LOH 对象返回 2 |
| `KeepAlive(obj)` | "让这个对象活到这一行" | 写测量代码、和非托管交互 | 它**不阻止** GC，只是"延长生命线" |

**`GC.GetGCMemoryInfo()` 里最该认识的字段**：

| 字段 | 含义 |
|---|---|
| `HeapSizeBytes` | 托管堆总大小（含尚未回收的垃圾） |
| `TotalCommittedBytes` | 已经从操作系统**要过来**的内存（≥ 堆大小） |
| `FragmentedBytes` | 碎片化字节数（压缩能减少它） |
| `GenerationInfo[i].SizeAfterBytes` | 第 i 代的堆大小；**`GenerationInfo[MaxGeneration + 1]` 才是 LOH** |
| `PauseDurations` | 各次 GC 造成的停顿时间（GC 停顿就是这么量的） |

> **⚠️ 关于"内存只涨不降"**：GC 回收了对象，但**很少把内存还给操作系统**，
> 它留着自己复用。所以任务管理器里进程内存"只增不减"是**正常的**，不是泄漏。
> 真正的泄漏特征是：**强制 GC 之后，堆大小还是一轮比一轮高**。

## 八、灵魂实验：用 `WeakReference` 证明对象真的被回收了

**怎么知道对象真的没了？** 打印 `GC.GetTotalMemory()` 不可靠（有噪声），看任务管理器更不可靠。
**唯一可信的办法是弱引用**：

```csharp
var weak = new WeakReference(new Payload("临时对象"));   // 弱引用：不阻止回收
GC.Collect();
Console.WriteLine(weak.IsAlive);        // False = 真的被回收了
```

| | 强引用（普通变量） | 弱引用 `WeakReference` |
|---|---|---|
| 算不算 GC 的根 | **算** | **不算** |
| 会阻止回收吗 | 会 | **不会** |
| 对象被回收后 | 变量变成"悬空"（C# 里不会出现，因为对象不会提前死） | `IsAlive` 变 `False`，`Target` 变 `null` |

**两种写法都要认识**：

```csharp
// ① 非泛型：先看 IsAlive，再看 Target（Target 是 object?，要转换）
var weak1 = new WeakReference(obj);
if (weak1.IsAlive) { var o = (Payload?)weak1.Target; }

// ② 泛型（推荐）：TryGetTarget 一次搞定"还活着吗 + 拿出来"
var weak2 = new WeakReference<Payload>(obj);
if (weak2.TryGetTarget(out Payload? got)) { /* 还活着，got 就是它 */ }
else { /* 已经被回收 */ }
```

**弱引用的真实用途**：缓存。你想缓存一个大对象，但又不想因为缓存而**阻止它被回收**
（"有就用，没有就重建"）。这时弱引用就是正解。WPF 的事件、`ConditionalWeakTable` 都基于这个思想。

> **Python 对照**：`weakref.ref(obj)` 和 `WeakValueDictionary` 就是同一件事。
> 你用 Python 时的直觉可以**原样搬过来**——这是本课少数几个不需要改直觉的地方。

**连起来看**：`InternalsLab` 菜单 8 就是这一节的完整四组对照（强引用 / 静态字段 / 循环引用 / 回收前后堆变化）：

## 九、循环引用：C# 和 Python 最大的分歧

```csharp
var a = new Node(); var b = new Node();
a.Next = b; b.Next = a;        // 互相引用，形成环
a = null!; b = null!;          // 断开外部引用
GC.Collect();
// → C# 把两个都回收了
```

**为什么 C# 能收？** 因为追踪式 GC 从**根**出发。这个环里没有任何对象是根，
也没有任何根指向它 ⇒ **走不进去** ⇒ 整个环一起被回收。
**"环内部互相引用"在追踪式 GC 眼里毫无意义。**

**Python 为什么不能立刻收？** 引用计数：A 的计数是 1（被 B 引用），B 的计数是 1（被 A 引用）。
**它们互相保命**。必须等 `gc` 模块的**循环检测器**定期扫描，才能发现并回收。
所以 Python 里 `__del__` 在循环引用中**可能永远不被调用**。

| | C#（追踪式分代 GC） | Python（引用计数 + 循环检测） |
|---|---|---|
| 释放时机 | **不确定**（等 GC，通常是分配触发） | 计数归零的**那一瞬间**（通常立刻） |
| 内存曲线 | 锯齿形（涨 → 回收 → 跌） | 平滑（边用边还） |
| 循环引用 | **天然处理**，不需要额外机制 | 需要 `gc` 模块额外扫描 |
| 每次赋值的开销 | 几乎没有 | **要改计数**（多线程要加锁） |
| 分配速度 | **极快**（移动指针） | 较慢（要初始化计数、走内存池） |
| 内存碎片 | 压缩解决 | 基本不移动，碎片长期存在 |
| 可控性 | 可以调 GC 模式（工作站/服务器、并发） | 可以 `gc.disable()`，但一般不推荐 |

> **一句话记住差别**：
> **Python 是"引用没了就死"；C# 是"没人能走到你就死"。**
> 前者快在**时机确定**，后者强在**分配便宜 + 天然处理环**。

## 十、`GC.Collect()`：只在测试和诊断里用

> ## ⚠️ 生产代码永远不要调用 `GC.Collect()`

它存在的意义只有一个：**让"回收"这件事在你指定的时刻发生**，好在测试和诊断里观察现象。

**为什么生产代码里它是坏主意：**

| 原因 | 说明 |
|---|---|
| ① 代价高 | 它强制一次**完整**回收（Gen2 + LOH），比一次普通 Gen0 回收贵几十倍 |
| ② 打断节奏 | GC 自己会挑合适时机（Gen0 满了），你插一脚反而让它判断失准 |
| ③ 造成停顿 | stop-the-world ⇒ 服务端就是请求延迟尖刺（长尾延迟） |
| ④ 通常不是解药 | 如果你在为内存发愁，真问题是"**谁还引用着这些对象**" |
| ⑤ 掩盖问题 | 加了它，泄漏变成"慢慢漏"；不加它，问题早点暴露 |

**那什么时候可以？**

- **单元测试**：要断言"对象确实被回收了"（配合 `WeakReference`）
- **诊断工具 / 抓内存快照前**：先 GC 两次把垃圾清干净，快照里才是真正的"存活对象"
- **本课的示例和练习**：为了让现象立刻发生

> **Python 对照**：相当于在 Python 里到处写 `gc.collect()`。
> 你会这么做吗？不会——同理，C# 里也不要。

  有强引用时：还活着 → 断开强引用后：已回收（IsAlive = False, Target = null）
---------- 三、标记 → 清除 → 压缩 ----------
  刚分配 30 个 100KB 的大对象，堆 = 5.12 MB
  当前堆 = 5.12 MB  ← 数字没变，垃圾还在
  回收后堆 = 1.02 MB  ← 垃圾被清掉、活对象被压缩
---------- 四、分代：Gen0 → Gen1 → Gen2 ----------
  刚 new 出来的对象在 Gen0 → 第 1 次 GC 后 Gen1 → 第 2 次后 Gen2 → 第 3 次后 Gen2（封顶）
---------- 五、大对象堆（LOH）与 85,000 字节门槛 ----------
    对象                              字节数  所在代  结论
  ────────────────────────────────────────────────────────────
    new byte[84,999]                  84,999  Gen0    普通堆
    new byte[85,001]                  85,001  Gen2    ★ 直接进 LOH
    new int[10,000]                   40,000  Gen0    普通堆
    new int[100,000]                 400,000  Gen2    ★ 直接进 LOH
---------- 六、为什么托管堆分配这么快？----------
  new byte[24] 连续分配 200,000 个：总耗时 ≈ 3 ms，平均每个 24.0 字节

## 十四、Python → C# 对照速查表

| 主题 | Python | C# |
|---|---|---|
| 内存管理机制 | 引用计数 + 循环检测器 | 追踪式分代 GC |
| 释放时机 | 计数归零**立即**（通常） | **不确定**（等 GC 跑） |
| 循环引用 | 要 `gc` 模块才能收 | **天然回收** |
| 手动触发 | `gc.collect()` | `GC.Collect()`（同样**别在生产里用**） |
| 强制前先等终结器 | `gc.collect(); gc.collect()` | `GC.Collect(); GC.WaitForPendingFinalizers(); GC.Collect();` |
| 弱引用 | `weakref.ref(obj)` | `WeakReference` / `WeakReference<T>` |
| 看对象代数 | `gc.get_objects()` + 手动分代 | `GC.GetGeneration(obj)` |
| 分代阈值 | `gc.get_threshold()` / `gc.set_threshold()` | 不可直接设置（用 `GCSettings` / 运行时配置调模式） |
| 分配统计 | `tracemalloc` / `sys.getallocatedblocks()` | `GC.GetAllocatedBytesForCurrentThread()` |
| 堆快照 | `tracemalloc.take_snapshot()`、`objgraph` | Rider Memory 视图、`dotnet-counters`、`dotnet-dump` |
| 大对象 | 无特殊堆（>512B 转 `malloc`） | **LOH**（≥85,000 字节，不压缩） |
| "内存没还回去" | 常见（arena 不释放） | 同样常见（GC 保留段复用）—— **两者都不是泄漏** |

## 十五、本课新 API 速查

| API | 一句话 |
|---|---|
| `GC.GetAllocatedBytesForCurrentThread()` | 本线程累计分配字节数（只增不减） |
| `GC.GetTotalMemory(true)` | 强制完整 GC 后的存活堆大小（会阻塞！） |
| `GC.GetTotalMemory(false)` | 当前堆大小（含未回收的垃圾） |
| `GC.CollectionCount(n)` | 第 n 代被回收的次数 |
| `GC.GetGeneration(obj)` | 对象在第几代（LOH 对象返回 2） |
| `GC.MaxGeneration` | 最大代数（.NET 上是 2） |
| `GC.GetGCMemoryInfo()` | 堆体检报告（大小/提交/碎片/停顿/各代） |
| `GC.KeepAlive(obj)` | 让对象活到这一行（防 JIT 提前判定死亡） |
| `GC.Collect()` | ⚠️ 强制回收，**只在测试和诊断里用** |
| `GC.WaitForPendingFinalizers()` | 等终结队列跑完（第 20 课细讲） |
| `WeakReference` / `WeakReference<T>` | 不阻止回收的引用（`IsAlive` / `TryGetTarget`） |
| `null!` | null 包容运算符：告诉编译器"这里可能为空，别警告我" |

## 十七、【下一课预告】

**第 20 课 ｜ 终结器与 `IDisposable`**

GC 只管**托管内存**。那**文件句柄、网络连接、数据库连接、原生内存**谁来管？

| 你会在第 20 课学到的 | 一句话 |
|---|---|
| 终结器 `~ClassName()` | 谁调用（GC）、什么时候（不确定）、代价（**多活一轮 GC**） |
| `IDisposable.Dispose()` | 谁调用（**你**）、什么时候（确定）、怎么保证（`using`） |
| **`Dispose` 模式** | 两者同时存在的正确写法，以及 `GC.SuppressFinalize` 为什么必要 |
| `using` / `await using` | 编译器帮你生成 `try/finally`（第 17 课学的 IL 会派上用场） |

> **一句话预热**：第 19 课你学的是"内存怎么自动回收"，
> 第 20 课你学的是"**内存之外的东西**为什么必须手动回收"。
