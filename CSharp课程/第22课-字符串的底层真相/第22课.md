## 一、不可变性的技术根基：**索引器只有 get，没有 set**

第 13 课说"字符串不可变"。这句话在 C# 里有一个**非常具体、非常机械**的实现方式：

```csharp
string s = "Hello";
Console.WriteLine(s[0]);       // 'H'      ✅ 读得到
s[0] = 'J';                    // ❌ 编译错误 CS0200
```

编译器给的原文是：

```
CS0200: 无法为属性或索引器 "string.this[int]" 赋值 -- 它是只读的
```

**注意三件事**：① 它在说"**只读**"；② 这是**编译器**在拒绝你（程序**根本编译不出 dll**）；
③ 所以它**不是**运行时异常 —— 你甚至没机会"跑到这一行"。
**为什么 C# 能在编译期发现？** 因为 C# 是静态类型语言，`s[i]` 在类型系统里就是一个**名叫 `this[int]` 的属性**：

```csharp
// string 内部（简化示意）
public char this[int index]
{
    get { /* 返回第 index 个 char */ }
    // ★ 这里没有 set —— 所以"赋值"这件事在类型系统里根本不存在
}
```

属性可以有 `get`、有 `set`、或者**只有 `get`**。`string` 的索引器只声明了 `get`，
编译器一看到"给索引器赋值"就直接报错。

### 和 Python 对照（本课第一个重要差异）

```python
s = "Hello"
print(s[0])     # 'H'
s[0] = 'J'      # TypeError: 'str' object does not support item assignment
```

| | Python | C# |
|---|---|---|
| 底层机制 | `str` 没实现 `__setitem__` | 索引器没声明 `set` |
| 报错时机 | **运行时**（跑到这一行才炸） | **编译时**（敲完回车就标红） |
| 报错内容 | `TypeError` | `CS0200` |
| 程序状态 | 已经跑了一半 | **一行都没跑** |

> **结论**：两门语言都在说"字符串不可改"，但 C# 把这件事**提前到了编译期** ——
> 一个只在特定输入下才触发的 bug，变成了**永远不可能写出来**的代码。
> **这也正是 C# 敢做"驻留池"的前提**：编译期就证明了没人能改字符串，
> 所以共享同一份数据绝对安全（见第二节）。

### 那"想改"怎么办？

```csharp
string a = "Hello";
string b = a.Replace('H', 'J');          // ① 造一个新的（最常用）—— a 没变
string c = a[0] + "ello";                // ② char 先转成字符串再拼接 → 至少 2 次堆分配

var chars = new char[] { 'H','e','l','l','o' };
chars[0] = 'J';                          // ③ ✅ 数组的索引器【有】 set
string d = new string(chars);            //    最后再"冻结"成字符串
```

> **★ 关键区分**：数组的索引器**返回一个存储位置**（可读可写）；
> `string` 的索引器**只返回一个值**（只读）。两者是完全不同的东西，
> 只是恰好用了同一套 `[]` 语法。
> `StringBuilder` 的原理就是第三条：**内部维护一个可变的 `char` 数组**。

## 二、驻留（Interning）：为什么两个 `"abc"` 是同一个对象

```csharp
string a = "abc";
string b = "abc";

Console.WriteLine(a == b);                   // True   ← 比内容
Console.WriteLine(ReferenceEquals(a, b));    // True   ← ★ 比身份，也是 True！
```

**第二个 `True` 才是本课的重点。**

### 什么是驻留

**源码里所有相同的字面量，编译后只保留一份数据，所有引用它的地方都指向同一个对象。**
这个共享的表叫**驻留池（intern pool）**，这个行为叫**驻留（interning）**。
为什么可以这么做？**因为字符串不可变**（第一节）—— 既然没人能改它，
让 1000 个变量共享同一份、和各自持有一份，**行为完全一样**，但省内存。

### 规律：只有编译器"亲眼看到"的字符串才进池

| 写法 | 编译器看到了什么 | 进池？ |
|---|---|---|
| `string b = "abc";` | 一个字面量 | ✅ |
| `string c = "ab" + "c";` | 两个字面量，**编译期就能算出结果** → 常量折叠 | ✅ |
| `string d = left + "c";` | 一个**变量** + 一个字面量 → 只能运行时算 | ❌ |
| `string.Concat(...)` / `new string(...)` | 一个方法调用，编译器不管 | ❌ |

**空字符串是特例**：`ReferenceEquals("", string.Empty)` 是 `True` ——
整个进程只有**一份** `""`。所以 `s.Length == 0` 和 `s == ""` 都是零分配的判断。

### Python 对照：`sys.intern`

```python
# Python
a = "abc"; b = "abc"
print(a is b)                       # True（CPython 的驻留，属于实现细节）
import sys
print(sys.intern("ab" + "c") is a)  # True（手动入池）
```

```csharp
// C#
string a = "abc";
string c = string.Intern("ab" + "c".ToString());   // 运行时拼的 → 手动入池
Console.WriteLine(ReferenceEquals(a, c));          // True
```

| | Python | C# |
|---|---|---|
| 字面量驻留 | 只对"看起来像标识符"的常量做，**是 CPython 实现细节** | **所有字面量都驻留，规范保证** |
| 手动驻留 | `sys.intern(s)` | `string.Intern(s)` |
| 查询 | —— | `string.IsInterned(s)`（只查不插） |
| 比身份 | `a is b` | `ReferenceEquals(a, b)` |
| 比内容 | `a == b` | `a == b`（**`string` 重载了 `==`，是值语义**） |

> **⚠️ 最容易踩的坑**：C# 的 `==` 对字符串是**按内容比较**的。所以 ——
> **C# 的 `==` 相当于 Python 的 `==`，C# 的 `ReferenceEquals` 才相当于 Python 的 `is`。**
>
> **三个关键差异**：① C# 的字面量驻留是**规范保证**的，Python 的常量驻留是**实现细节**（PyPy 行为不同）；
> ② C# 的驻留池**永不释放**（下节详述），Python 的 `sys.intern` 官方特意声明
> "interned strings are not immortal"，但只要还有引用就留着 —— 实践中同样别喂用户输入；
> ③ 身份比较的写法不同（见上）。

## 三、`string.Intern()` 和它的危险

```csharp
string literal = "hello";
string built = new string(new[] { 'h','e','l','l','o' });

Console.WriteLine(built == literal);                      // True   内容相同
Console.WriteLine(ReferenceEquals(literal, built));       // False  不是同一个对象

string interned = string.Intern(built);
Console.WriteLine(ReferenceEquals(literal, interned));    // True   ← 变成池里那一份了
Console.WriteLine(ReferenceEquals(built, interned));      // False  ← built 自己没变
```

### ⚠️ 第一坑：返回值必须接住

`string.Intern(x)` **不会改写 `x`**，它**返回**池里的那一份。

```csharp
string.Intern(built);                    // ❌ 等于没写！
built = string.Intern(built);            // ✅ 这才有效
```

### `string.IsInterned()`：只查不插

```csharp
string? found = string.IsInterned(someString);   // 返回 null = 池里没有
```

它**不会**顺手把字符串塞进池 —— 这是"安全地查询驻留状态"的唯一方式。
（`Nullable enable` 下它的返回类型就是 `string?`，用之前必须判 null。）

### ⚠️⚠️ 第二坑（本节最重要）：池里的字符串**永不释放**

驻留池**不是普通堆对象**：GC 扫描根时会把它当成**根**的一部分，
所以池里的字符串**永远"可达"**，GC **永远不敢回收它**。

> **`string.Intern(x)` = 一次【永久】的内存承诺。**

**❌ 绝对不要这样写：**

```csharp
// 从网络 / 文件 / 输入框拿到的字符串
string s = string.Intern(userInput);
```

**为什么这是拒绝服务攻击的入口：** 用户能给你发 **100 万个互不相同**的字符串，每个都进池：
`100 万个 × (约 50 字符 × 2 字节 + 对象头) ≈ 130 MB` —— **这辈子都不会还给你**。
再发 1000 万个？**进程直接被 OOM 杀掉。** 而且这里有个反讽：
这 100 万个字符串**没有一个重复**，所以驻留想省的"去重收益"是 **0** ——
**付了永久的代价，换来零收益。**

**✅ 正确做法：用自己的 `Dictionary` 做缓存**（它随 GC 回收，还能加**上限**：

```csharp
var cache = new Dictionary<string, string>();
if (!cache.TryGetValue(raw, out string? v)) { v = raw; cache[raw] = v; }
// 超过 10000 条就清空重来 —— 对手发再多也撑不爆你
```

| | `string.Intern` | 自己的 `Dictionary` |
|---|---|---|
| 生命周期 | **进程结束才释放** | 随 GC 回收 |
| 能加上限？ | ❌ | ✅ |
| 能被攻击撑爆？ | ✅ 能 | ❌ 不能 |
| 适用场景 | 有限且已知的高重复集合 | 一切动态数据 |

**那什么时候才该用 `Intern`？** 只有一种：字符串来自**有限且已知**的集合、重复率极高 ——
比如配置里读出来的几十个字段名、枚举名、状态码。而且连这个场景都基本不需要了：
编译器会自动驻留字面量，`Dictionary` 的默认比较器本来就比较内容（不看身份），
真要省内存用的是 `ArrayPool` / `Span`。**→ 日常代码里你几乎永远不该调用 `string.Intern`。**

## 四、UTF-16：为什么 `"𝄞".Length` 是 **2**

```csharp
Console.WriteLine("𝄞".Length);      // C# 输出 2
```

```python
print(len("𝄞"))                     # Python 输出 1
```

**同一个字符，C# 说 2，Python 说 1。这是 Python 程序员最容易翻车的地方。**

### 原因：两种语言"数东西"的方式不同

```
C#       的 Length = 【UTF-16 码元（code unit）】的个数   ← 每个 char 2 字节
Python 3 的 len()  = 【Unicode 码点（code point）】的个数  ← 一个"字"
```

`char` 是 **1 个 UTF-16 码元 = 2 字节**（不是 1 字节！），而 UTF-16 是**变长**的：

- **基本多文种平面（BMP）**内的字符（U+0000 ~ U+FFFF）→ **1 个码元**
- **BMP 之外**的字符（emoji、音乐符号、生僻汉字）→ **2 个码元**，
  这 2 个码元合起来叫一个**代理对（surrogate pair）**

所以 `𝄞`（高音谱号，U+1D11E，在 BMP 之外）：

```
U+1D11E  →  两个 UTF-16 码元  →  0xD834 和 0xDD1E  →  2 个 char  →  Length == 2
```

```csharp
string clef = "\uD834\uDD1E";                     // 就是那个高音谱号（也等价于 "𝄞"）
Console.WriteLine(clef.Length);                   // 2
Console.WriteLine(clef.EnumerateRunes().Count()); // 1  ← 正确"字数"
Console.WriteLine($"0x{(int)clef[0]:X4}");        // 0xD834  高代理（high surrogate）
Console.WriteLine($"0x{(int)clef[1]:X4}");        // 0xDD1E  低代理（low surrogate）
```

> **★ `clef[0]` 和 `clef[1]` 各自不是任何字符** —— 只有拼在一起才是那个符号。
> 所以这些"看起来很无辜"的代码全是错的：`clef[0]` / `clef.Substring(0, 1)` /
> `clef.Substring(1)` / `clef.Remove(0, 1)` / `clef.Length == 1` /
> `for (int i = 0; i < clef.Length; i++) Console.Write(clef[i])` —— 全都会切出**半个字符**。

### 「中文」反倒没问题

`"中文".Length` 是 **2**，`"abc".Length` 是 **3** —— 和 Python 一样。
汉字"中" = U+4E2D，**在 BMP 内**，一个码元装得下 → 1 个 `char` → 一个汉字算 1。
**所以"C# 的中文长度不对"是错觉**，出问题的只有 **BMP 之外**的字符（emoji、高音谱号、`𠀋` 这类生僻字）。

### 正确的写法：`Rune` 和 `StringInfo`

```csharp
using System.Text;                          // 想写 Rune 这个名字才需要它
foreach (Rune r in text.EnumerateRunes())   // ✅ 按【码点】遍历（一个"字"一次）
{
    Console.WriteLine(r);
}
int 正确字数 = text.EnumerateRunes().Count();
int 人眼字数 = new System.Globalization.StringInfo(text).LengthInTextElements;  // ✅ 人眼看到的字
```

**三种数法可以完全不同**，拿 `"👨‍👩‍👧"`（一家三口 emoji）实测：`Length` 是 **8**
（3 个代理对 = 6，+ 2 个零宽连接符 U+200D）、`EnumerateRunes().Count()` 是 **5**（3 个人 + 2 个连接符）、
`StringInfo.LengthInTextElements` 是 **1**（人眼看到的字）。

> 这就是"长度"这个词在文本处理里的**歧义**。选错一个，你的
> "昵称最多 10 个字"限制就会对 emoji 用户表现异常。

### Python 为什么不一样

Python 3 的 `str` 是**码点序列**，内部有 3 种表示（PEP 393）：全是 Latin-1 → 每字符 1 字节；
含 BMP 内字符 → 2 字节；含 BMP 外字符 → **4 字节（UTF-32）**。
所以 `len()` **永远等于码点数** —— 简单、直觉，代价是内存。

C# / Java / JavaScript / Windows API 选了 UTF-16：✅ 定长 2 字节 → `s[i]` 是 O(1) 的纯地址计算；
✅ 英文文本省内存（比 UTF-32 省一半）；❌ 代价是 `Length` 不是"字符数"、索引会切到代理对中间。
**★ JavaScript 一模一样**：`"𝄞".length` 也是 2 —— 这不是 C# 的怪癖，是整个 UTF-16 家族的通病。
**必须小心的地方**：用户昵称 / 聊天内容有 emoji、"最多 N 个字"的输入限制、
按长度截断文本、反转字符串、取首字母做头像。

## 五、拼接灾难：循环 `+=` 是 O(n²)

### 每一次 `+=` 到底做了什么

```csharp
string s = "";
for (int i = 0; i < n; i++) s += i;
```

第 `i` 次循环内部：① 分配一块能装下【旧内容 + 新内容】的新内存；
② 把旧内容**全部复制**过去 ← 灾难的根源；③ 追加新内容；④ 旧字符串变成垃圾等 GC。

**复制的字符总数 = 1 + 2 + 3 + ... + n ≈ n²/2 → 复杂度 O(n²)。n 翻倍，总工作量翻 4 倍。**

**实验菜单 11** 会打印对照表，并给出"分配/次"随 n 翻倍的 O(n²) 实测曲线。

### 实测数据（大纲记录的第 13 课运行结果）

```
拼接 20,000 次：
  s += i            :  77.5 ms,  分配 1581.07 MB
  StringBuilder     :   0.8 ms,  分配     0.35 MB
  → 慢了约 91 倍，多分配约 4454 倍内存
```

| 指标 | 可靠性 | 原因 |
|---|---|---|
| 耗时 | ⚠️ 波动大 | 受 JIT、GC 何时插入、后台任务影响，几十到几百 ms 都正常 |
| **分配量** | ✅ **非常稳定** | 只跟 n 有关，几乎不受干扰 |

> **★ 本课最重要的方法论：测"分配了多少字节"比测"花了多少毫秒"可靠得多。**
> 判断一段代码贵不贵，先看它的分配量。

### 为什么分配量这么大

```
n = 20000：复制的字符数 ≈ 20000² / 2 = 2 亿个字符，每个 char 2 字节 → 约 400 MB 的【复制量】；
           而每个中间结果都要【存活到下一次】才变成垃圾，累计【分配量】约数百 MB
```

实测通常**更大**（1000 MB 以上）：数字 `0`~`19999` 平均 4.x 个字符（比"1 个字符"的估算多得多），
而且字符串的**对象头 + 内存对齐**本身也占字节（第 18 课）。

**自己动手测出来**（三个细节：除以 **`1024.0`**，写成 `1024` 会变成整数除法得到 0；
测前先 **warmup**，否则测到的主要是 JIT 时间；它统计的是**分配量**而非"内存没释放"）：

```csharp
long before = GC.GetAllocatedBytesForCurrentThread();
// ... 被测代码 ...
long allocated = GC.GetAllocatedBytesForCurrentThread() - before;
Console.WriteLine($"分配 {allocated / 1024.0 / 1024:F2} MB");   // ★ 1024.0，不是 1024
```

## 六、别只知道 `StringBuilder`

| 场景 | 首选写法 | 为什么 |
|---|---|---|
| 少量拼接（2~5 段） | `a + b` 或 `$"..."` | 可读性优先，开销可忽略 |
| 循环里累加 | `StringBuilder` | 内部可变缓冲区，O(n) |
| 已知最终长度 | `StringBuilder(capacity)` | **连扩容复制都省掉** |
| 已知所有片段 | `string.Concat` / `string.Join` | 一次分配到位，零中间对象 |
| 已知长度 + 只填一次 | **`string.Create`** | **直接在最终对象里写，零额外分配** |
| 要做搜索 / 切片 | `ReadOnlySpan<char>` | 不分配新字符串 |

### `string.Create`：唯一能在"最终对象"里直接写字的方式

```csharp
string s = string.Create(10, 'x', (span, state) =>
{
    for (int i = 0; i < span.Length; i++)
    {
        span[i] = (char)(state + i);     // 'x','y','z','{','|',...
    }
});
```

它先分配好**最终长度**的字符串，然后给你一片**可写的 `Span<char>`** ——
改它就是改结果本身，**中间一次临时字符串都没有**。

> ⚠️ 上面的 lambda **没有捕获外部局部变量**（只用了参数 `span` / `state`）。
> 一旦捕获就会生成闭包类（**第 23 课**），反而多一次分配。

### 三个细节（很多人写错）

1. **`Append(int)` 有专门重载，不装箱**；`Append(object)` 才装箱（第 21 课）——
   编译器自动选最匹配的重载，你只要别先把值转成 `object`。
2. **能估出长度就传 `capacity`**（第 13 课实测里这又能省一大截）；
   **最后只调一次 `ToString()`** —— 写在循环里等于每轮把缓冲区整个复制一遍。
3. **插值字符串已被优化**：`$"{id},{score}"` 在 .NET 6+ 走 `DefaultInterpolatedStringHandler`，
   比 `string.Format("{0},{1}", ...)` 快且不装箱 → **用 `$"..."`，淘汰 `string.Format`。**

## 七、和 Unity 的关系（第 26 课铺垫）

第 26 课会讲：Unity 的 GC（Boehm，非分代非压缩）比 .NET Core 的弱得多，
**"少分配"在 Unity 里比在 .NET 里重要 10 倍。** 字符串是 Unity 里最常见的"隐形分配源"：

```csharp
void Update()                                  // 每帧执行，60fps
{
    scoreText.text = "Score: " + score;        // ❌ 每帧 1~2 次分配 → 每秒 60~120 次
    Debug.Log("HP: " + hp);                    // ❌ 同上
}
```

**解法**（第 26 课会做成"优化到每帧 `GC Alloc = 0 B`"的项目）：
① 只在分数变化时更新文本；② 缓存 `score.ToString()` 的结果；③ 复用同一个 `StringBuilder` 实例；
④ **用 Profiler 看 `GC Alloc` 那一列**，用数字验证，别猜。
