## 二、复杂度对照表（本课的总纲，建议抄下来）

| 集合 | 底层结构 | 查找 | 插入 | 删除 |
|---|---|---|---|---|
| `T[]` | 连续内存 | O(n) | ❌ | ❌ |
| `List<T>` | 动态数组（翻倍扩容） | O(n) | O(n) | O(n) |
| `Dictionary<K,V>` | 哈希表 | **O(1)** | O(1) | O(1) |
| `HashSet<T>` | 哈希表 | **O(1)** | O(1) | O(1) |
| `SortedDictionary<K,V>` | 红黑树 | O(log n) | O(log n) | O(log n) |
| `LinkedList<T>` | 双向链表 | O(n) | O(1) | O(1) |

**第 09 课实测**：10 万元素里查找，`List` 比 `Dictionary` 慢 **711 倍**。

### ⚠️ 这张表有两处最容易误读的地方

**① "`List<T>` 插入 O(n)" 不代表"添加元素很慢"。**

表里的"插入"指的是 `Insert(i, x)`（**插到中间**，要移动元素）。
而 `Add(x)`（**加到末尾**）是**分摊 O(1)** —— 绝大多数时候一步到位，
只有极少数几次触发扩容才要搬东西，平摊下来每次只多一点点。
本课第三节会把这件事算清楚。

**② "O(1)" 不是"一次就够"，是"和数据量无关"。**

哈希查找平均要比较 1~2 次，`List` 查找平均要比较 n/2 次。
差别不在"1 次 vs 2 次"，而在**数据量翻 10 倍时，前者几乎不变，后者翻 10 倍**。

### O(n) 到底是什么感觉？——用秒表建立直觉

光写符号没有体感。假设一次比较要 1 纳秒（现代 CPU 的大致量级）：

| n | O(n) 查找 | O(log n) | O(1) |
|---|---|---|---|
| 10 | 10 ns（眨眼都来不及） | ~3 ns | ~1 ns |
| 1,000 | 1 μs | ~10 ns | ~1 ns |
| 100,000 | 100 μs | ~17 ns | ~1 ns |
| 10,000,000 | **10 ms**（肉眼可感的卡顿） | ~23 ns | ~1 ns |

**怎么读这张表**：
- n = 10 时，"O(n) 比 O(1) 慢 10 倍"——但你根本感觉不到，**这时候纠结复杂度是浪费生命**。
- n = 1000 万时，同样一个 `Contains`，一个 10 毫秒、一个 1 纳秒，**差一千万倍**——
  这就是"游戏里一个查找把帧率打崩"的真相。
- **结论**：复杂度是"数据量大了以后会怎样"的预言。**小集合不用管，大集合必须管。**

> **经验阈值（不是定律）**：元素少于几十个时，`List` 的线性查找常常**比** `Dictionary` 更快
> —— 因为哈希计算本身也有开销，而连续的数组对 CPU 缓存友好得多。
> 数据量大起来（几百、几千以上）才是哈希表的主场。

## 三、手写 `MyList<T>`（本课大头）

### 3.1 核心认识：两个数字，不是一个

```csharp
class MyList<T>
{
    private T[] _items = new T[4];   // 真正装数据的数组
    public int Count { get; private set; }   // 实际装了几个

    public int Capacity => _items.Length;    // 数组有多大 = 能装多少
}
```

**数组有 8 个格子，不代表里面装了 8 个元素。**

```
_items:  [ 10 ][ 20 ][ 30 ][ 0 ][ 0 ][ 0 ][ 0 ][ 0 ]
           ↑     ↑     ↑     └─────── 空地 ───────┘
下标:      0     1     2      3   4   5   6   7
Count = 3                                  ← 只装了 3 个
Capacity = 8                               ← 但有 8 个格子
```

**元素只住在下标 `0 .. Count-1` 这段区间里。**后面的格子是"预留的空地"。

> **Python 对照**：`sys.getsizeof([1,2,3])` 返回的是**容量**，
> `len([1,2,3])` 返回的是 **Count**。C# 把这两件事拆成了两个属性，
> Python 干脆不告诉你容量（要自己去问 `sys.getsizeof`）。
> **C# 更透明，也更容易被误用** —— 所以这节课要专门讲它。

### 3.2 `Add`：分摊 O(1)

```csharp
public void Add(T item)
{
    if (Count == _items.Length)   // ★ 装元素的格子用完了
    {
        Expand();
    }
    _items[Count] = item;
    Count++;
}
```

注意判断条件是 `Count == _items.Length`（数组满了），**不是** `Count == Capacity`
——它俩是同一个数字，但前者更直接地表达"没地方了"。

### 3.3 `Expand`：为什么是翻倍，不是 +1，也不是 ×10

```csharp
private void Expand()
{
    int newCapacity = _items.Length == 0 ? 4 : _items.Length * 2;
    T[] bigger = new T[newCapacity];
    Array.Copy(_items, bigger, Count);     // 只搬 Count 个
    _items = bigger;
    ExpandCount++;
}
```

**三种倍数策略的代价对比**（加 n 个元素，总搬运次数）：

| 策略 | 扩容次数 | 总搬运量 | 每次 Add 平均 |
|---|---|---|---|
| **+1**（每次只加一格） | n | 1+2+3+...+n = **n²/2** | **O(n)** ← 灾难 |
| **×1.5** | ~log₁.₅n | ≈ 3n | 分摊 O(1) |
| **×2**（.NET 的选择） | ~log₂n | ≈ 2n | 分摊 O(1) |

**关键洞察**：只要倍数 **> 1**，总搬运量就是 **元素总量 × 常数**，
而不是 n²。这就是"分摊 O(1)"的全部含义——
**极少数几次很贵的扩容，平摊到 n 次 Add 上，每次只多一点点。**

那为什么 .NET 选 2 而不是 1.5？——2 更快（扩容次数更少），
代价是**最多浪费一半内存**。C++ 的 MSVC `vector` 选了 1.5，
就是为了在**内存碎片**上更友好（1.5 倍增长有机会复用之前释放的块）。
**这是一个纯工程取舍，没有"正确答案"。**

### 3.4 实测：不预分配 vs 预分配

本课示例（`Lesson25Demo`）跑出来的真实数字（加 10 万个 `int`）：

```
① 不预分配（从 4 格开始翻倍，加 100,000 个 int）
   Count            = 100,000
   Capacity         = 131,072（最后一个格子基本用不上，但必须留着）
   扩容发生次数      = 15 次
   本线程总分配      = 4.79 MB
   理论搬运总字节    = 2,621,408 字节（约 2.50 MB）

② 预分配（一次开 100,000 个格子）
   本线程总分配      = 0.38 MB
   扩容发生次数      = 0 次

★ 结论：不预分配要分配 4.79 MB，预分配只要 0.38 MB。
   多出来的部分全是"搬运时留下的旧数组垃圾"，要靠 GC 去回收。
```

**为什么 "15 次" 是可以手算的？**

```
4 → 8 → 16 → 32 → 64 → 128 → 256 → 512 → 1024 → 2048
  → 4096 → 8192 → 16384 → 32768 → 65536 → 131072
数一数箭头：15 个。100,000 落在 65,536 和 131,072 之间，所以最终容量是 131,072。
```

**⚠️ 注意：预分配省的不是时间，是垃圾。**

很多人以为 `new List<T>(100000)` 是为了"跑得更快"。
**对于 10 万次 Add 这种量级，时间差别其实很小**（内存拷贝非常快）。
真正的收益是：**不产生那 2.5 MB 的中途垃圾，GC 压力小**。

> 这一点在 Unity 里是**生死攸关**的（第 26 课）：
> Unity 用的 Boehm GC 不能压缩堆，每一次没必要的分配都可能变成一次卡顿。
> **"少分配"比"跑得快"重要。**

> **Python 对照**：Python 没有"预分配容量"这个 API（`list(100000)` 会造出
> 10 万个 `None`，语义完全不同）。C# 的 `new List<T>(capacity)` 是**只开地、不放东西**，
> 这是 C# 独有的优化手段。

### 3.5 索引器 `this[int index]`

```csharp
public T this[int index]
{
    get
    {
        if (index < 0 || index >= Count)       // ★ 越界判断用 Count，不是 Capacity
        {
            throw new IndexOutOfRangeException($"下标 {index} 越界（当前 Count = {Count}）");
        }
        return _items[index];
    }
    set
    {
        if (index < 0 || index >= Count)
        {
            throw new IndexOutOfRangeException($"下标 {index} 越界（当前 Count = {Count}）");
        }
        _items[index] = value;                 // ★ 索引器的 set 里，值叫 value
    }
}
```

**两个要点**：

**① `get` 和 `set` 可以只给一个。** 只读集合（比如一个"只允许读的包装类"）只写 `get`；
我们的 `MyList` 可读可写，所以两个都要。

**② 越界判断用 `Count` 而不是 `Capacity`。**
数组有 8 个格子、只装了 3 个，那 `list[5]` **必须越界**——
第 5 格里的东西是 `default(T)`，不是数据。

> **Python 对照**：Python 的 `list[i]` 越界抛 `IndexError`，而且支持负下标（`list[-1]`）。
> C# 的索引器**默认不支持负下标**——但你可以自己实现：
> ```csharp
> public T this[int index]
> {
>     get
>     {
>         if (index < 0) index += Count;        // ★ 自己加上负下标支持
>         if (index < 0 || index >= Count) throw new IndexOutOfRangeException();
>         return _items[index];
>     }
> }
> ```
> C# 8 之后更地道的写法是用 `Index` 类型（第 03 课的 `list[^1]`）。

### 3.6 `Insert` / `RemoveAt`：为什么它们是 O(n)

```csharp
public void Insert(int index, T item)
{
    if (index < 0 || index > Count) throw new ArgumentOutOfRangeException(nameof(index));

    if (Count == _items.Length) Expand();

    // 把 [index, Count) 这段整体右移一格
    Array.Copy(_items, index, _items, index + 1, Count - index);

    _items[index] = item;
    Count++;
}

public void RemoveAt(int index)
{
    if (index < 0 || index >= Count) throw new ArgumentOutOfRangeException(nameof(index));

    Count--;
    // 把 [index+1, Count+1) 这段整体左移一格
    Array.Copy(_items, index + 1, _items, index, Count - index);
    _items[Count] = default!;          // ★ 清空腾出来的格子（见下）
}
```

**搬家现场**（示例第四段的真实输出）：

```
初始           : [20, 30, 40, 50]              Count = 4
Insert(0, 10)  : [10, 20, 30, 40, 50]          ← 4 个元素全体后移！
Insert(3, 35)  : [10, 20, 30, 35, 40, 50]      ← 后 3 个后移
RemoveAt(0)    : [20, 30, 35, 40, 50]          ← 4 个元素全体前移
RemoveAt(末尾) : [20, 30, 35, 40]              ← 一个都不用挪
```

**在 10 万元素上插一次（实测）**：

```
插到【开头】Insert(0, x)      :   0.1xx ms   ← 要搬 100,000 个
插到【末尾】Insert(Count, x)  :   0.000x ms   ← 一个都不用搬
```

**⚠️ `_items[Count] = default!` 这一行千万别省。**

删掉元素后，如果不把腾出来的格子清成 `null`，那个**引用会一直留在数组里**：

```
RemoveAt 之后不清空：
_items:  [ A ][ C ][ C ][ D ][ null ][ null ]...
                              ↑
                        这个格子还把 D 抓着呢！
                        → GC 认为"还有人在用它"，永远回收不了
```

这叫**陈旧引用（stale reference）**，是内存泄漏的一种。
`.NET` 的 `List<T>.RemoveAt` 内部做的正是这件事。

> **`default!` 里的 `!` 是什么？** Nullable 开了以后，编译器会警告
> "你可能在往 `T`（可能是非空引用类型）里写 null"。
> `!` 是**告诉编译器"我知道，别再提醒了"**——它不改变运行时的值，纯粹是给编译器的备注。
> **不要拿 `!` 到处消警告**：它应该只在"我确实比编译器懂得多"的时候用。

### 3.7 把 MyList 和真实的 List 对照

| 能力 | `MyList<T>`（本课） | `List<T>`（.NET） |
|---|---|---|
| `Add` / 索引器 / `Count` / `Capacity` | ✅ | ✅ |
| `Insert` / `RemoveAt` / `IndexOf` | ✅ | ✅ |
| `Remove(T)` / `Clear` | 部分 | ✅ |
| `AddRange` / `Sort` / `BinarySearch` | ❌ | ✅ |
| `IEnumerable<T>`（能 `foreach`、能用 LINQ） | ❌ | ✅ |
| 线程安全 | ❌ | ❌（要 `ConcurrentBag` 等） |
| 版本号检查（遍历时修改会抛异常） | ❌ | ✅（`_version` 字段） |

**最后两行最值得注意**：
- **能 `foreach` 不是免费的**：`List<T>` 必须实现 `IEnumerable<T>`，
  还得配一个 `Enumerator` 结构体。这是第 16 课延迟执行的基础。
- **"遍历时修改集合"会抛异常**，靠的是内部一个 `_version` 计数器：
  每次改动 `_version++`，遍历开始时记一份，每走一步对比一次，不一致就抛
  `InvalidOperationException`。**这是一个非常便宜的防御性设计**，值得学。

## 四、手写简易哈希表 `MyHashMap<K,V>`

### 4.1 第一原理：哈希 → 桶 → 冲突链

哈希表的全部思想可以用一句话概括：

> **不用"一个一个找"，而是"根据键直接算出它应该在哪"。**

三步：

```
① 哈希        key.GetHashCode()  →  一个很大的 int（可能是负数）
② 压进桶      hash % 桶数        →  0 .. 桶数-1 之间的下标
③ 冲突链      同一个桶里的多个键值对，用链表串起来，逐个比 Equals
```

**第 1、2 步的实测**（示例第五段，`% 5` 只有 5 个桶）：

```
     字符串           GetHashCode()    % 5（桶下标）
     --------------------------------------------
     apple                  xxxxxxxx               2
     banana                 xxxxxxxx               0
     cherry                 xxxxxxxx               3
     date                   xxxxxxxx               4
     elderberry             xxxxxxxx               1
     fig                    xxxxxxxx               0     ← 和 banana 撞了！
```

**注意最后那一列**：值域从"几亿"压到了 `0~4`。
**这就是哈希函数的全部工作——把无限大的键空间，压进有限个桶。**

**而压缩必然带来冲突。** 这不是"实现不好"，是**数学上躲不掉**
（鸽巢原理：键比桶多，必然有桶装多个键）。所以哈希表必须处理冲突，
链地址法（separate chaining）是最经典的一种。

### 4.2 冲突链长什么样（示例第五段的"烂哈希"演示）

故意用一个烂哈希（`hash = key % 10`，只有 10 个桶），桶里的样子：

```
桶 0 : （空）
桶 1 : 1 → 11 → 21
桶 2 : 2 → 12
桶 3 : 3
桶 4 : 4
桶 5 : 5
桶 6 : 6
桶 7 : 7
桶 8 : （空）
桶 9 : （空）
```

**看桶 1**：`1 → 11 → 21` 三个键挤在同一条链上。
要找 `21`，得先跟 `1` 比一次、再跟 `11` 比一次——**这就是哈希表慢下来的唯一原因**。

> **所以哈希表的 O(1) 有前提：【哈希分布均匀 + 负载因子受控】。**
> 哈希函数写得烂（或被人恶意构造），哈希表可以退化成 O(n) 的链表。
> 这就是"哈希碰撞攻击（HashDoS）"的原理——现实里的安全漏洞。

### 4.3 `Put`：加/改一个键值对

```csharp
public void Put(K key, V value)
{
    // ★ 1. 先判断"装了这一对之后会不会超标"
    if ((_count + 1) > _buckets.Length * LoadFactorLimit)
    {
        Rehash();
    }

    int index = GetBucketIndex(key, _buckets.Length);

    // ★ 2. 沿着这条链找：键已存在就覆盖（这就是 map[k] = v 的语义）
    for (Node? node = _buckets[index]; node is not null; node = node.Next)
    {
        if (EqualityComparer<K>.Default.Equals(node.Key, key))
        {
            node.Value = value;
            return;                 // ★ 覆盖不算新增，_count 不变
        }
    }

    // ★ 3. 没找到 → 新建节点，插到链的【头部】（一步到位，O(1)）
    _buckets[index] = new Node(key, value) { Next = _buckets[index] };
    _count++;
}
```

**为什么插到链头而不是链尾？** 链头只用一步；链尾要先走完整条链。

**为什么用 `EqualityComparer<K>.Default.Equals` 而不是 `node.Key == key`？**
- `K` 是未知类型，可能没重载 `==`（那就变成比地址了）；
- 对值类型，泛型版的 `==` 会**装箱**（第 15 课的坑）；
- `EqualityComparer<K>.Default` 会自动挑最好的比较方式（实现了 `IEquatable<K>` 就走它），
  **而且会用正确的"相等语义"**——这正是哈希表需要的。

### 4.4 哈希函数：一个小细节能决定崩溃还是正常

```csharp
private int GetBucketIndex(K key, int bucketCount)
{
    int hash = key.GetHashCode();
    return (hash & 0x7FFFFFFF) % bucketCount;
}
```

**为什么不用 `Math.Abs(hash) % n`？**

因为 `int.MinValue`（-2147483648）取绝对值还是负数（溢出），
`Math.Abs` 会抛 `OverflowException` 或者返回一个负值 → **负数下标 → 数组越界崩溃**。

`hash & 0x7FFFFFFF` 把最高位（符号位）清 0，**永远得到非负数**，而且比取模更快。

> **为什么 .NET 不直接"对 2 的幂取模"？**
> 其实可以对 2 的幂用位运算 `hash & (bucketCount - 1)`（更快），
> 但**只有在 `bucketCount` 是 2 的幂时才等价**。
> .NET 的 `Dictionary` 确实用了质数大小的桶数组（为了更好的哈希分布），
> 所以它用真正的取模。**"桶数取质数还是 2 的幂"是哈希表设计的经典权衡。**

### 4.5 负载因子 + rehash

```csharp
public const double LoadFactorLimit = 0.75;

private void Rehash()
{
    Node?[] old = _buckets;
    _buckets = new Node?[old.Length * 2];          // ★ 桶数翻倍

    for (int i = 0; i < old.Length; i++)
    {
        Node? node = old[i];
        while (node is not null)
        {
            Node? next = node.Next;                 // ★ 先记住下一个

            int newIndex = GetBucketIndex(node.Key, _buckets.Length);   // ★ 重新算！
            node.Next = _buckets[newIndex];
            _buckets[newIndex] = node;

            node = next;
        }
    }

    RehashCount++;
}
```

**⚠️ 必须"重新算一遍"，不能直接拷贝。**
因为桶数变了，`hash % 桶数` 的结果**全变了**：

```
4 个桶：  hash = 13  →  13 % 4  = 1
8 个桶：  hash = 13  →  13 % 8  = 5     ← 同一个键，换了个桶！
```

**负载因子的实测**（示例第六段，从 4 个桶开始放 10 个键值对）：

```
     Count   桶数   负载因子   最长链
         1     4       0.25       1
         2     4       0.50       1
         3     4       0.75       1
         4     8       0.50       1   ← rehash！(3+1) > 4×0.75 成立
         5     8       0.62       1
         6     8       0.75       1
         7    16       0.44       1   ← rehash！(6+1) > 8×0.75 成立
         8    16       0.50       1
         9    16       0.56       2
        10    16       0.62       2
   存完 10 个键值对：rehash 发生 2 次，最终桶数 16
```

**读这张表的三个要点**：

**① 触发点是第 4 个、第 7 个。**
因为判断写在**插入之前**：`(_count + 1) > 桶数 × 0.75`。
装第 4 个时 `_count = 3`，`(3+1) > 3` 成立 → 扩容；
装第 7 个时 `_count = 6`，`(6+1) > 6` 成立 → 扩容。
**这个 `+1` 的位置是最容易写错的地方**，写错了负载因子就会短暂超标。

**② 从 4 个桶开始，最终停在 16 个桶，不是 8 个。**
数一遍：`4 →(第4个)→ 8 →(第7个)→ 16`。
16 × 0.75 = 12，10 个元素还没到上限，所以到此为止。

**③ 每次 rehash 之后，负载因子立刻掉下来。**
分子（元素数）没变，分母（桶数）翻倍了 —— 0.75 直接掉到 0.5 以下。
**这就是负载因子的意义：它是一个"该扩容了"的报警器。**

> **注意"最长链"那一列**：它取决于**字符串真实的哈希码**。
> .NET 的字符串哈希带**随机化种子**（防 HashDoS 攻击），
> **每次启动进程都不一样**。所以你的最长链可能是 1、可能是 2、某一格可能是 3。
> **这一列不用对答案**，看的是"桶数一变，负载因子就掉下来"这个趋势。

**0.75 这个数字哪来的？** 纯工程经验：
- 太小（比如 0.3）：桶大量空着 → 浪费内存，而且 rehash 太频繁
- 太大（比如 2.0）：链变长 → 查找退化成 O(n)，失去了哈希表的意义
- **0.75 是"空间浪费"和"链长"的经典折中**，Java 的 `HashMap` 也是 0.75

### 4.6 实测：手写哈希表 vs 官方 Dictionary

**自己动手测一遍**（这段代码建议你加到练习的 TODO 4 后面）：

```csharp
const int M = 200_000;
var mine = new MyHashMap<int, int>(M);          // 你的手写版
var theirs = new Dictionary<int, int>(M);       // 官方版

// ① 写入 20 万个键值对
double msMinePut = TimeBest(() => { for (int i = 0; i < M; i++) mine.Put(i, i); }, 3);
double msTheirsPut = TimeBest(() => { for (int i = 0; i < M; i++) theirs[i] = i; }, 3);

// ② 随机查 100 万次（命中 + 不命中混合）
var rnd = new Random(12345);
int[] qs = new int[1_000_000];
for (int i = 0; i < qs.Length; i++) qs[i] = rnd.Next(0, M * 2);

double msMineGet = TimeBest(() => {
    int hit = 0;
    foreach (int q in qs) if (mine.TryGetValue(q, out _)) hit++;
    GC.KeepAlive(hit);
}, 3);
double msTheirsGet = TimeBest(() => {
    int hit = 0;
    foreach (int q in qs) if (theirs.ContainsKey(q)) hit++;
    GC.KeepAlive(hit);
}, 3);

Console.WriteLine($"写入 20 万：手写 {msMinePut,7:F1} ms  |  官方 {msTheirsPut,7:F1} ms  |  慢 {msMinePut / msTheirsPut:F1} 倍");
Console.WriteLine($"查 100 万 ：手写 {msMineGet,7:F1} ms  |  官方 {msTheirsGet,7:F1} ms  |  慢 {msMineGet / msTheirsGet:F1} 倍");
```

**预期：手写的会慢几倍**（具体倍数看机器，通常在 **2~5 倍**之间）。
**结论：手写的会慢，慢在哪要说清楚**：

| 慢的原因 | 说明 | 官方怎么做 |
|---|---|---|
| **没有条目数组** | 官方 `Dictionary` 用连续数组存条目（对 CPU 缓存友好），我们每个元素一个 `Node` 对象（散在堆上） | 紧凑存储 |
| **每个键值对一个对象** | `Node` 是 class → 堆分配 + 对象头开销（24 字节起） | 结构体数组 |
| **取模用了 `%`** | `%` 是除法指令，约 20~40 个时钟周期 | 特殊化的快速取模 |
| **没有缓存哈希码** | 我们每次查找都调一次 `key.GetHashCode()` | 存进条目里，只算一次 |
| **链节点指针跳转** | 链表是"指针追逐"，每次跳转都可能 cache miss | 连续数组顺序探测 |
| **没有质数桶数优化** | 桶数固定 2 的幂，哈希分布依赖 `GetHashCode()` 的质量 | 质数桶数 + 随机化种子 |

**★ 最该注意的一点**：**手写版也是 O(1)，官方版也是 O(1)** ——
它们**在复杂度上完全同级**，差的是**常数因子**。
所以"手写的慢几倍"这件事**不影响本课的任何结论**：
- 找一个键，手写版平均比较 **1~2 次**，官方版也是 **1~2 次**（同一量级）
- 数据量从 10 万涨到 100 万，两边的耗时都**只涨一点点**，都不会像 `List` 那样翻 10 倍

**这正是"复杂度"和"常数因子"的分工**：
- **复杂度**决定"数据量大了会怎样"——手写版和官方版**同命**（都是 O(1)）
- **常数因子**决定"同一量级下谁更快"——官方版赢（紧凑存储 + 缓存友好）

**★ 那这 200 行代码白写了？——不。**
你现在知道 `Dictionary` 内部**大概长什么样**了，也知道它**为什么值这个复杂度**。
**"会用一个东西"和"知道它为什么能用"是两种能力。**

> **⚠️ 一个必须说清的坑**：上面这段对比代码里，`mine.Put` 的 `TimeBest(…, 3)`
> **第一轮就把 20 万个键值对全放进去了**，第二轮、第三轮是**覆盖**（键已存在）。
> 所以后两轮测的是"覆盖"而不是"新增"。**这是性能测试里非常常见的陷阱**：
> **测之前一定问自己"循环跑第二遍时，状态和第一遍一样吗？"**
> 要测真正的"新增"，得每轮 `new` 一个新的 map（不在计时区间里 new，或者干脆只跑 1 轮）。

> **Python 对照**：CPython 3.6+ 的 `dict` 从"经典链地址法"改成了**紧凑哈希表**：
> 索引数组（稀疏）+ 条目数组（紧凑，按插入顺序）分开存。
> 结果：**内存省了 20~25%，而且顺带保证了插入顺序**。
> .NET 的 `Dictionary` 至今还是经典设计。**同一个数据结构，不同语言的取舍完全不同。**

## 五、复杂度实测：10 万元素里查找

示例第七段的真实输出（数据量 100,000，查询 1,000 次，一半命中一半不命中）：

```
     集合                方法                     耗时        每次查询
     --------------------------------------------------------------------
     List<int>           Contains              6.80 ms       6.800 μs
     Dictionary          ContainsKey           0.02 ms       0.020 μs

     倍数：340 倍
```

**（第 09 课在同一台机器上测出 711 倍，数字不同很正常——
查询次数、命中率、Debug/Release、CPU 都会影响。要记的是【量级】。）**

**为什么差这么多？把"比较次数"算出来就明白了**：

| | 平均比较次数 | n 翻 10 倍时 |
|---|---|---|
| `List.Contains` | n/2 = 50,000 次 | 变成 500,000 次（**翻 10 倍**） |
| `Dictionary.ContainsKey` | 1~2 次 | 还是 1~2 次（**几乎不变**） |

**★ 这才是复杂度的真正含义：不是"谁快谁慢"，而是"数据量涨上去以后谁先崩"。**

> **实用判断**：如果你写了一个 `foreach`（或 `List.Contains`）**只是为了"找某个东西在不在"**
> —— 那八成该换成 `Dictionary` 或 `HashSet`。
> **这个"闻到味道就改"的直觉，就是本课最大的产出。**

### 为什么遍历数组比链表快（即使复杂度都是 O(n)）？

大纲里的自测题之一，答案在**硬件**，不在算法：

| | 数组 | 链表 |
|---|---|---|
| 元素位置 | 连续内存 | 散落在堆各处 |
| CPU 缓存 | **一次 cache line（64 字节）能装 8~16 个元素** → 后续访问命中缓存 | 每跳一个节点都可能 cache miss（要等 100+ 周期去内存取） |
| 预取器 | CPU 能预测"下一格"，提前把数据搬进缓存 | 完全预测不了 |
| 实测差距 | — | **同样 O(n)，数组常常快 5~10 倍** |

**"复杂度相同"不代表"性能相同"。O(n) 只说了"遍历一遍"，
没说"每一遍的每一次有多贵"。** 这也是为什么 `Dictionary` 宁可维护一个连续数组，
也不愿意用纯链表。

## 六、⚠️ 哈希契约（本课最该记住的一条）

> **如果 `a.Equals(b)` 为 true，那么 `a.GetHashCode()` 必须相等。**

### 6.1 反面例子：只重写 `Equals`，不重写 `GetHashCode`

```csharp
class BadPoint
{
    public int X { get; init; }
    public int Y { get; init; }

    public override bool Equals(object? obj)
        => obj is BadPoint other && other.X == X && other.Y == Y;

    // ★ 故意不写 GetHashCode()  → 用 object 的默认实现 → 基于对象地址
}
```

实测结果（示例第八段）：

```
badA.Equals(badB)              = True       ← 按值相等，正确
badA.GetHashCode() == badB...  = False      ← 哈希码不一样！
badSet.Contains(badB)          = False      ← ★ 明明相等，却说"没有"
badSet.Add(badB) 后再看 Count  = True / 2   ← ★ 重复元素被放进去了
```

**为什么？** 哈希集合的查找是**两步**：

```
① 按 GetHashCode() 找到桶
② 在桶里逐个比 Equals()
```

两个"相等"的对象哈希码不同 → **被分到不同的桶** → 第 ② 步**压根没机会执行**。
`Equals` 永远没被调用，所以答案当然是 `False`。

**这就是最阴险的地方**：`Equals` 写得完全正确，
但 `Contains` 返回 `False`、`HashSet` 里出现重复元素、
`Dictionary` 里同一个键存了两遍。**而且不报错、不崩溃，只是"数据不对"。**

### 6.2 正确写法：两个一起重写，且用同样的字段

```csharp
class GoodPoint
{
    public int X { get; init; }
    public int Y { get; init; }

    public override bool Equals(object? obj)
        => obj is GoodPoint other && other.X == X && other.Y == Y;

    public override int GetHashCode()
        => HashCode.Combine(X, Y);           // ★ 参与 Equals 的字段必须全部参与这里
}
```

实测：`Contains` 返回 `True`，`Add` 返回 `False`，`Count` 还是 1。**一切正常。**

**规则**：**参与 `Equals` 的字段，必须全部参与 `GetHashCode`。**
反过来（`GetHashCode` 用了 `Equals` 不用的字段）也是错的——
那会让两个相等的对象哈希码不同，**同样违反契约**。

> **省事的办法：用 `record`。**
> ```csharp
> record Point(int X, int Y);
> ```
> 编译器自动按**所有字段**同时生成 `Equals`、`GetHashCode`、`==`、`!=`、`ToString`
> ——**一劳永逸，不可能写错**（第 11 课）。
> **什么时候用 `record` 当字典键？当你希望"按值相等"的时候，一律用 `record`。**

### 6.3 另一个极端：`GetHashCode()` 永远返回常数

```csharp
class ConstantHashKey
{
    public int Id { get; init; }
    public override int GetHashCode() => 42;        // ★ 所有实例哈希码都一样
    public override bool Equals(object? obj)
        => obj is ConstantHashKey other && other.Id == Id;
}
```

**这【不违反】契约，它是合法的！**
`Equals` 相等的对象哈希码确实相等（都是 42）。

**但代价是灾难**：所有键挤进同一个桶，哈希表**退化成链表**，查找变成 O(n)。
**"合法但性能灾难"，这是最阴险的一种写法。**

> **实战教训**：如果你发现某个字典突然变慢了，
> **第一件事就是去查它的键类型的 `GetHashCode`**。
> 一个返回常数的 `GetHashCode`（或者基于一个几乎不变的字段）
> 能让 O(1) 静悄悄地变成 O(n)，而且**没有任何报错**。

| 概念 | Python | C# | 本课讲到的细节 |
|---|---|---|---|
| 动态数组 | `list` | `List<T>` | 都翻倍/近似翻倍扩容 |
| 预分配容量 | ❌ 没有 | `new List<T>(capacity)` | ★ 省的是**垃圾**，不是时间 |
| 容量查询 | `sys.getsizeof(l)`（近似） | `list.Capacity` | C# 直接暴露 |
| 元素个数 | `len(l)` | `list.Count` | 不是 `Length`（第 09 课） |
| 中间插入 | `l.insert(i, x)` | `l.Insert(i, x)` | 都是 O(n)，都要搬元素 |
| 按索引删 | `del l[i]` | `l.RemoveAt(i)` | 都是 O(n) |
| 末尾追加 | `l.append(x)` | `l.Add(x)` | 都是**分摊 O(1)** |
| 哈希表 | `dict` | `Dictionary<K,V>` | 原理相同，实现不同 |
| 紧凑哈希表 | ✅ 3.6+ | ❌ | Python 省内存 + 保序 |
| 取哈希 | `hash(obj)` | `obj.GetHashCode()` | 都是 int |
| 哈希契约 | `__eq__` 和 `__hash__` 必须一致 | 同 | **两个语言都是同一条铁律** |
| 只写 `__eq__` 的后果 | `__hash__` 被自动设成 `None`（**不可哈希，直接报错**） | **静默错误**（能找到但找不到） | ★ **C# 更危险** |
| 有序字典 | `dict`（3.7+ 保序） | `SortedDictionary` 或 `OrderedDictionary` | C# 的 `Dictionary` **不保序** |
| 遍历时修改 | `RuntimeError: dictionary changed size` | `InvalidOperationException` | 都要靠版本号检测 |

**⚠️ 最重要的一行是"只写 `__eq__` 的后果"那行**：

- **Python 会直接拦住你**：定义了 `__eq__` 但没定义 `__hash__`，
  Python 把 `__hash__` 设成 `None`，你一放进 `set` 就报
  `TypeError: unhashable type`。**错误立刻暴露。**
- **C# 不会拦你**：`GetHashCode` 从 `object` 继承，代码能编译、能运行、
  不抛异常，只是**结果不对**。

> **所以 C# 里这条铁律要靠自己记。** 好在有 `record` 可以一劳永逸。

## 十一、自己动手改坏它（本课最值钱的练习）

**学数据结构最快的方法不是"写对"，是"写坏，然后看懂为什么坏"。**
改完记得跑一遍，对照数字。

| # | 改什么 | 预期现象 | 学到什么 |
|---|---|---|---|
| ① | `MyList.Expand` 里把 `* 2` 改成 `+ 1` | 加 10 万个元素**跑很久**（O(n²)） | 分摊分析的威力 |
| ② | 改成 `+ _items.Length / 2`（1.5 倍） | 扩容次数 15 → 27 | 倍数越接近 1，垃圾越多 |
| ③ | 删掉 `RemoveAt` 里的 `_items[Count] = default!` | 塞 10 万个 `string`，内存下不去 | 陈旧引用 = 内存泄漏 |
| ④ | `LoadFactorLimit` 从 0.75 改成 **0.3** | rehash 次数暴涨，但最长链几乎都是 1 | 空间换时间 |
| ⑤ | `LoadFactorLimit` 从 0.75 改成 **3.0** | 最长链变长到 5~10，查找变慢 | 时间换空间 |
| ⑥ | `GetBucketIndex` 改成 `return 0;` | 所有键一条链，Put 10 万个卡死 | 哈希表退化成链表 |
| ⑦ | `BadPoint` 补上 `GetHashCode` | `Contains` 从 `False` 变 `True` | **哈希契约** |
| ⑧ | `GoodPoint.GetHashCode` 改成 `=> X;`（只用 X） | Y 不同、X 相同的点会被判"相等" | 字段必须**全部**参与 |
| ⑨ | `GetBucketIndex` 里的 `%` 换成 `& (bucketCount - 1)` | 结果**一样**（桶数一直是 2 的幂） | 为什么"2 的幂"是个特殊设计 |
| ⑩ | `MyList` 的索引器越界判断改成 `>= Capacity` | `list[Count]` 不再越界，读到 `default(T)` | Count vs Capacity 的本质 |

**其中 ③ 和 ⑦ 是必做的。** ③ 让你亲眼看到内存泄漏，
⑦ 让你亲眼看到"哈希契约被违反时会发生什么"——**这两件事光看文字是记不住的**。

**验证 ③ 的方法**：

```csharp
var list = new MyList<string>();
for (int i = 0; i < 100_000; i++) list.Add(new string('x', 100));   // 每个 100 字符
Console.WriteLine($"加完：{GC.GetTotalMemory(true) / 1024 / 1024} MB");

for (int i = 0; i < 100_000; i++) list.RemoveAt(list.Count - 1);    // 全删掉
Console.WriteLine($"删光：{GC.GetTotalMemory(true) / 1024 / 1024} MB");
// ★ 清空了的话，删光后内存应该明显掉下来；
//   把 _items[Count] = default! 注释掉再跑一次，内存下不去 —— 那就是泄漏。
```
